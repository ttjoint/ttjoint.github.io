## P3-3 查询描述编译器（已完成）

`src/store/query_lang.js` 已建，**31/31 测试通过**。

设计：`{type, where:[{field,op,value}], orderBy, cursor, limit}` → 参数化 SQL。
- 安全边界：`FIELD_SPECS` 白名单；所有值绑定；LIKE 元字符转义；FTS 输入加引号；limit 夹取（非正数→50，上限 1000）。
- 游标分页（base64url），**不用 OFFSET**。

### 已解决（本轮）

**1. `type` 语法糖曾产出 `WHERE [object Object]`——每个带 type 的查询都无法 prepare。**
`type` 快捷方式是原样塞进 `conds` 的 descriptor，从未走 `compileCondition`，最后被
`conds.map(c => c.sql ? c.sql : c)` 字符串化成 `[object Object]`。测试全部漏掉，因为它们要么
只查 ORDER BY / 索引名，要么不带 type。已修，并在 `compile()` 末尾加断言：任何不是
`{sql}` 片段的元素直接 `reject('INTERNAL')`，同类静默泄漏立刻炸在编译期而非运行期。

**2. 真正的性能问题比文档记录的更宽：不是只有 `dated:false`，而是所有 `ORDER BY` 缺索引支撑。**
实测基线（486,786 人）：`type+name` 121ms、`type+deathDate` 164ms、`dated+name` 816ms。
首屏因 LIMIT 提前停止而看不出，**深度游标页才暴露**（`dated+name` 第 400 页 182ms）。

修法不是发 `INDEXED BY`，而是补索引 + 让 keyset 谓词能用索引：
- `idx_entities_type_time` → `(type, valid_from, id)`；新增 `idx_entities_type_name_id`、`idx_entities_type_valid_to_id`；
  `idx_entities_undated` → `(name, id)`。**尾部 `id` 是游标 tiebreak**，没有它就是 scan-and-discard。
- tiebreak 方向改为跟随主排序方向（`ORDER BY name DESC, id DESC` 而非 `..., id ASC`），
  否则混合方向让索引无法整段满足、也拿不到行值谓词。
- keyset 谓词在**所有排序列非空且方向一致**时改用行值形式 `(a,b) > (?,?)`：
  从 scan-and-filter 变成 range seek，深度页 9.8ms → 0.27ms。
  时间列可空，仍走原来的展开 OR 形式——行值比较传播 NULL，不遵守 NULLS-FIRST/LAST 排序。

结果（第 400 页 / limit 200）：name 0.5ms、birthDate 12–13ms、deathDate 11ms、undated 0.3ms、dated 0.8ms。
代价：库 355MB → 395MB（+40MB），缓存构建 303s。

**3. `idx_entities_undated` 的 `INDEXED BY` 仍需要，不能删。**
`valid_from IS NULL` 无法由 `(type,name,id)` 满足；自然计划器仍选 `idx_entities_type_time`
再排序（0.26ms vs 100ms）。这是唯一保留索引名硬绑定的地方，`db_index.test.js` 断言其存在。

### 教训

- **基准必须测深度游标页。** 所有第一页都在 1ms 以内，看不出任何差别；`MULTI-INDEX OR` 和
  TEMP B-TREE 的代价只在游标推进后才出现。
- **加索引会连带毁掉别的查询。** 只加 `(type,name,id)` 让 name 排序 121→0.12ms，
  却把 `ORDER BY valid_to` 从 164ms 推到 1,971ms（计划器有了更差的选项可挑）。name 与时间
  排序必须**成对**存在，测试断言二者各自命中自己的索引。

## 关键领域规则（踩过坑才定下来的）

### 谓词 / 亲缘
- **方向语义 = 从属视角**：`A --father--> B` 读作「**A 的父亲是 B**」。用朱元璋真实数据证伪过文档。
- **`role` 语义 = 主体扮演的角色**，谓词读法看客体——两者方向相反，极易搞混。
- **性别约束落在客体**（`objectGender`），不是主体。
- **6 个真正独立原语**：`father`/`mother`/`brother`/`sister`/`husband`/`concubine`。
- **复合路径不建派生边**：祖父/孫/岳父由单步边组合得出，另存会让同一事实有两个来源。
- **模糊符号（G/K/P/U）不建边**：那是"说不出几代/哪种"的退化路径，建边等于把"不知道"记成事实。
- **无法判定方向时不猜**，保留 `spouse`/`sibling` 原 key。
- **`maleChild`/`femaleChild` 不改 key**：7,042 条边成本高于收益，是**已知偏差**。
- 谓词 key 必须是 `src/predicates/registry.js` 的英文 key；无法映射的 CBDB 关联**不建边**。

### 数据完整性
- **禁止编造/猜测数据**。缺口记 WARN 并文档化。
- **不可裁定的矛盾数据保留原状 + WARN**（`CONTRADICTORY` 白名单：`['daughter']`），绝不猜、绝不删。
- **姓名不详者**（纯「某」/`陈某(陈某子)`）不作为人格实体。
- **节点名字符串必须原子**——不含括号注记/修饰成分/序号。
- **名字字符串不能作主键**；所有实体用抽象编号；**同名多实体合法**，`NameIndex.get()` 遇同名返回 `null` 并标 ambiguous。
- **改错数据前先备份**：曾有误删 10 个实体，从 `D:\Docs\HumanMapBK` 恢复。
- **`【】` 不是引用标记**：CBDB 的 `史料注记` 把 `【】` 当普通中文引号用，
  `【參考《清代人物生卒年表》#21525.】` 里的 `#21525` 是 CBDB 来源编号，不是实体。
  判引用前**必须过形状闘**（`^(person|organization|event|thing|evidence):[A-Za-z0-9._-]+$`），
  且该闘在两处必须一致：构建期 `check_references.js` 与渲染期 `DataStore.resolveRef`。
  曾经只有前者有闘，于是 2,655 个引文片段全被渲染成指向 `/person/<书名>` 的可点击标签，
  一点就「未找到该实体」。当前发布树里这 2,655 个片段**无一**是真引用。

### 前端数据层 / 搜索
- **`_addRows()` 之后必须 `_refreshLists()`**。两个方法职责不同：前写入 `persons` 等 map，
  后重建 `personList` 等**快照数组**；`SearchEngine._items()` 读的是数组。只调前者，
  数据在缓存里但搜索看不见——`loadSearchBucket` 曾漏掉这一行，导致搜「王」返回不到任何王姓人物。
- **manifest 里的路径必须与写入路径同形**。`search.charToFile` 曾存裸文件名，
  客户端拼成 `data/persons/bucket-000.json` 得 404，又被 `.catch(() => [])` 吞掉，
  于是搜索静默退化为「只扫内存」，看上去像「功能没坏但搜不到东西」。
- **`catch` 不能无条件返回空数组**：它把 null、空结果、真错误三类情况碾成一类。
- **测试要能区分「走了快路径」与「退了 fallback」**。原搜索测试用的名字取自第 1 页，
  而第 1 页本来就在内存里，fallback 也能命中，所以上述两个 bug 全部绿灯发布。
  改为取第 2 页的名字，并断言 `personList` 真的变大。
- **空结果必须有 UI 反馈**。`onKeydown` 首行 `if (!this.results.length) return;`
  在搜不到时直接吞掉回车，用户无法区分「没搜到」和「功能坏了」。

### 详情页：可点引用与来源气泡
- **来源有两套字段，只看一套会静默丢 96%**。`sources`（evidence 实体 id）只有
  导入的现代人物有；CBDB 人物用的是 `provenance: [{rawRef, quote, reason}]`。
  详情页原先只渲染 `sources`，于是绝大多数实体「引用来源」是空白——不是没数据，是没读。
- **`provenance.reason` 是逗号分隔的字段名列表**（`出生年月,逝世时间`），
  一条原始记录可以支撑多个字段行。气泡按字段分组（`fieldCites`），
  点字段旁的 ⓘ 只显示该字段的那条引文。
- **不要在 computed 里对可能缺字段的对象直接取 `.length`**。未解析的 source 没有
  `_evidenceRows`，抛出异常会让整个详情视图挂掉——表现为「按钮渲染出来了，点了没反应」。
  这类故障不会进控制台红字（是未捕获的 promise rejection），只能靠零异常断言发现。
- **字面量谓词不是实体**。`era` 的 `range` 是 `literal`，值（`隋唐及以后`）不可点击、
  不加箭头、不能拼成实体链接。判断依据是注册表里的 `targetType`，不是「看起来像不像 id」。
- **未注册谓词不得静默丢弃**。`if (!relDef) continue;` 让新加的谓词在前端完全隐身；
  现在退化为用原始 key 当标签并标记 ↩。

### SQLite / 查询
- **递归 CTE 必须 `INDEXED BY`**——不是优化提示而是**承重**。不加时 SQLite 扫全部 father 边再 join：13.45ms vs 0.05ms。
- **加索引不是免费的，每加一个都要重跑基准**。`idx_entities_folder_time` 曾让游标分页 0.07ms→575ms。
- **查询计划测试断言"不是 SCAN / 不是 TEMP B-TREE"**，别绑死具体索引名。
- 禁止在查询路径写 `LIKE '%..%'`，文本搜索走 FTS5。
- **不要换图数据库**：本图稀疏高度结构化，换库会失去零依赖/FTS5/游标分页/事务。
  退出条件：若任意深度路径搜索成主线，加预计算路径表 `ancestor_pairs`。

### FTS5 两个坑
- `unicode61` 把整串当一个 token → 必须 `segment()` 在汉字间插空格。试过 `trigram` 被否（要求 ≥3 字符，单字姓氏搜不到）。
- 名字含 `?` 会 `fts5: syntax error near "?"` → 每个 token 用双引号包裹（`ftsPhrase`）。
- FTS 必须**在实体插入循环内同步写**，事后 486k UPDATE 太慢（WAL 261MB 被 timeout 杀）。

### CBDB 数据口径
- **CBDB 0 是未知哨兵**：`realYear()` 把 0→null，负数保留。
- **`c_female`**：1=女、0=男、null/2/其他=未知。
- **无年份者不得静默丢弃**：年份窗口 opt-in，默认全量。
- **全量仅本地，静态只发布 1900+**：靠输出目录分流，绝不靠删数据。
- **朝代 tag 已删除**（`dynastyTag` / `era` 谓词）。时代分类是查询时从 `birthDate`/`deathDate`
  推导的产物，永不入库。理由见 `docs/architecture/节点类型与谓词.md` §4.2.1。

### 布局：宽屏利用率

内容区宽度是 `--layout-max: min(1800px, calc(100vw - 40px))`，
用 `min()` 而不是若干断点——断点只能近似「随窗口变宽而变宽」，
`min()` 是连续的，任何窗口宽度下都恰好占满到上限，没有跳变。

上限 1800px 是实测定的：再宽时单行文字超过约 110 字符，
中文阅读时眼球回扫距离过长。

改动前固定 1200px 的实测浪费：

| 视口 | 改前利用率 | 改后 |
| --- | --- | --- |
| 1280px | 94% | 97% |
| 1920px | 63% | 94% |
| 2560px | 47% | 70% |

**详情页两栏**（`≥1400px`）：主内容 + 关系栏。原先 `.detail-main`
死限 900px，2560px 屏幕上容器 1200px 里正文只占 900px，右侧 300px
白空着，关系卡片还在 240px 一列地往下堆成一长条。
两栏后主栏 1071px、侧栏 669px，侧栏 sticky 跟随滚动。

**检索结果页多列**：`repeat(auto-fill, minmax(280px, 1fr))`，
2560px 下 6 列（原 1 列）。

断点 1400px 的依据：两栏各自最小可用宽度约 560px + 420px + 间距，
再窄下去单栏更好读。

**窄屏修复**：实测 375px 下 `.header-right`（徽标+按钮组）右边界到
411px，整个文档出现横向滚动。`≤640px` 时隐藏 `.mode-badge`、
允许按钮组换行。

 重叠点在哪：site/ 里既有「表示层代码」（拷过去的 js/），又有「数据」（筛出来的 3,604 人）。所以 site/ 同时扮演了两个角色：代码分发和数据筛选。

 现在的做法是「代码原样拷 + 数据另筛」。你提的方案是：代码和数据先渲染合体，再整体快照。

 这就是本质区别。

 ────────────────────────────────────────────────────────────────────────────────

 二、你的方案叫什么

 这不是新概念，有名字：SSG（Static Site Generation）/ 预渲染（prerender）。Nuxt、Next、Astro、Eleventy 都是干这个的。

 流程正如你描述的：

 ```
   全部数据 → View 组件渲染 → 完整 HTML → 裁掉动态部分 → 存成静态文件
 ```

 关键洞察你说对了：「以 view 组件渲染并拼装好的动态展示为基础做快照」。这样静态和动态天然一致——因为静态就是动态跑一遍的产物，不存在两套模板走样的问题。

 ────────────────────────────────────────────────────────────────────────────────

 三、优缺点（针对这个项目具体情况）

 ### 优点：真实的，且相当强

 1. 消除「两套渲染路径」这个整类 bug

 现在 site/ 和 dev 模式的差异已经咬过我们一次：我加了 api.js，site/ 里没有，curl 404。如果静态是动态的产物，这种漂移不可能发生。

 2. 首屏可读，SEO 可用

 现在是空壳，爬虫看到的是 {{ }}。预渲染后 HTML 里直接有内容。

 3. 静态页可离线/无 JS 可用

 这是最实质的好处：家谱页、实体详情页可以不带 JS 也能看。

 4. 视觉一致性由构造保证，不靠测试保证

 你担心的「保持观感一致」根本不需要担心——同一个组件渲染两次，不可能不一致。

 ### 缺点：对这个项目特别致命的

 1. 3,604 个页面 × 每页需要浏览器环境

 预渲染 Vue 组件需要一个 DOM。要么上 jsdom（慢、和真浏览器有差异），要么上无头 Chrome（我刚才那个 smoke test 用的方式）。

 我刚才跑 12 项检查用了约 15 秒。3,604 个页面 × 每个页面导航+等待 API ≈ 数小时。而且这还只是现在的 3,604，不是 48 万。

 2. 与你刚做的架构直接冲突

 api.js 的整个设计前提是「没有后端就优雅降级」。但预渲染意味着必须有后端才能生成静态——build:site 从「读本地 JSON」变成「起一个服务跑一整天」。

 现在 build:site 是无状态脚本，CI 里能跑。预渲染之后它需要一个活着的 SQLite 服务。

 3. 数据变了全部重算

 48 万人的语料，改一个姓名格式化规则 → 3,604 个页面全部重渲染。现在是 build_index.js --publish 筛选 + 拷贝，几分钟。

 4. 只有 3,604 个人有静态页，但交互查询不可能静态化

 时间轴筛选、全文检索、家谱展开本来就是动态的。预渲染只能覆盖「这个人的详情页长这样」，覆盖不了「搜一下王」。

 所以你还是需要 api.js + 动态渲染。结果是两套都在，不是二选一。

 ────────────────────────────────────────────────────────────────────────────────

 四、我的判断

 你的直觉对，但对这个项目的规模用错了工具。

 你说「这种方式我觉得更加清晰」——在页面数量小、数据稳定的场景确实更清晰。Astro 的整个卖点就是这个。但这里：

 - 3,604 页（将来可能更多）
 - 数据每轮 P4 都会大增
 - 查询能力本来就是动态的

 预渲染能省下的复杂度，还不够它自己带来的复杂度。

 但你的核心诉求——「静态和动态观感必须一致，不能漂移」——是完全合理且必须解决的。只是有更便宜的办法。

 ────────────────────────────────────────────────────────────────────────────────

 五、折中方案：分层预渲染

 真正的问题不是「要不要快照」，而是**「哪些页面值得快照」**。按价值分层：

 ┌────────┬────────────────────────────┬───────────────┬───────────────────────────────┐
 │ 层     │ 内容                       │ 现在          │ 建议                          │
 ├────────┼────────────────────────────┼───────────────┼───────────────────────────────┤
 │ 外壳   │ index.html 的 header/nav   │ 空壳，JS 渲染 │ 内联静态 HTML，Vue 挂载时接管 │
 ├────────┼────────────────────────────┼───────────────┼───────────────────────────────┤
 │ 热门页 │ 首页、全部对象、Top N 人物 │ JS 渲染       │ 预渲染（几十个，几分钟）      │
 ├────────┼────────────────────────────┼───────────────┼───────────────────────────────┤
 │ 长尾页 │ 3,604 个详情页             │ JS 渲染       │ 不预渲染，靠 API/分片         │
 ├────────┼────────────────────────────┼───────────────┼───────────────────────────────┤
 │ 交互   │ 搜索、时间轴、家谱         │ JS            │ 只能动态                      │
 └────────┴────────────────────────────┴───────────────┴───────────────────────────────┘

 第一层成本极低收益极高：爬虫和首屏立刻对了，且不需要浏览器。

 第二层可以按需做，几十个页面跑无头 Chrome 是秒级。

 ────────────────────────────────────────────────────────────────────────────────

 六、需要你决定的一点

 在设计之前有个前提必须确认，它决定后面所有方案：

 这个项目的 site/ 到底是要「给人看的网站」，还是「给机器索引的数据」？

 - 如果主要是人：预渲染价值不大，前端已经够快（API 都是 0.1ms 级）
 - 如果在意 SEO / 可离线：外壳内联 + 热门页预渲染是明显正确的
 - 如果它是 GitHub Pages 上的公开数据集：那现在的「筛数据 + 拷代码」其实已经对了，只需要修好外壳

 我不建议现在动手改。我更想知道你是怎么定位这个站的——是当作品集展示、当可检索的数据库、还是当可被搜索引擎收录的公开资料？答案不同，方案差很远。
