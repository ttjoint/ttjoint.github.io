# 项目结构与使用说明

> 面向使用者的操作手册。架构原理见 [`架构设计.md`](./架构设计.md)。

---

## 1. 快速开始

```bash
npm install

# 本地审核后台（写入 SQLite，仅监听 127.0.0.1:8787）
npm run admin
# 打开 http://127.0.0.1:8787/admin.html

# 审核通过后发布到静态数据
npm run publish

# 全量检查（构建索引 + 校验 + 引用检查 + 测试）
npm run check
```

静态站点直接打开 `index.html` 即可（纯前端，数据从 `data/` 读取）。

## 2. 目录一览

| 路径 | 作用 | 是否入库 |
| --- | --- | --- |
| `src/` | 核心库（时间 / 谓词 / 图 / 查询 / 导入器 / CLI） | ✅ |
| `scripts/` | 薄 CLI 封装（导入、校验、发布） | ✅ |
| `tools/oneoff/` | 一次性与临时脚本 | ✅ |
| `test/unit/` | 纯单元测试（无需数据） | ✅ |
| `test/integration/` | 加载真实数据的集成测试 | ✅ |
| `site/` | **发布产物**：可直接部署的静态站（约 4.5 MB） | ✅ |
| `site/data/*/` | 仅含 1900 年起的现代人物 + 全部非人物实体 | ✅ |
| `data/persons/entities/` | 全量人物分片（486,786 个） | ❌ 忽略 |
| `data/*/entities/` | 其余类型分片 | ❌ 忽略 |
| `data/*/manifest.json` | 计数、分页表、搜索桶表（前端启动读它） | ❌ 忽略（全量版） |
| `data/*/index/page-NNN.json` | 列表页，每页 2000 条摘要 | ❌ 忽略 |
| `data/*/index/chrono.json` | 有日期实体，按 JDN 升序（时间轴用） | ❌ 忽略 |
| `data/*/search/bucket-NNN.json` | 首字搜索桶 | ❌ 忽略 |
| `data/*/index.json` | **生成文件**：兼容包装 `{_truncated,_count,rows}`，仅首页 | ❌ 忽略 |
| `data/imports/` | 导入批次与待审核候选 | ❌ 忽略 |
| `js/core/*.js` | 浏览器纯逻辑模块（谓词/时间/存储/关系/搜索/解析/方向/证据展示/渲染） | ✅ |
| `js/services.js` | 服务装配层：把 core 模块接成组件可用的服务对象 | ✅ |
| `js/views/*.js` | Vue 组件（搜索栏/首页/实体详情/编辑器/关系面板/全量浏览/搜索结果） | ✅ |
| `js/app.js` | 路由 + 根实例 + 挂载（约 100 行，无业务逻辑） | ✅ |
| `cbdb_20260801/` | CBDB 原始 SQLite（584MB） | ❌ 忽略 |
| `local_data/` | 后台审核用 SQLite | ❌ 忽略 |

> **`data/` 整体不进版本库**。它是权威存储（486,786 人，487,389 个文件），
> **无法从仓库里任何东西重建**——索引是从分片派生的，从索引倒推只会得到空壳
> （见 `docs/架构设计.md` §6.7）。丢了就是丢数据，不是重建的问题。
> 备份位置：**`D:\Docs\HumanMapBK`**（含 `data/`、`site/`、审核库、`.id_seq.json`
> 及一份 `README.md` 恢复说明）。仓库跟踪的是 `site/`，由 `npm run build:site` 生成。

## 3. 常用命令

### 数据管线

| 命令 | 说明 |
| --- | --- |
| `npm run admin` | 启动本地审核后台 |
| `npm run admin -- --refresh [--from-shards]` | 把分片同步进审核库。默认只补入审核库没有的 id；`--from-shards` 额外用分片重写已存在的记录（修复分片后需要） |
| `npm run publish` | SQLite → `data/` → 索引 → 引用检查 |
| `npm run build:index` | 重建**全量**分页索引（写 `data/`，不进 git） |
| `npm run build:site` | **构建发布站**：清空并重建 `site/`，只收录 1900 年及以后的现代人物 + 全部非人物实体，约 4.5 MB |
| `npm run validate` | 数据完整性校验（读 `entities/` 全量，非截断的 `index.json`） |
| `npm run check:refs` | 检查引用完整性（含 `claims` 中的任职→组织标签） |
| `npm run check:manifests` | 校验分页不变量：页数和等于计数、id 不重复、桶覆盖全量、chrono 有序 |

#### 发布与本地数据的分流

全量语料与公开网站是**两个产物**，靠输出目录分开，绝不靠删数据：

```
npm run build:index   →  data/<类型>/    全量 486,786 人    不进 git（本地查询/管理用）
npm run build:site    →  site/data/<类型>/  3,604 人         进 git（GitHub Pages 部署的）
```

`site/` 是构建产物，**不要手改**。改完 `js/`、`css/`、`index.html` 或数据后重新
运行 `npm run build:site`（它默认 `--clean`，避免旧的已发布条目残留）。

发布过滤器实现于 `scripts/build_index.js` 的 `isPublishable()`：非人物实体全部发布；
人物需卒年或生年 ≥1900（用“已知的最晚一年”判定，所以 1880 生 / 1950 卒的人会发布）。
无任何年份的人**不发布**——48 万 CBDB 导入中25 万人无年份，无法证明其为现代。
被排除不代表对其评价，只是“无法定位到时间”的诚实结果。

### 查询服务（前端后端接口）

| 命令 | 说明 |
| --- | --- |
| `npm run build:db` | JSON 分片 → SQLite 索引库（`local_data/humanmap.sqlite3`，约 5 分钟） |
| `npm run serve` | 启动只读查询服务，服务 `site/` 发布树，http://127.0.0.1:8787 |
| `npm run serve:dev` | 同上但服务仓库根（`site/` 未重建时用），**只绑 127.0.0.1** |

SQLite 只是**索引**，不是权威。它随时可以删了重建，丢了不会丢数据。

**为什么要单独一个只读服务**：`npm run admin` 是写路径（人工审核改数据），
两者不合并——合并意味着一个公开页面能看到写入接口。

**无后端时会怎样**：站点照常打开，只是少了三项能力：家谱图、时间区间查询、
全文检索。前端会静默降级，不报错（静态部署本该如此）。

**开发模式为何不等 `build:site`**：重建 `site/` 要重跑全量发布（几十分钟）。
`serve:dev` 直接服务仓库根，代价是暴露全量语料（48 万人而非 3,604 人），
因此它只绑 127.0.0.1，**绝不能对外暴露**。`raw/`、`local_data/`、`src/`、
`tools/`、`test/`、`.git/` 两种模式下都返回 403。

| `strip_generated_fields.js` | 清掉分片里的生成字段（`detail`）。带 `detail` 说明该分片被索引行覆盖过（见架构 §6.7） |

### 五类节点

| 类型 | 目录 | 含义 |
| --- | --- | --- |
| `person` | `persons/` | 人物 |
| `thing` | `things/` | 非人实体：器物、地点、**出版物**、网站 |
| `organization` | `organizations/` | 组织与国家（含朝代、政党、机关、报社） |
| `event` | `events/` | 事件：发生过的事 |
| `evidence` | `evidence/` | 证据：某处记载了某事 |

实体的 `sources` 现在是 **evidence id 数组**（如 `["evidence:local-000042"]`），
不再是内联对象。需要 URL 时用 `src/store/sources.js` 的 `preferredUrl()` /
`sourceUrls()`，它同时兼容两种形态（迁移期）。

#### ID 不是名字派生的

ID 说明「这条记录从哪来」，名字只是一个可重复、可修改的字段：

| 前缀 | 含义 | 例 |
| --- | --- | --- |
| `cbdb-N` | CBDB 自己的主键 | `person:cbdb-467817` |
| `cpc-N-N` | 人民网的目录号-文章号 | `person:cpc-448511-32550074` |
| `src-…` | 从官方页面 URL 提取的稳定段 | `organization:src-5745000` |
| `local-N` | 无外部来源时分配的顺序号（永不复用） | `evidence:local-000042` |

具体后果：

- **同名多实体是正常的**。CBDB 里两个 `關羽`（467817、497161）是两个人，各有一个 ID。
  搜索 `韓氏` 会返回 9 个结果，靠**约束边**（配偶、生卒、朝代）区分。
- **名字必须原子**。不带 `（1）` 序号，也不带 `(許亨妻)` 这类关系注记——前者是 ID
  该管的事，后者是 `spouse` 边该说的话。`test/unit/id_migration.test.js` 会拦。
- **改名字不会断引用**，因为 ID 与名字无关。
- 想从名字拿到 ID 时必须接受**可能不唯一**：`NameIndex.get()` 遇到同名返回 `null`，
  不猜。

> 旧方案是 `type:sha256(name)[:20]`，把显示名当身份。它导致 9 个 `韓氏` 塌成一个、
> 163 个 cbdbId 各占两个实体、改错别字就断边。详见 `docs/架构设计.md` §6.9。

#### 前端路由与类型表

五类节点的标签、图标、路由全部来自 `js/services.js` 的 `EntitySchema`，
视图通过 `typeLabel(type)` / `typeRoute(type, id)` 取值：

| 类型 | 路由 |
| --- | --- |
| `person` | `#/person/<id>` |
| `thing` | `#/thing/<id>` |
| `organization` | `#/org/<id>` |
| `event` | `#/event/<id>` |
| `evidence` | `#/evidence/<id>` |

> 这张表曾经在 6 个视图里各写一份 `{person, organization, event}`，而数据模型
> 已经是五类。后果是新增类型**不会报错**，只会把详情链接静默指向 `/person/`、
> 把类型标签渲染成原始英文 key。现在 `test/unit/app_wiring.test.js` 断言
> `EntitySchema` 的每个类型都有标签、有路由、并且在 `routes` 数组里真有对应条目。

#### 证据卡片

详情页的来源卡片不再只显示名称和链接。`js/core/evidence.js` 的
`describeEvidence()` 把证据节点转成「载体 / 媒介 / 记载时间 / 可信度 / 链接 / 抓取时间」
的字段行，只输出**确实有值**的字段（不给读者整屏「未知」）。

证据节点住在自己的分片里，人物页不会预载它们，所以详情页 `mounted` 时按需
拉取（`loadEvidence()`）。拉不到的条目显示 id 并标 `_unresolved`，而不是从页面上消失。

> `MEDIUM_LABELS` 在核心与浏览器各有一份（核心给导入器、浏览器给 UI）。
> `test/unit/evidence_browser.test.js` 逐项比对两份拷贝：两份表飘移不会报错，
> 只会安静地显示错误的标签。

#### 亲属代码如何映射

CBDB 的 `KIN_DATA.c_kin_code` 指向 `KINSHIP_CODES` 的 488 个代码。
**本仓库不再手写这张映射表**——以前手写的两张都有错（代码 75 是「父」
却被写成「子女」，方向整个颠倒）。现在一律在导入时从
`KINSHIP_CODES.c_kinrel` 推导：

```
F 父  M 母  S 子  D 女  B 兄弟  Z 姊妹  H 夫  W 妻  C 妾
A 姻親  G 直系祖先  K 同族長輩  P 表親  U 未詳
```

- `F` → `father`，`M` → `mother`，`S` → `maleChild`，`D` → `femaleChild`
- `FF` → `kin`（祖父），`FFF` → `kin`（曾祖），路径记录在 `chain`
- `[missing data]` / `Not Applicable` 是 CBDB 哨兵行，标为未解析、不入图

实测覆盖率 486/488（仅剩 2 条哨兵行）。导入时会把覆盖率打印出来，
如果这个数字下降了，说明 CBDB 升级后出现了新写法，需要补进
`src/importers/cbdb_kinship.js` 的基符号表。

## 4. 时间轴筛选（新功能）

在「全部对象」页点击 **⏱ 时间轴** 按钮启用。

- **拖动条**：左右把手调整起止年份，拖动中间高亮区整体平移。
- **三档精度**：
  | 开关 | 含义 | 覆盖的数据 |
  | --- | --- | --- |
  | 精确日期 | 两端均精确到日 | 如 `1956年9月15日` |
  | 单端点模糊 | 至少一端已知但非精确到日 | 如 `1955年2月生`、`1042–1104年` |
  | 完全模糊 | 仅中值点 ± 大范围 | 如 尧、舜、女娲类传说人物 |
- 启用时间轴后，**没有时间数据的条目会被排除**（无法证明其存在于该区间）。
- 「重置」恢复全时段并勾选全部三档。

筛选逻辑在 `js/core/timeline.js`，与 `src/time/julian.js` 保持逐项一致
（由 `test/unit/timeline_browser.test.js` 锁定）。

## 5. 关系词（谓词）使用

查询与展示都基于谓词原语，而不是自由文本：

```
a 是 b 的父亲      →  father
b 是 a 的子女      →  father/inverse
c 不是 b 的父亲    →  father/negate
```

- 同义词自动归一：`爸爸` / `父` / `家父` → `father`。
- 带性别指称：`儿子` → `maleChild`（仅男性主语），`女儿` → `femaleChild`。
- 反向查询自动生效：查 `父亲` 也会返回以 `子女` 方向存储的边。

扩展谓词：编辑 `data/predicates/registry.json`（如不存在则新建），
加载时与内置注册表合并；冲突别名会记录在 `mergeConflicts` 中待人工确认。

## 6. 新增数据源的标准流程

1. 在 `src/importers/` 写适配器（只做解析，不做入库）。
2. 在 `scripts/` 写薄 CLI 调用适配器，输出**导入批次**到 `data/imports/`。
3. 批次经 `validate:structured` 校验后，通过 `npm run admin` 人工审核。
4. `npm run publish` 把审核结果合并回分片（经由 `entity_writer.upsertAll`）。
5. 跑 `npm run check`，更新本文档与 `架构设计.md`，提交。

> **`npm run publish` 是合并，不是重建。** 它不会删除分片，也不会用空值覆盖
> 已有 `props`/`sources`；未改动的分片一个都不会重写（输出会显示
> `0 files changed`）。如果它报告写入量很大而你又没改数据，说明合并逻辑出问题了。

**可以手工编辑 `data/*/entities/*.json`**（旧文档曾禁止）：`publish` 现在是
合并式的，手改不会被覆盖；但推荐仍然走 admin + publish，好处是有审计记录。

**已删除的旧脚本**：`tools/oneoff/legacy_broken/`（`import_mythology.js`、
`import_pre_qin_han.js`、`import_three_kingdoms.js` 等，共 2371 行）已删除。
它们写于“单文件索引”时代，会读到只有首页的 `index.json` 并覆写它，导致数据
静默丢失。其数据已入库（盘古/女娲/黄帝/孔子/曹操/诸葛亮/刘备/秦始皇 等均已
可在库中查到），引文链保存在 `docs/legacy-import-provenance.json`（237 条来源）。
如需重新导入，按下述流程写正式适配器。

## 7. 每次改动后必须做的三件事

1. `npm run check` 必须全绿。
2. 更新 `docs/架构设计.md`（结构变化）与本文（用法变化）。
3. 提交 Git（索引与 manifest 入库，实体分片可忽略）。

**改了索引格式时**：必须同时更新 `scripts/build_index.js`、
`scripts/check_manifests.js`、`js/core/data_store.js`、
`test/unit/index_paging.test.js`，以及本文的 §2 文件表。

## 9. 验证方法（人工可复跑）

时间轴的浏览器端实现有两层保障：

1. **单元层**：`test/unit/timeline_browser.test.js` 在 Node 中用 `vm` 加载
   `js/core/timeline.js`，逐项比对 JDN 换算与置信度分档是否与
   `src/time/julian.js` 完全一致。
2. **端到端层**：可用无头 Chrome 验证真实渲染：

```bash
python -m http.server 8899        # 在项目根启动静态服务
"/c/Program Files/Google/Chrome/Application/chrome.exe" \
  --headless=new --disable-gpu --no-sandbox \
  --user-data-dir=/tmp/hm_chrome --remote-debugging-port=9344 about:blank
# 然后用 CDP 访问 http://127.0.0.1:8899/index.html，切到 #/all，点击「时间轴」
```

验收标准：`.timeline-filter` 存在、2 个 `.tl-handle`、3 个置信度复选框、
范围文本为 `年份 – 年份`，且表格行数随时间窗变化。

> 注意：清理无头实例时必须按 `--remote-debugging-port` / `--user-data-dir`
> 精确匹配，**禁止**按进程名批量结束 chrome（见 `AGENTS.md`）。
