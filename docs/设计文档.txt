项目需求：

这是一个类似维基、知识图谱的多用户协作式数据库及可视化展示系统。主要结构，是以“现象”作为基本单元进行收集，并进行可视化展示。

==原则==
充分记录由多个信源各自陈述的事件现象侧面，保留全部原始数据证据，记录尽可能完整证据链，在此基础上，采用模块化的、不同粒度的处置函数/规则管道，将原始数据进行格式化、归并、筛选，用于上层分析及分组展示。

==基本结构连线==
 原始数据   --  现象库  --  （多层）域管道  -- 可视化界面
 现象库 -- 转换器（包括时间、空间字段解算，逻辑推理） -- 现象库


==操作流程概览==
用户按规则输入（原始文献原文或个人主观背书的文本）  -  选择现象处置管道等 - 纳入现象库
用户查看可视化 - 选取图表类型或域 - 后台调用域管道或其缓存生成图表及自然语言段落  
用户查看可视化 - 拉取特定原始信息 - 对现象进行增改 - 转入输入界面
用户查看特定域代码 - 增改域情况（仅限有权限） - 更新域版本号并推送 - 后台处置依赖关系及更新

== 现象 ==
什么是现象？就是一个特定的 信源+时间+陈述 组合，是系统的最基本存储单元，且一旦录入就不可更易。
例如，“我看到人民日报记载，1949年10月1日中华人民共和国中央人民政府被宣布成立”即描述了一个现象，具备多个要素，包含了一些据我声称的、声称由人民日报提出的，在特定时空点下所发生的事件，并昭示了一些默许的概念，例如中华人民共和国中央人民政府在特定时空开始出现（并至少持续至一段时间后，即每个现象不可能是时间轴上测度为0的点，而是有最小持续时间的。例如我说“x月x日x时我看到a在吃饭”，不是说我只声称一瞬间的a在吃饭的现象，而是说可能我至少保证了+-几分钟的测度内声称了a的吃饭。这个概念也应当考虑和法律修辞学或者语言学有关），例如人民日报至少在相当的测度时间内成立（排序上早于政府成立，而也早于“我”即观测者的成立，当然这一切都不是“公认”的，其置信度应绑定于“我”即该信息录入者的背书），例如中央人民政府在此测度内应被认为是中华人民共和国的关联实体（下属实体，下属这个词也应当作为一个“谓词”），公历历法至少在特定政府成立的正负测度范围内已被确认……等等这些隐含的“合乎逻辑推测”的现象也是一并被我这一个现象默许的。

现象的存储基本要素：
1、信源（或称视角、提出者，其所属类别是“事件”）序列（即“我在x日期称a书（出版于y日期）记载的b段落证明此现象”，包含一个有序的证据链，即直接提出者是我，就是向本项目录入的负责人（默认自动填充），间接提出者是a书（即录入者声明的出处）。）这个序列可以非常长（a书引述了其他转述等），也可以根据之后的内容进行补充修改。每个单独的现象应至少有一个信源链，如果多人同时声称某事或多书记载某事（或反驳某证据），应分开作为很多信源节点，然后彼此通过逻辑关联，最终联通到相关现象上。每个证据节点的必填内容包括：提出者，提出时间，原始文件索引。这个索引可以是x书x页x行之类，或者url，或者站内录入过的原始数据的索引，或者是其他现象的标号。
用户在录入现象的时候，默认是由用户个人主观（系统注册者的默认身份）提出的，即信源是从用户主观（用户身份+信息录入日期）并直接指向最终现象。信源链的开头总是从上述用户主观节点开始。在录入后，信源链可以追加节点进行延长，或者对现有信源节点提出认同（已查证属实）、存疑标记、替换（不会删除旧数据，而是打替换重定位至新节点）、遗弃（只是增加标记）、共指（独立信源指向同一个现象）等操作，因此这种信源节点仍属于一类特殊的现象，并为其引入特殊的一类meta谓语，这些谓语只能够用于信源相关的主语和宾语间，且这种信源节点本身的信源默认也是用户个人主观（以此支持递归地创作对信源节点的信源链）。
例如：
#1：【（陈述省略）】，时间x，#2   // 格式是  现象编号：【陈述】，发生时间，信源
#2：【{主观信源}，#1】，时间a，#user1  //初始录入者的信源节点
#3：【{主观信源}，#1】，时间b，#user2  //这个是别人的主观认同
#4：【{信源}，#1，#人民日报，当日第三版第6行】，时间y，#5  
#5：【{主观信源}，#4】，时间c，#user1
#6：【{信源替换}，#2，#4】，时间c，#user1

2、时间。时间是一个有序连续计量实体，特定现象只能出现在一个时间段上，应同时标记其被信源所确信发生于的起止范围，也可以是模糊的范围。在标记时刻的时候，应考虑其实存在一个最小观测时段使该现象存续，即，任何现象都不会是在时间线上的单个无测度的点。时间应记录位于的参考系，未必是公历日期，但出于系统之后将要加入的多种对比图表等功能，时间应当是可比较的，且应容许多个体系的跨体系比较（例如用OTL现实世界公历与某个虚拟宇宙的其历法放在同一个图表下进行跨“视野”比较）。应考虑时空推测的失准，因此就算是都用某种标准儒略日的序列来内在存储时间，也应当容许在特定事件记录下对此进行修正，而非直接套用目前的公历推算。为了时间精准，本系统基础层应加入多种日历带有天文学算法的精确换算。目前仅考虑精确到秒。
目前认为时间字段应记录未加第三方限定的原始表述，以额外插件进行非侵入式映射。映射结果作为单独现象，类似于：
#1：【（陈述省略）】，时间x，#2
#123：【{时间映射}，#1，公元2016年9月30日 21:55:00（UTC+8）】，时间y，#TimeBot_v1

3、陈述。
陈述，是本系统精简化的最基础语义组，应只表达单个简单含义，一般是主谓宾结构。复杂句式及修饰成分应以外部插件提前拆分为多个单独现象来入库。其中，主语、谓语或宾语各自指向一个临时性、唯一性的指代符号，谓词就是动词或者动词短语，在显示中如果用图上节点表示主语或宾语，那么谓词就是节点间的连线。
例如：“我的父亲是张三，我是张小三”其中“是”所对应的就是谓词，等价于一个“等同”关系的谓词。该现象应在系统内录入时，拆为
#1：【有（#VA），我（#A） ，父亲（#B）】
#2：【是（#VB），父亲（#B），张三（#C）】
#3：【是（#VC），我（#A），张小三（#D）】
#4：【{等同}，#VC，#VB】
或者
#101：【父子关系（#VX），我（#A），张三（#B）】
#102：【姓名（#VY），我（#A），张小三（#C）】

主语、宾语可以是空值。主语、宾语既可以是临时性新符号，也可以是一个现有的符号，也可以是现有的现象标号（在上面的例子里，现象标号是#1#2，实体临时符号是#A#B）。但是，如果指向现有的情况，应仅仅存在于同一个工作域下（类似于函数在特定定义域之下），即实质上是在一句话当中的拆分，或者连续多句话里面用代词来指代上文逻辑提及的对象，而非不同人或不同时间下的多个原始录入，在这种情况下，其实多个现象是一个复杂现象的共时性拆分结果，逻辑上是恒等的，因此，可以容许在多个独立现象之间直接采用同一个符号作为主语或者宾语。而每个现象的谓词永远是单独标记的符号。
谓词（在上面例子的符号是#VA#VB）不可是空值，但不必在某个预先标定的白名单内挑选，而是可任意使用（应有系统或社区的建议或约定或推荐列表，以防现象数据录入时的大量任意性的语句拆分，导致后续逻辑处置的混乱）并作为一个临时符号存在。
主谓宾结构中，谓词前可以放置否定（非）结构标记，用于表示该现象是一个拒斥性的记载，例如“我的父亲不是李四”“并非是我偷了钱”。否定标记最多出现1次。
#113：【{非}是（#VD），父亲（#E），李四（#F）】
#114：【{等同}，#E，#B】
#115：【{等同}，#VD，#VC】

系统应该内置少量meta谓词，用于各个指代符号之间的逻辑变换，以支持后续高阶分析，但是凡是使用meta谓词的现象，应是符合特定条件才可录入。
例如{等同}谓词构成的现象，用于标记两个现象里的某个符号（在这位录入者眼里）是完全双向等价的，是同一个东西，因此在系统中（在逻辑上）是图上两个点之间有了双向连线，可互换，而且有传递性。但条件是，使用{等同}的时候，主宾应该皆是谓词或皆非谓词。
谓词在现象中必不可少，是意义的来源，但是意义是从词的用法的总括，而不是某种先验的、内含的形而上的东西。用户最终录入系统的谓词选用可能较为复杂，因此需要用域进行一些后处理。

== 域 ==
定义域，或称之为命名空间、视窗……是指为了系统进行显示和运算，所框定的某种运算函数或者规则集，例如，本系统对于现象的每个具体可视化展现都依赖于一个特定的定义域，例如，用于展示人物家族血脉谱系的家谱定义域，囊括作为父亲、作为儿子、是女儿、是妻子、是情妇、是爷爷、是外甥……之类的一堆谓词，并且规定按照某种有序关系进行展示，即父亲在上、儿子在下、孙子在儿子更下的拓扑顺序标定规则，产生出类似遗传系谱那样的一个有序图表，作为该定义域的展示效果。
我希望系统的展示能多元化和方便调节，例如，我应当可以划分只看其父系/母系的图谱，只看在美国国籍下的图谱，或者综合融合“血缘”和“商业”两个定义域，来直观的看出这个人的公司及同事里有多少是他们家族的，亲疏远近情况。此外，图谱应当有多种，例如基础图谱如果是毋论现象时间而都纳入，那么应当还有那种“侧视图”即以纵坐标是年份/时间轴，横坐标是不同的现象，来可以选择浏览特定时间节点上这个人仍存在的亲属关系之类。还有时空图谱，即类似于用于展示某个事件在时空下（例如一场持续多月、扩展到多个城市的运动）的总体情况，可以拖动地图及时间轴来显示特定时空该事件的切片。此外，定义域也可以声明遣词造句方式，即例如人物的条目，用特定的人物模板定义域来根据现象集提取并声称一段描述（例如：某人（1933-1964），字某某，某国某地某某籍人，某国某形容词某某学家……）这种生成模板也是某种定义域。注意，这表明本系统的展示效果里面的“自然语言段落”实际上均应该是生成式的，而非wikimedia系统的那种人写的词条。
定义域应包括不限于以下类别：
实体：一个被建构的实体，人、组织、国家……都是实体。事件的时空范围由现象标定，即，本系统中不在基础层面上存储例如“鸟都会飞”“中华人民共和国从1949年至今存续”这样的数据，而是应以“我：人民日报记载，1949年10月1日中华人民共和国中央人民政府被宣布成立”“我：产经新闻记载，1999年3月12日中华人民共和国发布了某新闻”……之类的现象，而这些现象正由于其同时指向了特定实体作为主谓宾之一，因此共同框定了中华人民共和国作为实体同时存续在这两个点。本系统中的任何实体都是通过现象来自下而上建构的。
概念：一个概念也是从现象中通过域的形式定义的。人的概念之存在，是依靠多个不同的现象中的主语或者宾语是暗示出有“人”的属性，因此可以称“人”的概念在这些时段框定的范围内以某种程度成立。例如，“我吃饭”其中有两个实体或概念：我，吃饭。该现象（【吃饭，我】）同时（以其信源的置信程度）保证了在此时间范围内“我”存在且“吃饭”概念也存在。
转换器：例如公历农历互转、父子关系扩充（即，如果写了【父亲，A，B】那么用该转换器自动添加【儿子，B，A】或者【女儿，B，A】）、逻辑推导（例如根据【父亲，A，B】推导【性别，A，男】）等。这种转换是一次性不可逆的，因其输出的结果是向数据库中自动写入一系列现象，而现象一旦加入是无法被硬删除的。
抽象层级：例如一个关于中国党史研究的域，根据原始的现象数据筛选出特定条件（例如，信源属于本域自定义白名单用户，或非本域黑名单用户的主观支持者超过3，或以特定白名单现象作为主语的那些现象，且时间在特定范围（大于公历1921，OTL时空））的现象集合，并对其进行整合归纳，按关键字或正则或某种方式从中抽象出较为高层的字词（例如，中国共产党、毛泽东、长征、新民主主义革命）作为该层级的输出产物。这种抽象层级用于提供一系列向上封装的抽象符号编号，以屏蔽实际杂乱数据细节，支持高层次的对象分析域编写，并提供性能缓存。注意，每个层级不仅仅可以直接引用现象，也可以将这种抽象概念单元作为其规则的参数，但在实际运算时往往是向下连续展开为实际在现象图网上的运算。需要考虑这里的一致性问题。
定义域之间可以像npm程序包类似的方式管理引用，如果引用就证明完全引入相关定义域特定版本的抽象概念（引入的概念可能在域规则代码中需要加入前缀）。如果子包更新了版本（即某些域的规则发生了更新变化）可能会触发依赖项连锁更新提醒。其中一些包允许使用js代码之类的方式来引入复杂算法处理之类，例如日历或geo地理位置映射，或需要加载特定的资源类库。

== 用户界面 ==
该系统最终呈现类似于一个wiki，但是区别在于并不是以词条组织文件，每个人看到一样的内容，而是以自选的模块化图表/生成式词条来呈现，用户可能是从库中检索特定事件前因后果相关信息，并使用一个自定义域来将其呈现为时序列表。也可以将一组选定范围内的人物/组织绘制关系拓扑图形，并在该页面中查、增、改特定关系或概念。
注意，用户的任何输入首先按原文存储入后台作为主观证据（用户也可以录入长篇的历史文献或图片、pdf之类），然后其实际能够被反馈到各域的是以从原文自动或手动提取出的现象组为基础而不是直接去查询原始数据。提取过程在一个输入界面由用户可控可观察地实现，类似传统wiki的编辑界面，只不过编辑结果是生成的一系列现象，用户确认后完成一次提交，即现象永久不可逆入库。用户也可以打开查看任何已上传的（任何人的，非主观的）文献数据并对其片段进行提取为现象的操作（即，类似别人上传了一本古书，你可以去在里面提取，但是别人主观提交的句子片段你就不能去从中提取现象，你可以从自己以往提交的句子片段证据中多次提取现象）。
作为最基础的功能，用户可以查询任何现象的数据，证据链，关联现象等，可以查看自己曾经上传的各类数据。用户不能删除以自己身份提交的文献、现象，但是可以（通过含特定谓语的新的有关现象）软性标注他们为已过时、已放弃主观承认、已反对（区别在于，已放弃是将原有主观支持取消，改作为未有定论的现象，而反对在于明确表示该现象值是主观取反，例如，【身份，我，大学生】放弃是【{无依据}身份，我，大学生】，而取反是【{非}身份，我，大学生】）
系统应具有身份管理，用户可被赋予不同权限是否可以创设编辑某些域、是否可以公开发布域等，如恶意提交太多可能加入限制或封禁组，用户身份组也是域规则中可以拿来筛选的条件。

== 性能和规模 ==
本系统希望做成类似wikimedia那种的可轻可重的、可以迁移部署的基于web的交互系统，最多应可以允许数千用户同时操作、多达上亿现象、数百万层级的运算处理（有些层级，例如实体，只会查询影响极少量现象）。应参考已有的类似知识系统/众创类知识图谱网站/百科的性能指标和数据持久性、数据安全性。




录入的原始资料应当和wiki类似可以以查看源码的形式查看和编辑，也提供实时的可视化显示。这种语法有点像编程语言，即应当是严格遵循特定完整句式的，并用一些特定符号标定划分出现象的上面说的那些元素。可以认为一个句子就是一个现象的定义。

1、我认为本系统应当是高度兼容、容忍用户自由输入的，系统内置的任何计算函数都应当作为模块组件可以在展示时候进行替换，例如时间空间及主语是否一致等，都是在特定定义域下进行的，乃至于用户应当可以随意加入自己需要的域（view）来自定义自己对某个概念的工作空间，并保存他的个性化配置，例如他需要用民国纪年法或者太平天国独有的天历对某些历史现象进行考察推算，那他就自己定义一个在他自己命名空间（类似wiki也有User:下的命名空间那样）然后在里面搭建他的多个个性化配置。然后每个用户也可以公开自己的一些配置以作为类似插件的方式来对数据进行过滤筛选与可视化演算。因为这个系统实质上并不需要做成某种高度自主性、智能化的系统，而是作为一个多人共同编辑的协作的wiki类或者学术研究用的支持系统。

2、多个现象里的主谓宾哪怕名字一致，怎么被确信是同一个连贯实体呢？而且存在大量重名、别名等现象。按我的设想，每个现象提出时带有提出者-提出日期等内容前缀的，即默认他们都是唯一unique的新实体。那么实体间如何被划归同一个，包括谓词如何划归，这也是一个主要的问题，涉及到系统最终会不会由于太过杂乱而难以理出头绪、空有数据集而缺乏归纳整理的情况。这方面你有什么好的建议吗？可能可以以ai辅助类似于wiki的自动处理bot那样进行一些自动化处理，当然都会打上处理者（也就是bot）的名号来作为信源，即对于这些现象的解释也应该是一种“元现象”或者合并为类似“提出者”那种可信链条，即用一个网站本身的默认bot作为一些基础整合的信源提供者，如果你愿意在定义域里相信bot（默认勾选）那么就用，不愿意的话你也可以基于最原始单独的点进行手动勾画（就是定义你自己的合并方式）。

另外我们希望保留文本原文，即留存可作为存档的可触达出处/证据，而由于文本段落或媒体资源可能同时表达了一连串我上述定义的原子化现象，那么实际上相当于是对于同一个现象的多种描述（例如现象描述某时空a杀了b，也有可能同步叠加表述了多个议题例如a射击了b，a谋杀了b，之类）但是这种情况，由于我为了保有后续的质疑链，因此需要原子化每一个单独的小的现象，不应轻易进行整合到同一个现象里。对于信源，我上面描述为可以进行链式处理，这相当于只是对单个现象，而如果多个现象指向了同一个主体（事件），那么我在后一个现象作出录入的情况下，通过gui挑选了某个已存在的对象（例如中国）作为主语，但是这时候是否应该自动首先将我的现象描述的主语定义为unique的成分，然后通过附加一个同时声明的主语一致的主张句，相当于同时自动录入两条资料，这样来表达这个关系，而非在原子现象里面增加一个字段来标示。

我希望该系统可以支持类似代码版本管理/调色板那样，参与者可以对某个现象原子进行支持（提供额外资料作为附加支撑节点，用特殊连接线连接？或者附加在目前节点的证据链上，标记版本号），可以进行反驳，进行认可（类似于点赞，即以独立查证了确实该现象成立的声称，用于增加节点权重之类？），进行补充或修正（即可能源节点对时空的描述不够精确或有误差，进行修补。当然这种修补也是修补者的个人主张，用个人信用背书。系统内的所有提交都默认是由某个用户进行，当然每个自然人可以申请或切换多个用户身份。是否允许对谓词或者主语宾语进行修补？这样似乎也不太符合我的需要），此外关于事实（即多现象组合）我又感觉似乎不需要这样的单独分层数据节点来表示，即，事实既然是由很多现象进行标定（至少1个），那么它应当是对于现象的一种定义域

综上，是目前本项目的主要构想。请你进行具体可实施性的讨论，指出需要进一步细化或者存在歧义、你不懂的地方。












1. 最接近的整体架构：Event Sourcing + CQRS（事件溯源 + 命令查询职责分离）
这是目前与你的设计哲学最契合的软件架构。

你的概念Event Sourcing / CQRS 对应原子现象Event（不可变事件）支持 / 反驳 / 修正 / 认可不同类型的 Event定义域（View）Projection / Read Model多层定义域叠层多个 Projection 可以互相依赖或再投影用户选择采信哪些主张Projection 的过滤与合并规则最终展示Query 侧的 Read Model
典型系统：

银行核心账务系统、电商订单系统、协作编辑后端（如 Linear、部分 Notion 实现）
开源框架：Axon Framework、EventStoreDB、Akka Persistence、Marten（.NET）等

可直接借鉴的点：

所有写操作只追加事件，从不修改旧事件。
读侧通过投影（Projection）把事件流“折叠”成当前需要的状态。
投影可以有多个、可以版本化、可以按用户/按场景定制。
投影失败或规则变更时，可以从头重放事件流重新生成。

这几乎就是你系统的工程翻译。

3. 多层视图 / 规则叠层的经典模式
这些模式专门解决“底层很散 → 中间多层计算 → 最终视图”的问题：

Materialized View（物化视图）
数据库里很常见。底层表原子，视图根据规则预计算或实时计算。你的定义域就相当于可配置的物化视图。
Pipeline / Transformation Graph（数据管道图）
类似 Apache Airflow、dbt、或现代数据湖的 Transform 层。每个定义域是一个 transform 节点，可以依赖其他定义域的输出。
Lens / Optics 模式（函数式编程）
从复杂数据结构中“聚焦”出需要的部分，并允许在聚焦视图上进行修改（修改会反向传播）。虽然你的数据不可变，但“Lens”的思想可以用来描述定义域如何从原子现象中抽取和重组。
Policy / Rule Engine 叠层（如 OPA、Drools、或游戏引擎的 Buff 系统）
多条规则按优先级或组合方式作用于同一批数据，最终得到不同视角的结果。定义域之间的“采信规则”可以用规则引擎实现。
Collaborative Filtering + View Composition（如 Notion 的 Linked Database + Filter + Sort 的多层组合，或 Airtable 的 Interface）
用户通过叠加 Filter、Group、Sort、公式来从同一底层数据得到完全不同的界面。

5. 针对你系统的具体架构建议（综合以上）
推荐采用以下分层：
1. Event Store（现象存储）
   - 所有现象、支持、反驳、修正、Identity Claim 都以不可变事件追加
   - 带完整提出者链与证据引用

2. Projection Engine（定义域引擎）
   - 每个定义域 = 一套投影规则（过滤哪些事件、如何合并实体、如何计算权重、如何生成展示结构）
   - 支持定义域之间的依赖与组合（叠层）
   - 可物化（预计算）也可即时计算

3. View / Renderer 层
   - 图谱、时间轴、时空切片、自然语言生成、表格……
   - 只消费投影后的结果
这套架构在工业界已经过大量验证，既保证了底层的原子性与可审计性，又通过中间的投影层解决了“太散、难以直接使用”的问题。

总结：

你的设计在软件工程上最接近 Event Sourcing + 可配置 Projection（定义域） 的架构，同时在知识管理侧可参考 Wikidata 的陈述模型 + Hypothesis 的标注交互 + Notion/Obsidian 的视图组合。
这些都是已经跑在大规模生产环境中的成熟模式，完全可以支撑你想要的高度原子化底层 + 多层定义域叠层。
