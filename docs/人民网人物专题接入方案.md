# 人民网人物专题接入方案

## 1. 对源站的分析（2026-? 离线核验）

入口 `https://cpc.people.com.cn/GB/64162/394696/index.html` 是一个专题索引，不是稳定 JSON API。页面中存在大量重复链接，人物详情主要通过 `n1/...html` 文章页提供，另有“报道集”栏目页。入口当前可见的核心人物包括习近平、李强、赵乐际、王沪宁、蔡奇、丁薛祥、李希等，并延伸到全国人大、政协、国务院组成部门和民主党派等人物/职务页面。页面会随届次、机构调整而变化，且部分链接存在旧年份、重复人物、HTTP/HTTPS 混用和同一文章承担多个职务标题的情况。

因此不能把“抓到的当前职务”直接当作永久事实，也不应在 GitHub Pages 浏览器端实时抓取。正确的粒度是：

- 人物实体：姓名、别名、标签；
- 任职主张：人物—所属组织，附职务、起止时间、来源；
- 原始证据：人民网文章 URL、抓取时间、标题、摘要/原文快照哈希；
- 采集批次：入口 URL、运行时间、解析器版本、链接数量、失败列表。

人物同名不能仅用姓名作唯一键。第一版脚本保留现有项目兼容性，并用姓名合并已有数据；正式生产应升级为稳定 `entityId`，把姓名作为 `label`，并通过人工确认或身份主张完成合并。

## 2. 已加入的离线导入器

文件：`scripts/import_cpc.js`

```bash
node scripts/import_cpc.js --dry-run
node scripts/import_cpc.js --limit=20 --dry-run
node scripts/import_cpc.js
```

脚本特点：去重入口链接、限速、记录来源 URL/抓取时间、保留抓取摘要、失败不中断、支持 dry-run。它只负责“发现和初步归档”，不应自动把文章中的所有叙述转换为关系；任职关系、出生信息等应通过人工复核或可审计的抽取器确认。建议先提交 `data/imports/cpc/<timestamp>/manifest.json` 和原始页面快照，再将审核结果合并进 `data/persons/index.json`。

运行前请确认人民网的 robots、版权和转载要求；仅保存必要的事实性元数据/链接更稳妥，不要未经许可批量镜像全文或图片。

## 3. 当前代码结构的主要问题

目前 `index.json` 是超大单文件，前端启动时一次性加载全部人物、组织、事件，并用 `localStorage` 覆盖本地修改。这适合演示，不适合持续增加中央领导、任职时间线和证据链：首屏、搜索、编辑、版本审计彼此耦合；关系定义也混在 `js/app.js` 中。

建议分阶段改造：

### A. 先做静态站可承受的改造

```text
data/
  manifests/persons.json       # 分片清单、版本、统计
  persons/index.json            # 兼容旧数据的轻量索引
  persons/<id>.json             # 详情与关系
  claims/<id>.json              # 不可变主张/任职记录
  sources/<batch>/<id>.json     # 来源元数据
  imports/cpc/<batch>/manifest.json
js/
  core/entity-store.js          # 加载、缓存、版本校验
  core/source-store.js          # 来源/批次
  core/claim-store.js           # 主张与证据
  views/person-list.js
  views/person-detail.js
  views/timeline.js
  app.js                        # 路由与组装，不再承载全部领域逻辑
scripts/
  import_cpc.js
  validate_data.js
```

首次加载只读 manifest 和摘要；打开详情时再 fetch 单人物文件；列表/搜索使用预生成索引。这样可以继续部署到 GitHub Pages，也能减少启动内存和页面卡顿。

### B. 把“实体”和“主张”分开

```json
{
  "id": "person:uuid",
  "name": "李强",
  "type": "person",
  "aliases": [],
  "sources": ["source:cpc:..."],
  "claims": ["claim:..."],
  "status": "published"
}
```

```json
{
  "id": "claim:employment:...",
  "subject": "person:uuid",
  "predicate": "所属组织",
  "object": "org:国务院",
  "qualifiers": {"role":"国务院总理", "start":"2023-03-11"},
  "sourceRefs": ["source:cpc:..."],
  "assertedAt": "...",
  "confidence": "unreviewed",
  "provenance": {"collector":"cpc-importer", "parserVersion":"1.0.0"}
}
```

这样同一人物可以有多条任职记录，来源冲突也不会覆盖原数据；“支持、反驳、修正”是新主张，不是修改旧主张。现有 `relations` 可以作为兼容的投影缓存，逐步由 claims 生成。

### C. 新增面向展示的视图

- **人物目录**：按届次、机构、职务、在任状态筛选，虚拟列表/分页；
- **人物详情**：基本信息、任职时间线、关系图、证据来源、数据状态；
- **组织视图**：机构树/领导班子时间轴；
- **证据面板**：来源 URL、抓取批次、原文摘要、人工审核状态；
- **图谱过滤**：默认只显示已审核或用户选中的来源，避免把未经核验的自动抽取当成事实；
- **导入报告**：新增、更新、重复、失败、待审核条目。

## 4. 后台启用建议

静态文件负责发布“已审核投影”；本地后台负责抓取、解析、审核、写入和重建索引。建议增加明确命令：

```bash
npm run import:cpc -- --dry-run
npm run validate
npm run build:index
```

导入必须是幂等的（以规范化 URL/外部文章 ID 去重），每次生成 manifest 和校验报告。若未来多人协作，`localStorage` 不能作为数据库，应迁移到 SQLite/PostgreSQL；静态站只消费版本化导出文件。

## 5. 必须人工确认的边界

1. 文章标题中的职务不一定代表文章正文中的完整任职事实；
2. 同名人物、简称、民族/外文姓名不能只靠字符串合并；
3. 当前页面可能包含未来日期或后续改版链接，导入时需记录抓取时间并标记待审核；
4. 自动抽取的简介和关系不得覆盖已有人工数据；
5. 源站变更、HTTP 重定向、编码异常、限流和版权政策都要进入导入报告。

推荐实施顺序：先运行 dry-run 检查链接和数量 → 引入 source/claim 模型 → 加载分片和时间线 → 增加审核后台 → 最后再启用自动关系抽取。这样既能纳入人民网专题，也不会破坏现有历史人物数据和本地编辑功能。
