# HumanMap 项目架构

> 面向"历史至今的人物家谱、组织与企业关系"的可视化知识图谱。
> 本文档描述整体架构、数据模型与扩展方式。**每次结构性改动后必须同步更新本文档。**

> ⚠️ **架构正在向四层重构（raw / entities / index / views）。**
> 本文描述的是**当前已实现**的单层架构（`data/` 既权威又派生）。
> 分层的目标、理由与实施顺序见 [`docs/architecture/分层架构重构方案.md`](architecture/分层架构重构方案.md)，
> 两者冲突时以分层方案为准。

---

## 1. 设计目标

| 目标 | 落地方式 |
| --- | --- |
| 支撑超大规模实体（486,786 人物已入库） | 分片 JSON + 派生图索引，存储与查询分离 |
| 关系词可检索、可分类、可合并 | **谓词原语注册表**（谓词即边类型） |
| 反向 / 否定语义 | 谓词前缀修饰符 `/inverse`、`/negate` |
| 任意历史时间跨度（公元前至今） | 一律以**儒略日（JDN）**存储，支持模糊区间 |
| 时段时间轴筛选 | `TimeRange{start,end,mid,uncertainty}` + 置信度分桶 |
| 可审计、可回溯 | 每条边记录 `createdAt`（录入时刻）与 `sourceUrl` |
| 原始语料可回溯 | **目标态**：raw 层只追加，实体带 `provenance`（待实施） |
| 静态站点可部署 | `site/` 为发布快照；`data/` 为本地全量权威 |

**约定**
- `src/` 内全部为 `module.exports`，不直接读 `process.argv`。
- `scripts/` 只做参数解析与调用，便于测试。
- 临时脚本一律放 `tools/oneoff/`，不进入 npm scripts。
- **实体详情分片不可重建**：它是权威存储。任何“从索引重建分片”的脚本都是错的
  （见 §6.7）。`data/` 整体不进 Git，备份在 `D:\Docs\HumanMapBK`。
- **`site/` 是构建产物**，由 `npm run build:site` 生成，不要手改。
- **新增类型只改 `src/store/entity_types.js` 一张表**。此前 FOLDERS 被复制到 9 个
  文件，加类型时漏改一处就会造成「部分类型导入、其余静默跳过」。

## 3. 数据模型

### 3.1 节点（Node）

节点分**四类基础节点 + 一类证据节点**。组织与国家是同一类（用 `props['类型']` 区分
朝代/诸侯国/王朝/报纸/政党），不设独立的 `state` / `polity` 类型。

| 类型 | 目录 | 含义 | 例 |
|---|---|---|---|
| `person` | `persons/` | 人物 | 张澜、石泰峰 |
| `thing` | `things/` | 非人实体：器物、地点、**出版物**、网站 | 人民日报、人民网、中国政府网 |
| `organization` | `organizations/` | 组织与国家（含朝代、政党、机关、报社） | 人民日报社、最高人民检察院、中国共产党 |
| `event` | `events/` | 事件：发生过的事 | 中共二十届一中全会 |
| `evidence` | `evidence/` | 证据：**某处记载了某事** | 人民日报 1978-05-11 某篇报道 |

**事件不是证据。** 事件是「发生过的事」，证据是「某处记载了某事」，两者用
`documents` / `documentedBy` 连接。把二者混为一类会让「同一件事有多处记载」
无法表达。

**证据的主语必须是系统内已注册的实体。** 「人民日报」是 `thing`，「人民日报社」是
`organization`，「张澜」是 `person`——都可以作证据的主语；「某篇报道」本身不能
指向一个未注册的字符串。

```jsonc
{
  "id": "person:cbdb-467817",      // 不透明 ID：类型 + 来源键（见 §6.9）
  "type": "person | thing | organization | event | evidence",
  "name": "石泰峰",                 // 普通字段：可重复（同名多实体合法）、可修改
  "aliases": ["石泰"],
  "props": { "性别": "男", "出生年月": "1956年9月", "籍贯": "山西榆社" },
  "summary": "…",
  "sources": ["evidence:local-000042"],  // 证据引用，不再是内联对象
  "external": { "cbdbId": 467817 },     // 来源自己的主键，ID 由它派生
  "lifespan": { "start": 2435731, "end": null, "mid": 2435746, "uncertainty": 0, "precision": "month" }
}
```

证据节点的形状（`evidence` 类型）：

```jsonc
{
  "id": "evidence:local-000042",            // 不透明 ID，与标题/日期无关
  "type": "evidence",
  "name": "人民日报 1978-05-11 某篇报道",    // 展示名，由 carrier + documentedAt + title 生成
  "title": "某篇报道",
  "carrier": "thing:local-000007",          // 载体：谁刊载了这条记录（必为已注册实体）
  "carrierName": "人民日报",
  "medium": "newspaper",                    // 见 MEDIUM 枚举
  "documentedAt": { "start": 2443640, "end": 2443640, "mid": 2443640, "uncertainty": 0, "precision": "day" },
  "url": "http://paper.people.com.cn/…",
  "accessedAt": "2026-10-17T08:45:29.296Z",
  "reliability": 1.0,
  "unresolved": false                       // true = 载体无法推断，诚实暴露而非编造
}
```

**证据 ID 用 `(carrierName, dateKey, title)` 而非 URL**：同一篇文章被两处引用应当是
一个节点，同一报纸同日的两篇文章应当是两个节点。用载体**名**而非 id，避免载体改名
后所有证据 id 失效。

**`data/<type>/index.json` 是生成文件**（仅首页兼容包装），除 `build_index.js` 外
禁止写入；结构为对象包装 `{_truncated,_count,_pageSize,_manifest,_note,rows}`。

### 3.2 边（Edge）—— 一切关系皆为断言

```jsonc
{
  "id": "edge:<subject>|<key>|<object>|<role>|<span>",
  "key": "father",            // 谓词键，可带 /inverse 或 /negate
  "subject": "person:aaa",
  "object": "person:bbb",     // 或字符串（literal: true）
  "literal": false,
  "role": "总理",              // 限定词：官职/头衔
  "range": { "start": …, "end": …, "mid": …, "uncertainty": 0 },
  "note": "",
  "sourceUrl": "",
  "confidence": 1.0,
  "createdAt": "2026-10-17T03:00:00.000Z"   // 录入时刻
}
```

**属性也是边**：`性别`、`民族`、`学历`、`籍贯`、`出生年月` 等 scalar 值被提升为
literal 边（`gender` / `ethnicity` / `education` / `residedAt` / `birthDate`），
因此谓词检索、可视化、过滤共用同一套索引。

## 4. 谓词原语（关系词）

### 4.1 定义

谓词不是自由文本，而是注册表中的原语，具备：

| 字段 | 说明 |
| --- | --- |
| `key` | 规范键，如 `father` |
| `label` | 默认显示名，如 `父亲` |
| `domain` / `range` | 主语 / 宾语类型约束 |
| `inverse` | 反向谓词键（`father` ↔ `childOfFather`） |
| `aliases` | 同义词，检索时归一（`爸爸` → `father`） |
| `symmetric` | 自反谓词（`spouse`,`sibling`,`friend`） |
| `negatable` | 是否允许 `/negate` |
| `subjectGender` | 主语性别约束（`maleChild` = `male`） |
| `qualifiers` | 允许的限定词：`role`/`dates`/`place`/`note`/`source` |

### 4.2 修饰符而非新谓词

```
a 是 b 的父亲      →  (father,        a, b)
b 是 a 的子女      →  (childOfFather, b, a)        ← 等价，故存为 father/inverse
c 不是 b 的父亲    →  (father/negate, c, b)        ← 明确否定
```

- `/inverse` 表示该边以反向视角记录；查询 `父亲` 时同时命中 `childOfFather`。
- `/negate` 表示"明确不成立"（如"已不在该地任职"），区别于"无记录"。

### 4.3 带性别的指称

不做谓词爆炸，而用 `subjectGender` 约束：

```
儿子 = (father/inverse) 且 subject.gender == male
女儿 = (father/inverse) 且 subject.gender == female
```

因此检索"儿子"只会返回男性子女。实现见 `registry.js` 的 `maleChild` /
`femaleChild`（`genderFamily: 'child'`）。

### 4.4 同义词合并

- 内置别名在 `BUILTIN` 中声明。
- 外部扩展放 `data/predicates/registry.json`，加载时合并。
- `PredicateRegistry.suggestMerges()` 给出候选合并建议，**不自动应用**，
  由管理员确认后写入 registry.json。
- 冲突（同一别名指向两个原语）记录在 `mergeConflicts`，不静默覆盖。

## 5. 时间模型

### 5.1 儒略日

所有时刻存为 JDN（整数天）。已验证：`2000-01-01 → 2451545`、`1970-01-01 → 2440588`，
并支持公元前（天文纪年，1 BCE = 0）。后续可扩展历法/年号层，JDN 作为统一底层。

### 5.2 TimeRange

```jsonc
{ "start": 2435731, "end": 2435760, "mid": 2435746,
  "uncertainty": 0, "precision": "month", "source": "parsed" }
```

- `start`/`end`：已知边界，`null` 表示未知。
- `mid` + `uncertainty`：完全模糊时的中值点 ± 年数（如 尧 = `-1200±50年`）。
- `precision`：`exact|month|year|decade|century|approx|unknown`。
- 只知卒年时，只填 `end`，`start` 为 `null`。

### 5.3 置信度分桶（UI 三档筛选）

| 桶 | 判定 |
| --- | --- |
| `exact` | 两端均精确到日 |
| `fuzzy` | 至少一端已知，但非精确到日，或 ± 半径 < 100 年 |
| `vague` | 仅中值点且宽度大（如神话人物） |

时间轴滑块产生 `[loJdn, hiJdn]`，`QueryEngine.search({lo,hi,confidence})` 完成过滤。

## 6. 存储与查询

```
CBDB SQLite (584MB)  ─┐
官方网站抓取          ├─► 导入器 ─► 候选 JSON ─► 管理员审核 ─► SQLite(admin)
人工录入             ─┘                                              │
                                                                     ▼
                                        data/*/entities/*.json ◄─ export_static
                                                                     │
                                                     build_index ────┤
                                                                     ▼
                        manifest.json / index/page-NNN.json
                        index/chrono.json / search/bucket-NNN.json
                                                                     │
                                                        GraphStore + QueryEngine
                                                                     │
                                                       前端 (js/core/*.js)
```

- **权威源** = `data/`（Git 可回溯）。SQLite 仅作为审核工作区。
- 大规模优化：`GraphStore` 建立 `outEdges` / `inEdges` / `byPredicate` 三份内存索引，
  查询为 O(1) 定位 + O(k) 遍历。

### 6.1 索引文件布局（v3）

早期实现把全部实体写进单个 `index.json`。5,287 条时它是 1.5 MB，还能接受；
但目标规模 66 万条时约 190 MB，浏览器无法加载。于是索引改为**按页 + 按桶**：

| 文件 | 内容 | 使用时机 |
| --- | --- | --- |
| `manifest.json` | 计数、分页表（含每页首尾姓名）、搜索桶表 `charToFile`、日期计数 | 启动时（约 14 KB） |
| `index/page-NNN.json` | 每页 2000 条摘要行（id/name/type/aliases/summary/lifespan/detail） | 列表视图按页取 |
| `index/chrono.json` | 仅有可解析时间范围的实体，按 JDN 中点升序 | 时间轴筛选 |
| `search/bucket-NNN.json` | 按姓名首字分组的轻量行（id/name/type/aliases） | 搜索时只取命中首字所在桶 |
| `index.json` | **仅为兼容**：`{_truncated, _count, _pageSize, _manifest, rows:[…首页…]}` | 旧代码降级路径 |

> `index.json` 是**对象包装**（`{_truncated, _count, rows}`），不是裸数组。
> 早期版本把 `_truncated` 作为**数组属性**挂上去，而 `JSON.stringify` 会丢弃
> 数组上的自定义属性——于是消费方看到的只是一个 2000 行的裸数组，无法分辨
> 是否被截断。这正是“校验了 2000/5351 却报告 OK”的根因。
> 现在标记随序列化保留，`data_reader` 与 `js/core/data_store.js` 同时接受
> 对象包装与旧版裸数组两种形状。

**搜索桶的划分**：按首字分组后，再按约 4000 行装箱。中文检索以姓氏为首字符
（李 / 張 / 王 …），"查李"只需一个桶，这正是真实访问模式。若按两字前缀建桶，
5.3k 人就要 3,828 个文件、manifest 与数据等大，扩到 66 万时文件数不可维护。

**启动开销**与语料总量解耦：

```
manifest.json ≈ 14 KB + 首页(page-000) ≈ 980 KB + 搜索桶 ≈ 1 MB（仅搜索时）
```

### 6.2 一致性检查

`scripts/check_manifests.js` 校验分页索引的不变量：各页行数之和等于
manifest 计数、id 不重复、每个 id 都有分片文件、`chrono.json` 按 JDN 有序、
搜索桶覆盖全量。它打印的是**排序后 id 列表的 sha256**，而不是页面文件哈希——
后者只要改页大小就会变，前者才代表数据本身。

### 6.3 数据管线的“静默漏检”防护

分页重构暴露出了**一整类不报错的错误**：`index.json` 从全量变成首页后，
所有仍读它的代码都在处理 `2000/5287` 条数据，却全部退出码 0、无异常：

| 位置 | 修复前实际覆盖 | 修复后 |
| --- | --- | --- |
| `validate_data.js` | 2000 / 5287 人 | 5351 / 5351 实体 |
| `check_references.js` | 目标域只有 2000 个 id | 97 处引用，全量目标域 |
| `admin_server.js` 播种 | 2064 / 5351 | 5351 / 5351 |
| `import_cbdb.js` / `import_cpc.js` | 合并进首页后整体写回（**丢数据**） | 写 `entities/` 分片 |
| `import_gov_organizations.js` | 同上 | 写 `entities/` 分片 |
| `test/data.test.js` | 2000 条 | 全量分片 |

现在由三件事共同防止回归：

1. `src/store/data_reader.js` 是**唯一**的读入口，优先读 `manifest.json` +
   `entities/`，`index.json` 只作最后回退。
2. `src/store/entity_writer.js` 是**唯一**的写入口，按 id / name 匹配合并，
   保留人工整理过的 `props` 与 `sources`；并且**内容未变就不写文件**
   （否则 66 万条语料每次导入都要重写整个目录）。
   `setDataRoot()` 允许测试把写入口指向临时目录——这是必要的，因为早先的测试
   用 monkey-patch 改一个在模块加载时就被闭包捕获的常量，结果把测试实体写进了
   真实语料（5287 → 5290），只能靠手工删除才复原。
3. `test/unit/data_integrity.test.js` 断言“覆盖量”本身：校验脚本报告的总数
   必须等于分片总数，`check_references` 的检查数必须大于 0（0 意味着看错了地方），
   并静态扫描 `scripts/` 禁止除 `build_index.js` 之外任何脚本写 `index.json`。

### 6.4 读路径决不得写：详情页的那个空壳

比「静默漏检」和「静默写错」更糟糕的是**静默覆盖**。

分页后只有第一页会被预载，所以 `getEntity(id)` 对 3287/5287 个实体返回 `null`。
旧代码的处理方式是：

```js
let entity = DataStore.getEntity(id);
if (!entity) {
  entity = { id, name: id, props: {}, … };   // 名字就是 id
  DataStore.saveEntity(entity);              // 直接写进 localStorage
}
```

后果：任何指向非首屏实体的链接（分享、搜索历史、外部引用）都会渲染出一个
**名字是 id 的空壳**，并把它持久化——页面上看起来「渲染成功」，实际数据已被取代。
`tools/oneoff/smoke_browser.js` 首次跑详情页时打印的就是 `person:05b9d3c6cbfbcb555cba`
而不是「张庆伟」。

修复分两层：

1. `loadEntity` 不再依赖预载行：分片路径是 id 的纯函数
   （`entities/<encodeURIComponent(id)>.json`），直接从 id 推导并拉取。
2. `_ensureEntity` 找不到时只返回**临时占位对象**（标 `_missing`），不再调
   `saveEntity`，并在页面上明确显示「未找到该实体」。

**规则**：读路径不写。需要占位就返回临时对象，让「找不到」可见，而不是造一个假实体。

同一个修里还踩了一个坑值得记下：`getType()` 对未加载的 id 返回字符串 `'unknown'`
而不是 `null`，所以 `if (!type)` 永远不触发——兜底逻辑写了等于没写。测试
`getType returns the literal unknown` 把这一点钉死。

### 6.5 编造映射：比漏检更危险的「静默写错」

漏检至少会让数字对不上；**映射写错则数据完好、校验全绿，但语义全反**。
CBDB 导入器曾同时存在两张手写的亲属代码表，都是凭印象写的：

| 代码 | CBDB 权威含义 | `src/importers` 旧表 | `scripts` 旧表 |
| --- | --- | --- | --- |
| 75 | 父（F） | `father` ✓ | `子女` ✗ |
| 111 | 母（M） | `mother` ✓ | `子女` ✗ |
| 76 | 岳父（WF） | `kin` | `子女` ✗ |
| 63 | 妻之祖父（WFF） | `teacherOf` ✗ | `亲属` |
| 64 | 伯叔祖（FFB） | `studentOf` ✗ | `亲属` |
| 165 / 166 | 長兄 / 季弟 | `friend` ✗ | `亲属` |
| 300 | **CBDB 无此代码** | `sibling` ✗ | — |

`scripts` 那张表还是按区间猜的（`1–22 → 父母`、`75–160 → 子女`）。
用它导入会把**每个父亲写成儿子**，整棵家谱方向颠倒，而所有校验都会通过。

**处理方式：两张表全部删除，不再手写任何映射。** 改为在导入时从
`KINSHIP_CODES.c_kinrel`（CBDB 自己的结构记号）**推导**谓词：

```
F 父   M 母   S 子   D 女   B 兄弟   Z 姊妹
H 夫   W 妻   C 妾   A 姻親   G 直系祖先   K 同族長輩   P 表親   U 未詳
```

`FFF` = 曾祖（三级父系），`WFF` = 妻之祖父（妻子也是一步，不丢弃），
`B1` = 長兄（保留谓词 `kin`，标注 `modified`）。分层规则：

| 层 | 条件 | 结果 |
| --- | --- | --- |
| 单步 | `c_kinrel` 恰为单个基符号 | `father` / `mother` / `maleChild` / `femaleChild` / `spouse` / `sibling` / `kin` |
| 复合 | 含至少一个基符号 | 谓词 `kin`，`chain` 记录世代路径供界面展示（“父之父”） |
| 哨兵 | `[missing data]`、`Not Applicable` | `resolved: false`，**不计入**路径 |

实测覆盖率：**488 个代码中 486 个解析成功**，仅剩 2 条 CBDB 哨兵行。

实现位于 `src/importers/cbdb_kinship.js`，由三道防线锁定：

1. `assertNoDirectionInversion()` 每次构建映射后自检：父/母符号不得映射到
   子/女谓词，子/女符号不得映射到父/母谓词；违反则导入直接抛错。
2. `test/unit/cbdb_kinship.test.js` **直接连真实 CBDB 库**断言 75→父、111→母、
   63≠teacherOf、code 300 不存在、每个派生谓词都已注册。
3. 同一测试静态扫描 `src/importers/cbdb.js` 与 `scripts/import_cbdb.js`，
   禁止再出现 `KIN_MAP = {` / `KIN_CODE_MAP = {` 或“按中文标签猜谓词”的写法。

**教训**：只要映射是手写的，就一定会漂。数据源本身有权威代码表时，
映射应当是**从数据源推导出来的**，而不是抄进代码里的。

### 6.6 导出路径：删除后重建是错的写法

`scripts/export_static.js` 把 admin 数据库（`local_data/humanmap.sqlite3`）
的内容写回分片。旧实现先从 `data/<type>/entities/` 里 `unlinkSync` 掉所有
`.json`，再从 SQLite 重建。这个写法有两个独立问题：

1. **绕过了唯一写入口。** 它自己拼文件名、自己 `writeFileSync`，意味着
   `entity_writer` 的所有不变量（内容感知写入、props/sources 合并）都不适用。
2. **先删后写。** 中途抛错会让语料处于半删状态；而且**分片里存在、SQLite 里
   不存在的实体会被直接销毁**——admin 数据库的播种时间早于后续导入，这是常态。

现在改为经由 `upsertAll()` 合并，并加了 `test/unit/export_safety.test.js`：
断言导出前已存在的分片不会被删、缺少 `props` 的入参不会抹掉已有 `props`、
空 `props` 不覆盖真实 `props`、同一份数据导出两次写入 0 个文件，以及静态扫描
`export_static.js` 禁止出现 `unlinkSync` / `rmSync`。

#### 6.6.1 `sourcesAudit`：审核库用旧的来源形态，不能污染分片

证据迁移（`sources` 内联对象 → `evidence:` 引用）只改分片，**不改 SQLite**。
admin 数据库是「审核工作区」，播种时间早于迁移，所以它里面的实体仍然带着
迁移前的内联来源对象。于是 `npm run publish` 做了一次「合并」，把 114 条内联
对象又加回了 82 个实体——**迁移成果被一次无意的发布静默撤销**，而且证据引用和
内联副本同时存在，同一个网址被引用了两次。

根因不是 `defaultMerge` 的并集语义本身（它要不要丢来源是对的），而是**来源的
身份键不一致**：分片里是 `"evidence:3e1d…"`（字符串），审核库里是同一条文章的
对象。按 id 去重时两者不相等，对象就被当成新来源追加了。

所以合并时做了两件事：

1. **来源按 URL 识别**。一个网址就是一个来源，不管它以引用还是一内联对象出现。
2. **`{ sourcesAudit: true, evidenceUrl }`**。`export_static.js` 把
   `evidence id → url` 映射传进来，让分片上的引用能“认领”审核库里同网址的
   旧对象；只有认领成功时才丢弃对象，**分片从没见过的来源一律保留**——否则
   `publish` 会把审核界面里新加的出处悄悄丢掉。

> 教训：这是同一个坑的第三次复发（第一次是 `prev` 覆盖 `rec` 的 `claims`，
> 第二次是 `sources` 并集使迁移不可逆）。**任何一个字段只要有“旧形态”和
> “新形态”，合并函数就必须能在两种形态之间认出同一个事实**，否则合并就是在
> 制造重复。改完 `defaultMerge` 后重跑 `npm run publish` 验证应为
> `0 files changed`，并抽查内联对象计数为 0。

顺带暴露另一个静默问题：`defaultMerge` 原先无条件写 `sources: []` 和
`external: {}`，导致一条本来两者都没有的记录在第一次合并后“变了”，于是
**每次导出都会重写每一个分片**。一次无实际改动的 `npm run publish` 报告了
“64 files changed”，实际内容零变化。现在容器字段只在非空时才落地，同一个
命令报告 “0 files changed”。

> 排查记录：这次曾一度误判为“组织和事件的 `props` 被导出清空了”。实际核对
> `id-sha256`（persons `07d54c4ed8c7` / organizations `c2cb812a35e5` /
> events `2b376c079ee6`）前后完全一致，且 SQLite 的 `updated_at` 是 02:34、
> 早于导出运行时间，才确认那些空 `props` 是**既有状态**而非本次损坏。
> 教训：判断“数据丢了”要看内容哈希，不要只看文件 mtime。

### 6.7 分片是权威存储：5269 个实体被索引倒灌

这是本项目最严重的一次数据事故，根因是一句写反的假设。

**起因**：`.gitignore` 曾把 `data/<type>/entities/` 标注为“由索引生成的产物，
用 `npm run shard:data` 重建”。据此写的 `scripts/shard_data.js`（已删除）做两件事：

1. 把 `index.json` 切成「摘要索引 + 每实体分片」；
2. **用摘要覆盖 `index.json`**。

它**不可重入**。第二次运行读到的是摘要，于是把摘要当成实体写进分片：

- 5269 个分片丢掉了 `props` / `relations` / `claims`，只剩 `id`/`name`/`tags`；
- 分片里凭空多出 `detail`——那是 `build_index.js` 生成索引时才算的指针字段。

`detail` 出现在分片里就是**倒灌的确凿指纹**：它在权威存储里没有任何意义。

**为什么没有校验能发现**：`validate_data.js` 当时只查 id 唯一性、必填字段和
日期格式。“实体只剩名字”是合法 JSON，也是合法的结构。

**修复分三步**：

1. `npm run import-cbdb` 重跑。`defaultMerge` 里 `Object.assign({}, rec, prev)`
   让 `prev` 的非空字段胜出，而 `prev.props` 是空 `{}`，所以 `rec.props` 赢得——
   空壳被原地填回，且因为 id 是 `personId(name)`，重跑不会产生重复实体。
2. `tools/oneoff/strip_generated_fields.js` 清掉残留的 `detail`（幂等、带
   `--dry-run`）。它**不是**合并函数的职责：让写入口知道“哪些字段是生成物”
   会把数据模型的知识塞进通用层。
3. `validate_data.js` 加硬失败：分片带 `detail` 即报错，并注明“这是从索引行
   写的，不是实体”。

**同时修掉的三个隐性问题**：

- `MAX_PERSONS = 5000` 硬截断。查询返回 6918 人，被 `slice(0, 5000)` 按数据库
  顺序砍掉 1918 个——**而且每次可能砍掉不同的 1918 个**。这就是重跑导入只能
  覆盖 1209/5205 个空壳的原因。现在是 `--limit=N` 可选，默认全量。
- `import_cbdb.js` 曾用**裸名字**当 id（`王雅`），而 `upsertAll` 不做规范化，
  重跑会写出 `王雅.json` 与 `person:0000f94d….json` 并存——同一个人两个节点。
- `buildDescription` 曾把 `c_notes` 拼进 `简介`。那是 CBDB 的学术注记
  （`"XCB, 362.14b, SS; 471.21a"`，共 232k 行），不是传记。现存入独立的
  `props['史料注记']`。

**教训**：

> **分片是权威存储，索引是它的派生物，方向不能反。** 一个“可从 X 重建”的
> 注释如果写错了方向，就会有人写出按这个方向重建的脚本，而这个脚本看起来
> 完全正常、跑完不报错、校验也发现不了。**判断数据有没有被掏空，不能看
> 结构是否合法，要看内容是否非空。**

> 同时：**校验规则要能区分“损坏”与“本来就薄”。** 431 个实体（367 人 + 34 组织
> + 30 事件）只有名字、别名和标签——它们是手工录入的骨架，不是本次损坏。
> 把它们当致命错误会让 `npm run check` 永久变红，最后一定有人把规则删掉。
> 现在的判定是「空 + 带 `detail` 指纹 = 损坏（致命）」，「空但无指纹 = 数据
> 缺口（警告，条目可见）」。缺口清单见 `docs/使用说明.md` §8。

### 6.8 溯源审计：7489 个实体里哪些说得清出处

数据事故修完不代表数据可信。这一节记录一次全量溯源审计，判据是**每个实体
能否指着一条外部记录说「我来自这里」**。

**审计结果**：7489 个实体中，只有 evidence 节点（111 个）和 things（6 个）
天然带出处；7283 个人物里绝大多数靠 `external.cbdbId` 追溯到 CBDB 行。
审计暴露了四类**无出处且无意义**的节点，全部已处理：

| 问题 | 数量 | 处置 |
|---|---|---|
| 姓名不详的占位人物（`某某（7）`） | 17 | 导入时丢弃，不再生成节点 |
| 无注册谓词的关系边（`其他`/`文学`） | 256 条边 / 109 实体 | 导入时跳过，历史残留已清 |
| 无 props、无 aliases、无人引用的空实体 | 92（84 人 + 8 事件） | 删除 |
| 有 CBDB 记录却填不进去的空壳 | 163 | 修 id 匹配后原地填充 |

**四个根因，都不是“数据脏”，而是代码在撒谎**：

1. **占位名被当成人格。** CBDB 有 253 行叫 `某某`，如实记录了无名者。但两个
   `某某` 在图上变成两个互不相干的人，搜索返回 `某某（7）`，每条亲属边都挂在
   一个无法识别的主体上。**「姓名不详」不是身份**，导入时直接丢弃。
   （注意不能用 `.*某.*` 一刀切：`陈某(陈某子)` 是真实亲属记录，`某昉` 是残缺
   姓名而非占位——判定要窄到「去掉括号注记后只剩某字」。）

2. **未映射的关系被塞进 `其他`。** `import_cbdb.js` 的 `ASSOC_CODE_MAP` 里写了
   `relationType = ASSOC_CODE_MAP[code] || '其他'`，把 CBDB 的 门客/政敌/文学/
   同乡 等类别折叠成一个中文 catch-all（109 条边）。这些边在浏览器端无法反查
   方向、无法渲染标签，`其他` 更是断言了「有某种关系」却说不出是什么。
   现在**映射不到就不建边**（295 条），并在输出里报告条数——
   **一条没有标签的边比一条贴错标签的边好**。

3. **同名编号规则与磁盘上的名字不一致。** CBDB 里 `劉環雋` 有 2 行，导入器据此
   生成 `劉環雋（1）`/`劉環雋（2）`；而磁盘上的空壳叫 `劉環雋`
   （id `person:03bc…`）。合并按 id-then-name 匹配，两者都对不上，于是**追加了
   一个新节点，旧的空壳继续空着**。
   → **重跑导入永远无法收敛**，这正是 163 个空壳修不掉的原因。
   现在导入前先建「磁盘名字 → id」索引，同名首行**复用已有 id**，后续行才加
   序号。修复后 dry-run 的“会变化”从 6901 条降到 338 条。

4. **手工名单从未填充。** 92 个实体是「先把名字列上，回头再补」的产物：
   张辽、廉颇、蔺相如，以及阪泉之战、精卫填海等。它们没有 props、没有
   aliases，也没有任何实体引用它们——**不是“稀疏”，是“空”**。
   搜索「张辽」会得到一个没有任何内容、也看不出是占位页的页面。

**教训**：

> **审计要问“这个节点凭什么存在”，而不是“这个节点格式对不对”。** 上面四类
> 问题都能通过 `validate_data.js` 的结构校验，因为它们都是合法 JSON。
> 只有把「有没有出处」「有没有人引用它」当成独立判据，才会浮出来。

> **删除是最后一步，不是第一步。** 92 个空实体可以直接删，因为无人引用
> （删了也不会悬空）；163 个空壳不能删，因为它们代表真实存在的人——
> 要先修 id 匹配把数据灌进去。**先判断是不是“我们欠了数据”，再决定删还是补。**

> `tools/oneoff/prune_invalid_edges.js` 因此区分三个开关：默认只清非法谓词
> （安全），`--prune-orphans` 删无引用空实体（需引用检查保证不悬空），
> `--prune-placeholders` 删占位人物（会连带删亲属边，默认关闭）。

### 6.9 名字不是主键：从 `sha256(name)` 到 `type:origin-key`

早期 ID 是 `type:sha256(type\0name)[:20]`。它看起来简洁，实际把**显示名当成了身份**，
而这是本项目最多 bug 的单一根源。一个字段同时承担两种职责时，每种操作都会撞上另一种：

| 现象 | 根因 | 曾经的“补丁” |
| --- | --- | --- |
| 9 个 `韓氏` 只剩 1 个 | 同名必然同 ID | 往名字里塞序号：`韓氏（1）`…`韓氏（8）` |
| `韓氏(田通妻)` 这种名字 | 同名者无其它区分手段 | 把亲属关系写进名字 |
| 163 个 cbdbId 各占两个实体 | 导入器按「名+序号」认领分片，而磁盘上是裸名 | 按行占槽位 + 合并脚本 |
| 改个错别字，所有边断掉 | 名字变了 → ID 变了 | 不敢改名（于是错名永久留存） |
| 证据标题修正后引用悬空 | evidence ID 是 `sha256(carrier+date+title)` | 不敢修正标题 |

这些补丁互相矛盾：一个说“名字得带序号才能区分”，另一个说“名字得干净才能匹配”。
矛盾的根源不在名字，在 ID。

**现在的方案：ID 说明“这条记录从哪来”，名字只是字段。**

```jsonc
"id": "person:cbdb-467817"     // CBDB 自己的主键
"id": "person:cpc-448511-32550074"  // 人民网的栏目号-文章号
"id": "person:local-000042"    // 无外部来源时分配的顺序号（永不复用）
"id": "evidence:local-000042"
```

由此：

- **同名多实体是合法的**。两个 CBDB 行都叫 `關羽`（467817、497161）——它们就是两个人，
  各有一个 ID，各有一条到 CBDB 的溯源链。
- **名字可以随时改**。把 `韓氏(田通妻)` 改成 `韓氏`、把关系移到 `spouse` 边，ID 不动，
  所有引用不断。迁移中 541 个名字被原子化，零边丢失。
- **不再需要序号**。1106 个 `（N）` 后缀全部删除，其中 9 個 `韓氏` 靠 `spouse` 边区分。
- **名字不得含关系**。`(許亨妻)` 是 `spouse` 边说的事，`(唐太宗)` 是 `aliases` 说的事，
  两者都不属于 `name`。

**名字不唯一，所以按名字找实体是不安全的。** `graph_source.js` 的 `NameIndex` 因此
记录冲突而不是“先到先得”：一个标签匹配多个实体时返回 `null` 并标为 ambiguous，
而不是默默选中排序最靠前的那个。要把 `中央委员会` 挂在某个具体机构下，得靠约束
（类型、时间、上级）；靠名字猜是错的。

**代价与约束：**

- 无外部来源的实体需要一个**单调、持久、永不复用**的序号分配器
  （`src/store/id_allocator.js`，落在 `data/.id_seq.json`）。顺序号被复用就等于把
  旧引用接到新实体上——这是本类系统最隐蔽的脏数据来源。
- 导入器必须能回答“这条记录的身份从哪来”。`personId(name)` 等名牌构造器已改为
  **抛错**（`removedByDesign`），而不是弃用：留着可调用，新代码就会再次用它造出
  一个看似合理、实则与所有同名者碰撞的 ID。
- `carrier` 这类**裸引用字段**是迁移的盲区。它不在 `relations`、也不在 `sources` 里，
  所以第一版迁移改完了所有边、却没改它，111 个证据节点全部指错。更阴的是：同一轮
  里 local 序号也动了，旧 ID 仍能解析到**相邻的某个实体**——没有任何形状校验看得出来。
  校验因此不能只查“ID 存在”，得查“指向的载体是不是这条记录真正的出处”。

### 6.10 时间轴的“静默空集”：0 人是可解析的

这是本项目最具有教育意义的一个缺陷，因为它**从未报错**，而且每个测试都是绿的。

#### 现象

时间轴的二档筛选、`index/chrono.json`、所有日期查询都在一个**空集**上运行。
7,120 个人物中，`lifespanFromProps()` 能返回非 `null` 的数量是 **0**。

#### 根因（三个 bug 叠在一起）

| # | 缺陷 | 后果 |
| --- | --- | --- |
| 1 | 导入器写 `props['生卒'] = "0年 ~ 不详"`，而读取层只认 `出生年月`/`逝世时间` | **两端从不接上**，任何人都不可能有日期 |
| 2 | 读列名写成 `c_death_year`，BIOG_MAIN 的真实列名是 `c_deathyear` | 每行的卒年都是 `undefined`，71,283 条已知卒年被丢 |
| 3 | 完全没用 `c_birthyear`，拿 `c_index_year`（活动年）当出生年 | 59,851 条真实出生年未入库 |

另一个同源缺陷：CBDB 用 **`0` 表示“未知”**（`c_index_year = 0`，290 行），
导入器把它渲染成字面的 `0年`。公历没有“0 年”，这使这些人排到时间轴**最前面**，
看起来像语料里最早的一个人——比没有日期更糟。

#### 最危险的部分：丢弃“无年份”的人

导入器有一道看似合理的卫生规则：

```js
if (indexYear == null && deathYear == null) continue;   // ← 错
```

CBDB 660,311 人中 **352,779 人没有任何年份**。这道规则把 `關羽`（2 行）、`劉備`、
`張遼` 全部挡在门外，却放进了一位 **1064 年**的 `周瑜` 和一位 **1419 年**的 `趙雲`
（同名现代人）。搜三国人物，得到空结果或一个明代同名者。

**缺日期是源头的空白，不是排除一个人的理由。** 现在年份窗口改为可选（`--years=MIN:MAX`），
无年份者默认全部保留——他们占不到时间轴上是诚实的代价。

#### 修复后的诚实边界

- 486,786 人中 **234,470** 人有可解析区间（出生年 / 卒年 / 或仅活动年 `生卒`）。
- 只有卒年的人**不会**得到虚构出生年：`start` 为 `null`，锚在 `end` 上。
- `生卒`（活动年）作为单端点入 `start`，不冒充“出生年”。
- 朝代分档修正：旧写法 `<= -221 → 先秦` 使下一支 `<= -206 → 秦` **永远不可达**
  （任何 ≤−206 也 ≤−221），秦朝人物全被标成先秦。无年份者标为 `年代不详`，不猜。

#### 教训

**一个从不报错的空集，比一个报错的错值更难发现。** 测试只断言了“导入成功”、
“实体数对”，没断言“时间轴上有东西”。现在 `test/unit/timeline_data.test.js`
直接断言索引里的 `dated > 200000`。

#### 名字里的括注（同类脏数据）

全量导入后出现 49,106 个 `阿魯渾氏(王結妻)` 式的名字。这是同一个错误的不同表现：
把一段关系塞进了显示字段。三重危害——搜不到（没人会输入括号）、
同名但不同婚配会变成两个身份、关系本身对任何查询都不可见。

`split_relational_names.js` 把它们拆开：名字原子化，括注转别名，
能唯一解析到对方时**额外建一条亲属边**。41,174 条成功建边，451 条因对端同名歧义
而放弃建边，5,534 条因对端不存在只保留别名——**宁缺不猜**。

## 7. 前端

前端没有构建步骤，`index.html` 按依赖顺序直接加载 `<script>`。业务逻辑放在
`js/core/*.js`——**无 Vue、无 DOM 的纯函数模块**，因此可以在 Node 里用 `vm`
沙箱直接单测；`js/services.js` 把它们装配成服务；`js/views/*.js` 是组件；
`js/app.js` 只剩路由与挂载。

**分层与加载顺序**（`index.html` 按此顺序加载）：

```
js/core/*.js     纯逻辑，无 Vue/DOM，可在 Node 单测
      ↓
js/services.js   装配：DataStore / SearchEngine / relations / RelationManager / renderGraph…
      ↓
js/views/*.js    Vue 组件（一个文件一个职责）
      ↓
js/app.js        路由 + 根实例 + mount('#app')，不含业务逻辑
```

**为什么这层拆分是必要的**：`app.js` 曾经是 1712 行的单体，同时装着服务装配、
7 个 Vue 组件和路由。改动任何一个组件都需要在 1700 行里导航，而服务层的
改动又无法从组件中独立验证。拆分后各文件：

| 文件 | 行数 | 职责 |
| --- | --- | --- |
| `js/services.js` | ~270 | 环境探测、`EntitySchema`、`RelationRegistry`（谓词兼容视图）、各服务实例、`renderGraph` 垫片 |
| `js/views/search_bar.js` | ~160 | 搜索栏与高级筛选 |
| `js/views/home.js` | ~80 | 首页统计与入口 |
| `js/views/entity_detail.js` | ~385 | 实体详情（三类共用一个工厂函数） |
| `js/views/editor_panel.js` | ~285 | 编辑器抽屉（属性/关系/源码双向） |
| `js/views/relation_panel.js` | ~260 | 关系词管理（内置只读、自定义增删改） |
| `js/views/all_objects.js` | ~180 | 全量浏览 + 时间轴筛选 |
| `js/views/search_results.js` | ~65 | 搜索结果列表 |
| `js/app.js` | ~100 | 路由 + 根实例 + 挂载 |

**拆分的安全网**：`app_wiring.test.js` 按 `index.html` 的顺序加载全部文件，
并断言 `DataStore / SearchEngine / SourceParser / RelationManager /
RelationRegistry / RelationDirection / renderGraph / EntitySchema /
isLocalMode / listRelationWords` 全部可见——这正是模块拆分最容易弄坏的
东西（符号被搬走却没重新引入）。

| 模块 | 职责 | 测试 |
| --- | --- | --- |
| `js/core/predicates.js` | 谓词表、同义词归一、`/inverse`、`/negate`、性别约束 | `predicates_browser.test.js` |
| `js/core/timeline.js` | JDN 换算与三档置信度（与 `src/time/julian.js` 对齐） | `timeline_browser.test.js` |
| `js/core/data_store.js` | manifest/分页/搜索桶加载、详情懒加载、localStorage 覆盖 | `index_paging.test.js` |
| `js/core/relations.js` | 关系分组、反向写入、性别检索、引用清理 | `data_layer_browser.test.js` |
| `js/core/search.js` | 首字桶收窄 + 模糊匹配（Fuse 缺失退化为子串） | `index_paging.test.js` |
| `js/core/source_parser.js` | 源码 ⇄ 实体（关系词由谓词表判定） | `data_layer_browser.test.js` |
| `js/core/direction.js` | 箭头方向（由谓词对称性推导） | `app_wiring.test.js` |
| `js/core/graph_render.js` | D3 力导向渲染 | — |
| `js/services.js` | 服务装配层（无组件） | `app_wiring.test.js` |
| `js/views/*.js` | Vue 组件 | `app_wiring.test.js`（全局可达性） |
| `js/app.js` | 路由 + 根实例 + 挂载 | `app_wiring.test.js` |

**加载顺序**（`index.html`，不可打乱）：predicates → timeline → data_store →
relations → search → source_parser → direction → graph_render → app。

**前端词表不重复定义**：`js/core/predicates.js` 的 `BUILTIN` 由 Node 侧
`src/predicates/registry.js` 生成，并由 `predicates_browser.test.js` 逐条比对
钉住。此前前后端各维护一份词表，已经发生过标签错位（employer/employee 等），
该测试是这一问题的根治措施。

前端的筛选参数与 `QueryEngine.search()` 一一对应，便于将来把查询下沉到服务端。

## 9. 大规模与扩展性

目标规模：CBDB 66 万人物、56 万亲属边、59 万任职边。当前实装 **486,786 人物**。

- **分批导入**：按朝代/年份分片导入（`--years=MIN:MAX`），每批产出独立 import 批次。
  默认不设年份窗口——见 §6.10，旧窗口把 關羽/劉備/張遼 这类无年份的古代人物挡在门外。
- **索引分页**：见 §6.1。启动成本与语料总量无关；列表取一页、搜索取一桶、
  时间轴取 `chrono.json`。
- **惰性详情**：`index` 只存摘要，正文在 `entities/*.json`，点开才取。
- **O(1) 查找**：`src/store/graph_source.js` 用 `NameIndex` 建名字/别名索引，
  建边不再对节点做线性扫描（此前 6 万节点时即有明显停顿）。
- **字段裁剪**：摘要行只保留 id/name/type/aliases/summary/lifespan/detail。
- **边界**：浏览器内存能装下的实体数仍有限（约数十万摘要行）。若需全量浏览，
  下一步是把 `chrono.json` 与分页索引换成按需查询的只读 API；`GraphSource`
  接口（`src/store/`）已抽象，替换实现不影响前端与测试。

### 9.1 本地全量 vs 公开发布

语料从 7k 实体涨到 48.7 万后，一个原本不存在的问题出现了：**权威语料不适合进 Git**。

| | `data/` | `site/` |
| --- | --- | --- |
| 内容 | 全量 486,786 人 | 现代 3,604 人 + 全部非人物实体 |
| 体积 | 约 610 MB | 约 4.5 MB |
| 用途 | 本地后台、CLI、导入器 | GitHub Pages 静态展示 |
| 进 Git | ❌ | ✅ |
| 生成 | `build_index.js` | `build_site.js`（内部调 `build_index.js --publish`） |

分流靠**输出目录**，绝不靠删数据：`data/` 里的任何东西都不会被发布过滤器移除，
它只决定哪些行被复制进发布树。

**发布规则**（`scripts/build_index.js` `isPublishable()`）：

- 非人物实体（组织/事件/证据/非人实体）**全部发布**——它们只因现代官方文档提及而存在。
- 人物需“已知的最晚一年”≥1900（`lifespan.end ?? start ?? mid`）。用最晚一年而非出生年，
  使 1880 生 / 1950 卒 的二十世纪人物能被看见。
- **无任何年份的人物不发布**：48 万 CBDB 导入中有 25 万人无年份，无法证明其为现代。
  被排除不是对人的评价，而是“无法定位到时间”的诚实结果。
- 发布 manifest 明写 `publish.filtered: true` 与 `personsFromYear`，否则一个 3.6k 行的
  网站会看起来像全量语料丢了 99% 数据。
