## 1. 现状与约束

| 项目 | 数值 |

### 1.2 当前架构的假设（已不成立）

项目最初是静态展示页，隐含三个假设：

1. **数据能一次装进内存** —— 29 MB 的 chrono.json 尚可，接入 180 万条边后不可行
2. **查询可预计算** —— 时间轴、首字桶可以；跨实体组合查询（「曹操的儿子们的任职」）不可
3. **写入与读取可分离** —— 现在要支持录入，写路径必须能事务化

## 2. 存储引擎选型

### 2.1 结论：SQLite（FTS5）

| 候选 | 优点 | 缺点 | 判断 |
| --- | --- | --- | --- |
| **静态 JSON（现状）** | 零运维、可直接部署 | 无法组合查询；29 MB 单文件 | 保留为**发布快照**，不再承担查询 |
| **SQLite + FTS5** | 单文件、零运维、已有 `sql.js` 依赖；FTS5 解决 208k 别名检索；递归 CTE 做亲属链 | 写并发有限 | ✅ **采用** |
| PostgreSQL | 并发强、生态好 | 需服务进程、运维成本；百万级数据用不上 | 若将来公网多人写入再考虑 |
| Neo4j / 图库 | 深图遍历快 | 本项目 90% 查询是「属性筛选 + 一跳邻接」；运维重、录入生态弱 | ❌ 不采用 |

### 2.2 关键理由：SQLite 而不是 Postgres

- 已有 `sql.js` 依赖，`local_data/humanmap.sqlite3` 在用
- **单文件可备份** —— 与 `raw/` 一起构成完整快照
- WAL 模式足以支撑单机/局域网的录入
- 数据量级（百万实体 + 180 万边）远未到 SQLite 的瓶颈

**不要为 1 亿条做设计。** 本项目合理上限是百万级；为超大规模设计会拖垮当前实现。

### 2.3 SQLite 的角色：索引，不是权威

```
raw/（只追加，唯一需备份）
   → entities/（派生，可重建）
      → SQLite / index/（派生，可重建）
```

**任何时候都不能把 SQLite 当唯一真相。** 它丢失可重建，`raw/` 丢失不可恢复。

## 3. 后端形态

### 3.1 分阶段

| 阶段 | 形态 | 说明 |
| --- | --- | --- |
| **S1** | 只读静态 | 保持现状，`site/` 部署 |
| **S2** | 只读 HTTP API | Node + `node:sqlite`（Node 22+ 内置）或 `better-sqlite3` |
| **S3** | 读写 API | 录入、编辑、事务 |
| **S4** | 多用户 | 认证、权限（若需要） |

**S1 → S2 是唯一必须的跳跃**，其余按需。

### 3.2 API 草案

```
GET /api/entities?type=person&page=0&size=200
GET /api/entities/:id
GET /api/search?q=曹操
GET /api/timeline?from=JDN&to=JDN&type=person
GET /api/entities/:id/edges?direction=out
```

**保持与现有 `data/*/index/page-NNN.json` 的响应形状兼容**，前端改动才能可控。

### 3.3 依赖选择

已确认：本项目运行在 **Node v24.19.0**，`node:sqlite` **内置可用**，无需新增任何依赖。

```js
const { DatabaseSync } = require('node:sqlite');
```

`sql.js` 保留用于「读取 CBDB 的 584 MB SQLite 文件」——它是 WASM，无需编译；
而 `node:sqlite` 读大文件也很快，将来可统一。

## 4. 前端重建规划

### 4.1 现状问题

| 问题 | 表现 |
| --- | --- |
| 无构建步骤 | `index.html` 手写 20 个 `<script>`，依赖顺序靠人 |
| 全局变量通信 | `js/core/*.js` 挂在 `window` 上 |
| 视图硬编码 | 每个视图自己拼 HTML 字符串 |
| CSS 单文件 1,078 行 | 无分层、无变量、选择器耦合 |
| 取数假设全量 | 视图假设数据已全部在内存 |

### 4.2 重建原则

**不引入重度框架。** Vue 3 已在用（CDN），保留。改动集中在：

1. **取数层抽象**：`js/core/data_store.js` 改为接口，静态实现 / API 实现可切换
2. **CSS 分层**：拆为 tokens / base / components / views
3. **视图拆分**：2,583 行的 `js/views/` 按职责拆

### 4.3 CSS 重构方案

现状 1,078 行单文件的问题：无设计令牌、选择器与 DOM 结构强耦合、无法复用。

**拆为 4 层**：

```
css/
├── tokens.css       # 颜色、字号、间距、圆角、阴影变量
├── base.css         # reset、排版、链接
├── components/      # 按钮、标签、卡片、表格、分页
│   ├── button.css
│   ├── tag.css
│   ├── card.css
│   └── table.css
└── views/           # 每个视图的布局
    ├── home.css
    ├── entity.css
    └── graph.css
```

**约束**：
- 组件层**不得**出现视图专属类名
- 视图层只能用 tokens 和组件，不得重新定义颜色字面值
- 保持无构建步骤（纯 CSS，`index.html` 顺序加载）

**验收**：重构前后截图对比，无视觉回归。

## 5. 构建管线调整

### 5.1 新的 pipeline

```
raw/*.jsonl
   ↓ tools/raw/ingest_*.js        （一次性，搬运）
raw/（只追加）
   ↓ src/transformers/*.js        （可版本化，可重跑）
data/*/entities/*.json           （第 1 层，派生）
   ↓ scripts/build_db.js          （新）
humanmap.sqlite3                 （第 2 层，查询）
   ↓ scripts/build_index.js       （现有）
data/*/index/ + search/          （第 2 层，静态兼容）
   ↓ scripts/build_site.js        （现有）
site/                            （发布快照）
```

### 5.2 幂等性要求

每个环节必须可重复执行且结果一致：

- `ingest`：`rawId` 由 `source + sourceKey` 决定，重复执行不产生重复记录
- `transform`：同版本转换器 + 同 raw → 逐字节相同输出
- `build_db` / `build_index` / `build_site`：全量重建，不增量

**验收方式**：连续跑两次，`git diff` 为空。
