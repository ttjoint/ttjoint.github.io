## 系统分层：后端 / 前端

**这是全局的分工定义，下面各阶段的归属都以此为准。**

分界线是**「各实体及谓词边组成的网」**（下面简称「概念网」）。
网的左侧只能写，右侧只能读。

### 后端：从原始字节到带出处的概念网

四个子系统，全部属于「施工」而非「展示」：

| 子系统 | 职责 | 代码 | 状态 |
|---|---|---|---|
| **raw 存储** | 原始字节录入、维护、备份、哈希链 | `raw_store.js` / `raw_schema.js` / `tools/raw/` | ✅ P0 |
| **抽取引擎** | raw → 概念网，模块化 transformer | `src/transformers/` | ✅ 通道已通（P2），覆盖率低 |
| **概念网存储** | 实体 + 带 `provenance` 的边 + `commitId` | `data/*/entities/`、`commits.js` | ✅ 形状已定 |
| **操作接口** | 读 raw / 写概念网，均可追溯 | 部分 | ⬜ 未成形 |

**操作接口两组：**

- **读 raw**：给 bot 和真人看原始记录。只读，不写。
- **写概念网**：接收「**带证据引用的增删改查请求**」，按批次执行。

抽取引擎的产出也是这种「请求」而不是直接写库——这样每一批处置都是
可审查、可批准、可回滚的中间产物。

**所有操作带时间戳与记录**（`commits.js` 已有骨架，只增不改）。

### 前端：只读的抽取子集

**前端不修改数据。** 它建立的是「带缓存的抽取子集」——等价于数据库视图。

用途举例：家族图谱可视化、人物一生经历、组织成员地区/年龄分布、交叉检索。

**这些可以晚做**。P3 只需要把框架搭起来：

- 可模块化、可组装的视图单元
- 能接受「构造好的查询描述」（外部传入）
- 不自己承担复杂 SQL

### 三个关键取舍

#### 1. 概念网存储：JSON 权威 + SQLite 索引（**不换图数据库**）

**理由**：本数据的形状不支持图数据库的优势。

- 图数据库的杀手锥是变深、变宽、无模式遍历和稠密图。
- 本图是**稀疏且高度结构化**的：51,814 条边 / 486,786 个点 = 每点 0.1 条边；
  57 个谓词里 46 个零边；家谱查询默认深度 5，实际超 3 代很少。
- 真正的重查询是**递归邻域（限深 5）**，已实测可行（见 §「家谱图递归查询实测」）。

**换图库会失去的**：零依赖部署（`node:sqlite` 内置）、FTS5、游标分页、
事务、`UPDATE` 定点修订。而 **bot 分批修订只能靠 `UPDATE`**。

**退出条件（写在这里以免将来重讫）**：若「任意深度家谱路径搜索」成为主线，
递归 CTE 会顶不住。那时的正确做法不是换数据库，而是加一张**预计算路径表**
（`ancestor_pairs(ancestor, descendant, depth)`）——一次递归预计算换 O(1) 查询，
不影响其他一切。

#### 2. 复杂查询：SQLite + 查询描述编译器（**不改技术路径**）

各应用的 SQL 难度实测：

| 应用 | 写法 | 难度 |
|---|---|---|
| 家谱图（限深 5） | 递归 CTE + `INDEXED BY` | 已实测可行 |
| 人物一生经历 | 单表 `ORDER BY` 时间轴 | 简单 |
| 成员地区分布 | `GROUP BY` + 索引 | 简单 |
| 成员年龄分布 | `GROUP BY` 分桶 | 简单 |
| **交叉检索（多条件组合）** | 动态拼 SQL | **需编译器** |

只有最后一项需要「SQL 撰写器」，而它也是最常见的。正确形态**不是拼字符串**，
而是**受限的查询描述语言**：

```js
{ type: 'person', where: [{ field: 'era', op: 'eq', value: '宋' }], orderBy, cursor }
```

后端编译成参数化 SQL。好处：SQL 注入不可能（全部走参数）、
前端不需懂 SQL、新查询类型 = 注册一个描述模板而不改前端。

**若将来不够用**，退路是「静态部分预计算成物化视图表，动态部分留 SQL」，
不需要换数据库。

#### 3. 静态抽取子集：三层 + 依赖指纹

不能实时算（484 万实体全量重算不现实），也不能只靠 HTTP 缓存
（它管不了「数据变了但文件没变」）。按变化节奏分三层：

| 层 | 内容 | 更新时机 |
|---|---|---|
| **页面静态文件** | 实体详情页、列表页 | 数据变更后延迟合并（debounce，如 6 小时） |
| **物化查询结果** | 家谱图、统计分布 | 依赖数据变更后重算（记依赖指纹） |
| **实时查询** | 用户自由检索 | 每次算 |

关键是**「依赖指纹」**：每个物化结果记录它读了哪些实体的哪些 `contentHash`。
数据变更时只重算指纹变了的那些——比定时全量重算省得多，比实时稳定。

### 数据填充暂缓的理由（重要）

**平台未完工前不填数据。** 具体理由：

1. **现在填的每一批都按当前规则填，而规则还会变。** 例：`maleChild`/`femaleChild`
   已被认定「本质上是 `father/反 + 客体性别`」，但已存 7,042 条边，改 key
   成本高于收益。若现在按它补 35 万条边，将来裁定要改就是 35 万条要重写。

2. **提取 bot 本身还没设计。** CBDB 规范化与本系统规范化之间的系统性差异
   （年份→儒略日、年号→年份、朝代→时段）需要一套**独立的、可测试、可回滚、
   能分批跑**的 process。

3. **反面教材（本轮亲历）**：`fix_dynasty_tags.js` → `normalize_dynasty_to_traditional.js`
   → 又发现 3,788 个标签与 `c_dy` 不符。三次手术，每次全量扫 486k 文件，
   每次都在上一刀切口上再切一刀。这就是「一上来就填数据」的代价。

4. **平台未完工时填数据会让缺陷不可验证。** P2 的对照脚本能工作，是因为
   现有数据都出自同一个有缺陷的导入器，差异能归因。补完 35 万条新边后再
   发现 transformer 有 bug，就分不清哪些是 bug、哪些是当时就补错的数据。

**P2/P3 的验收标准是「框架成立」，不是「数据完整」。**

### P0 实施中发现的两个真实缺陷

**① `rawId` 用 `-` 分隔无法解析（已修）**

初版 `rawId = raw:<source>-<group>-<key>`。写入成功，但 `get()` 全返回 null：
`raw:web-gov-5746205` 被切成 source=`web`、group=`gov`，而实际 group 是
`gov-5746205`。记录就在磁盘上，却报「找不到」——比报错更糟的失败模式。

修复：改为 `/` 分隔（`makeRawId`/`parseRawId` 成对导出，身份格式不得重复实现），
并补三条回归测试（含「端到端在含连字符的 group 里真的取回文档」）。
已入库的 247 万条按新格式重建。

**② 哈希链全量验证比预估慢 5 倍（已按用途拆档）**

此前实测「247 万条 12.8 s」只算了哈希函数耗时，没算 290 MB 解压 + 247 万次
JSON 解析。真实全量验证 62 s。结论不是「哈希链不值得」，而是**两种校验粒度要分开**：
heads 模式（0.23 s，抓「树没了/文件坏了」）进每次 check，
完整模式（62 s，抓「有人改了历史」）发布前跑。

### P3-3/P3-4 实测发现的四个 bug（都已修并写成回归测试）

**1. 共享排序键的行会静默丢失**

`ORDER BY name` 时两个「王氏」共享排序键。游标只存名字，`name > '王氏'`
把两个人一起跳过——第二个人永远不会出现在任何一页。
根因：tiebreak `id` 加进了 `ORDER BY` 却没加进游标。
**规范：游标描述的排序必须就是行实际到来的排序。**

**2. DESC 排序永远少最后一行**

NULL 在 DESC 里排最后，`valid_from < ?` 对 NULL 行恒为假，所以所有无日期
人物在倒序翻页时被永久排除。语料库里有 **252,316** 个无日期人物，
表现为「最后一页有时少一条」。正确条件：`(col < ? OR col IS NULL)`。

**3. 加索引拖慢了另一个查询（又一次）**

新增 `idx_entities_undated` 后，优化器仍选 `idx_entities_time` 做等值查找
再排序：**196ms**；强制走部分索引：**0ms**。
这是优化器估计错误，不是索引错。解法：`dated:false` 条件带 `preferIndex`，
编译器发出 `INDEXED BY`。这是**编译器唯一硬绑索引的地方**，
理由是该选择可测地错误且 SQL 无法表达「用部分索引」；
`db_index.test.js` 断言该索引存在，schema 改动会立即失败而不是运行时。

**4. 物化视图报错原因永远是 'fresh'**

`materialize()` 重建后重新查新鲜度，于是 `reason` 报告的是重建后的状态，
而不是「为什么要重建」——这个字段就失去了作用。改为重建前先捕获原因。

### 一个否定的结论：`hasPredicate` 无法再优化

「哪些实体有父亲边」实测 10–13ms。试过的三种写法：

| 写法 | 耗时 | 结果 |
|---|---|---|
| 两个 `EXISTS` 用 `OR` 连接 | 145ms | 两个都跑，不短路 |
| `EXISTS` 套 `UNION ALL` | **10–13ms** | ✓ 采用 |
| `id IN (SELECT ... UNION ...)` | 36ms | `UNION` 去重要建临时表 |
| `id IN (SELECT ... UNION ALL ...)` | 22–26ms | `IN` 子查询仍去重 |

**固有成本**：问题本身就是「486,781 个实体里哪些有这种边」，
每个实体至少要看一次。再优化只能改查询语义（比如不从实体出发而从边出发），
那是调用方的选择，不是编译器的职责。

### 本轮实测抓到的两个真 bug

**1. 递归 CTE 参数顺序颠倒 → 谓词过滤完全失效**

SQL 占位符顺序是 `id, depth, predicate`，参数传的是 `[id, predicate, depth]`。
**无谓词时完全无害，一加谓词就变成 `w.depth < 'father'`**（SQLite 把字符串
转成 0），递归立刻停止，返回只有种子自己。
表现为「家谱页选择谓词后只剩一个人」，很容易被读成「此人无此类亲属」。

**2. 深度上限只在 route 层 → 单条 URL 可让服务器跑 64 秒**

`familyTree(id, dir, 999)` 实测跑了 **64 秒** 才返回。clamp 写在路由里，
而函数本身没有防御——测试直调、脚本、未来新端点都是绕过路径。
**规范：限制必须写在使用点上，不能写在某一个调用方上。**

### P3 实测基线与两个真问题

`tools/oneoff/bench_db.js`，325MB 库，每条查询跑 20 次取中位数：

```
  0.06 ms  游标分页 50 条
  0.01 ms  counts 查表
  0.02 ms  某人的孩子
  0.01 ms  某人的父亲（反向）
  0.01 ms  谁的孩子是 X
  0.14 ms  某谓词全部边
  0.07 ms  上溯家谱限深 5
  0.05 ms  下溯家谱限深 5
  0.09 ms  FTS 前缀搜索
  0.06 ms  时间轴窗口（30 年）
  0.02 ms  一实体出处 join 证据
  0.01 ms  别名查表
```

**问题一：下溯家谱比上溯慢 40 倍（13.45ms vs 0.35ms）**

不加 `INDEXED BY` 时，SQLite 选 `idx_edges_predicate`——因为 `predicate='father'`
是等值条件，它把**全部** `father` 边扫一遍再 join。加提示后 **0.05ms**（270 倍）。
边越多差距越大，而 P4 正是要把边从 5 万补到 41 万。

**问题二：加索引反而拖慢另一个查询（自造回归）**

为修时间轴（81ms）加了 `idx_entities_folder_time`，结果优化器改用它来跑
游标分页，变成全表按名字排序：**0.07ms → 575ms**。
正确做法是加 `(folder, name)` 复合索引，让范围与 `ORDER BY` 都从索引出。

**教训**：加索引不是免费的，每加一个都要重跑基准。两条都写成了回归测试
（断言查询计划里不出现 `TEMP B-TREE`）。

### P5-5c 实际结论

**§8.5 的「删 `inverse`」被推翻。** 实测发现 `inverse` 不只是别名索引：
`Graph.edgesByPredicate()` 与 `Query._collectRows()` 都靠它做跨 key 召回。
删了它，查「父亲」会静默漏掉 `childOfFather` 方向的断言——正确性问题。

而 §8.5 预期的收益（谓词数减半）在本项目不成立：

```
有边数据的谓词   11   （全是亲缘，P5-5a/b 修的那批）
零边的谓词      46   （组织/事件/物关系尚未导入，是能力声明）
```

在零边的谓词上做镜像合并只减计数，不减真实复杂度，却弄坏那 11 个的查询。

**真正删掉的是 `subjectGender` / `genderFamily`**：

```
A --maleChild--> B   读作「A 的儿子是 B」
                    主体 A 是父，客体 B 才是孩子
```

原字段声称约束**主体**，而约束应落在**客体**。原注释写的是
“constraint on the SUBJECT of this edge (the child)”——把主体当成了孩子。

这个错误**从未被发现**，因为 `checkAssertion()` 只看 domain/range，
完全不看性别字段，所以它从第一天起就是死代码。

修正：`subjectGender` → `objectGender`，`matchesGender()` 同步。
与 P5-5b 删 `elderBrother` 是同一个毛病：主体视角与 label 视角混用。

**中文修饰符**：`splitModifiers()` 现在同时接受中文与英文：

```
父亲/反  父亲/非  兄弟/男  兄弟/女
```

内部表示仍只有一套英文名，因为存量数据里已存了 `father/negate` 这类 key。

**`symmetric` 改为显式声明**，不再从 `inverse === key` 推导。

**测试**：266/266 通过。新增 4 条（六个原语、方向语义、中文修饰符、客体性别）。

### P5-5a 实际结论（与初判不同，必须保留）

**做了什么**：34,698 条非法谓词边收敛为 2 条（矛盾数据，已文档化 WARN）。
最终分布：`spouse` 22,562 / `mother` 15,428 / `maleChild` 6,542 / `father` 5,345 /
`kin` 1,376 / `femaleChild` 500 / `youngerSibling` 32 / `sibling` 26 / `childOfMother` 1。

**两次误判（记录以免重犯）**：

1. **误判「这些关系在 CBDB 里不存在」**。抽样 3,000 个 `wife` 边主体回查
   `KIN_DATA`，4,068 行有记录（均 1.36 条）——她们是真实 CBDB 人物。

2. **误判「方向反了」**。同方向记录里 15,119 条是 code 134（`H`）。单看码表
   `H`=丈夫会得出方向反了，但查性别后否定：

   ```
   45940 某氏(安燾妻) female=1  --H-->  3 安燾 female=0
   ```

   CBDB 是从「某氏(安燾妻)」这个**从属人物**出发记的，`H` 只是「其配偶是 X」的占位。
   实体名已明确是妻，所以 `split_relational_names.js` 写出的方向是**对的**。

**关键语义**：注册表里 `father` 的 label 是「父亲」，即 `A --father--> B`
读作「**A 的父亲是 B**」（从属视角），不是语言学上的「A 是 B 的父」。
这决定了 `D`（女兒）在从属人物上应映射为 `femaleChild` 而非 `daughter`。

**为什么不盲删**：8,069 条 raw 双向都查不到的边，其中 8,064 条（99.9%）的
`aliases` 含亲属括注（`項某妻`、`邱峻繼母`）——它们是 `split_relational_names.js`
从名字里抽出来的，有出处，只是不在 `KIN_DATA`。按 `FROM_QUALIFIER` 对齐 key 而非删除。

**脚本自身两个 bug（已修）**：
- `delete rel[badKey]` 在 `target === badKey` 时（`daughter→daughter{kind:step}`）
  会先写入再删自己，静默丢数据。
- 统一拼 `` `person:cbdb-${oid}` `` 会把 `person:local-000307` 变成
  `person:cbdb-person:local-000307`（已损坏 1 条，已修复）。改为保留原 id。

**遗留 2 条 WARN**：`person:cbdb-160224 崔氏`、`person:cbdb-161275 劉氏`。
CBDB 互记了一对 `M^`(繼母) 与 `D^`(繼女)，两者矛盾（不能既是母又是女），
**不猜、不删、保留原状**。详见脚注 `CONTRADICTORY` 注释。

### P5-5b 实际结论

**做了什么**：22,319 条边拆到 6 个原语上。边总数不变（51,814）。

```
husband 21,897   mother 15,428   maleChild 6,542   father 5,345
kin      1,376   femaleChild 500   wife 364   spouse 301
brother     51   sister 7
```

**新增谓词**：`husband` / `wife` / `brother` / `sister`。
**删除谓词**：`elderBrother` / `youngerSibling`。

**为什么删 `elderBrother`/`youngerSibling`**：

// 错：role 记录的是「主体扮演的角色」，但谓词读法看客体

## 性能红线（写代码时必须遵守）

基于 §9 实测，以下规则**违反即性能事故**：

1. **禁止在查询路径写 `LIKE '%..%'`** —— 200 万行 247ms，线性增长。文本搜索一律走 FTS5
2. **`edges` 必须有三个索引**：`(subject,predicate)`、`(object,predicate)`、**(predicate,subject)**
3. **递归 CTE 必须限深度** —— 「某人的所有后代」不加限制会指数爆炸
4. **`COUNT(*)` 可放心用** —— 200 万行仅 2ms

基准记录（500k 实体 + 180 万边）：
跳邻接查询 0.005 ms、谓词 count 19 ms、建库 11 s。
一跳/二跳是本项目 90% 的查询形态，**均为微秒级**。

追加（千万级实测，见 `分层架构重构方案.md` §9.7–9.8）：

5. **列表查询一律用游标分页** —— `OFFSET 9000000` 要 713 ms，且已录入 API
   一旦发布为 `?page=N` 就要改两次
6. **只写标准 SQL** —— 不用 SQLite 特有语法，保留将来换库的可能
7. **`counts` 表从第一天就建** —— 单类型 `COUNT(*)` 千万级 88 ms，百万级用不上但成本为零

> 这三项在百万级**现在做成本几乎为零**，以后补则需改 API 形状与前端。
> 千万级本身**不需要换数据库**（一跳 0.14 ms），但上述三项必须改。

### 递归查询红线（家谱图必读）

实测：同一个家谱查询，写法不同差 **2.5 万倍**（1 ms vs 26,546 ms）。

8. **递归必须写 `FROM edges e INDEXED BY i1`**
   只要写了 `predicate IN (...)` 而不加提示，优化器会选 `(predicate,subject)` 索引，
   变成「扫全部同类边」——7,582 ms vs 2.45 ms。
   `OR` 写法一样错（8,147 ms）。**只有 `INDEXED BY` 能拦住它。**

9. **上向与下向递归必须拆成两个 CTE**
   塞进一个 `UNION` 递归会路径爆炸：`UNION` 按 `(id,dep)` 去重，
   同一节点在不同深度被视为不同行。实测 26,546 ms / 返回 241,383 假节点
   （实际只有 64 人）。拆开后 1.05 ms / 64 节点。

10. **家谱视图强制 `depth` 上限，默认 5**
    扇出 10 时，下 5 代 11 万人（150 ms）、下 6 代 111 万人（1.7 s）。
    真实家谱确实会出现高扇出，不限深就会把浏览器拖死。

可直接用的完整查询见 `分层架构重构方案.md` §9.8。
正常家谱（200 万人 / 880 万边）实测 **0.85 ms**，不需要额外优化。
