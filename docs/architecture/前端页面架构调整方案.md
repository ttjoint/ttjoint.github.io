### 1.3 未解决：编辑功能与架构原则冲突

**现状**：

| 组件 | 行数 | 状态 |
| --- | --- | --- |
| `editor_panel.js` | 283 | 弹窗抽屉，编辑实体属性/关系/源码 |
| `relation_panel.js` | 258 | 弹窗抽屉，增删改关系类型 |

编辑写入 `localStorage`（`data_store.js:381 saveEntity`），不是数据库：

```js
DataStore.prototype.saveEntity = function (entity) {
  if (!this.isLocalMode || !entity || !FOLDERS[entity.type]) return false;
  this[folder][entity.id] = entity;
  local[entity.id] = entity;
  this._write(STORAGE_KEYS[entity.type], local);   // ← 只写浏览器本地
};
```

**这与项目原则冲突**：

1. **绕过 commit 机制**。`节点类型与谓词.md` §6 要求每条断言带 `commitId`，
   指向提交表；前端直接改实体等于凭空产生无出处的数据。
2. **绕过 provenance**。`provenance` 必填非空是硬约束，前端编辑不会产生它。
3. **编辑结果不共享**。只存在当前浏览器，刷新别人的视角看不到。
4. **UI 形态错位**。关系类型管理是低频、结构性操作，塞进弹窗抽屉不合适。

## 2. 目标架构

### 2.1 三层职责

```
raw/（只追加，唯一需备份）
   ↓  tools/raw/ingest_*       搬运，不解释
raw/（第 0 层）
   ↓  src/transformers/*.js     解释，可重跑
data/*/entities/（第 1 层）      派生，可重建
   ↓  scripts/build_db.js
humanmap.sqlite3（第 2 层）      查询用，可重建
   ↓  scripts/build_index.js → build_site.js
site/（发布快照）
```

**写路径只在第 0 层**。任何对意义网的修改都必须：
1. 落到 `raw/`（附文献依据）
2. 由 transformer 重跑生成第 1 层
3. 重新 build 第 2 层

前端**不参与**这条链路。

### 2.2 前端只读原则

| 允许 | 禁止 |
| --- | --- |
| 展示、检索、跳转、图谱 | 修改实体属性 |
| 查看出处、复制引用 | 增删关系 |
| 查看 commit 历史 | 改关系类型定义 |

理由不是「权限」，是**一致性**：前端改的数据没有 `provenance`、没有 `commitId`，
一旦允许，数据库里就会混进无法溯源的条目——而这正是前几轮清理 `tags`/`era`/`kin`
要消灭的东西。

### 2.3 编辑的正确形态

编辑需要**后端**（`技术选型与前端重建.md` §3.1 的 S3 阶段），不是前端功能：

```
POST /api/commit
  { entityId, changes, rawRef, quote, reason }
  → 校验 rawRef 在 raw/ 中存在
  → 校验 quote 非空
  → 写 raw/（只追加）
  → 触发 transformer + build
  → 生成 commitId
```

**在此之前，前端不提供编辑入口。** 宁可没有，也不要一个产生脏数据的入口。

| person→literal | 5 |
| person→organization | 4 |
| organization→person | 4 |
| organization→literal | 3 |
| event→event | 2 |
| person→event | 1 |

**收益**：实体详情里的谓词名可点击跳转到定义页——与「有 id 的地方都可点击」

## 5.5 已实施：文献反向视图（S3 的前置能力）

编辑功能需要「查看 bot 抽取了哪些证据、从哪些证据文件」。
现有查询方向都是「实体 → 它的出处」，管理界面需要反过来。

新增 `/sources` 与 `/sources/:title`：

| 页面 | 内容 |
| --- | --- |
| `/sources` | 389 种文献，按引用数排序，带条形图 |
| `/sources/:title` | 该文献支撑的边断言 / 实体断言 + 引文多样性判定 |

### 数据层改动

`provenance` 表新增两列：

| 列 | 作用 |
| --- | --- |
| `locator` | JSON：`{sourceId, pages, title}`。此前只在分片里，未入库 |
| `source_title` | 文献名，带索引。此前只能从 `reason` 的《…》正则解析 |

实测：396,428 条出处有 locator（含页码/条目号），279,131 条有文献名（86.2%）。

### 引文多样性：核对出处质量的唯一手段

`distinctQuotes / total`。若某文献 2,348 条边断言只有 785 种 quote，
说明 1,563 条复用了别人的引文——它们仍「有出处」，但那个出处不是为它单独核对的。

页面给出三档判定：

- `≥ 0.9` 每条断言几乎都有独立引文
- `≥ 0.5` 部分共用，尚可
- `< 0.5` 大量共用同一条引文，可能不是逐条核对

实测《宋史》：2,348 条边 / 785 种 quote = 0.33，触发警告。这符合实际——
CBDB 的 `c_autogen_notes` 里有大量 `Auto-generated from PersonID = …` 的记录。

### 发现的源数据缺口

《宋史》来源的 3,742 条 KIN_DATA 行里，只有 94 行有 `c_pages`（2.5%）。
所以能追到「出自《宋史》」，追不到「卷 471 页 21a」。

这是 CBDB 本身的缺失，不是我们的 bug——但正是反向视图让这类缺口可见。

### 顺带修的竞态

`Api.isAvailable()` 是同步检查，而 probe 在 `app.mounted()` 里异步跑。
子组件可能先于 probe，于是 `isAvailable()` 返回 false，页面永远走「静态模式」——
即使后端明明在。

实测：`/sources` 页控制台里 `Api.isAvailable()` 是 true，组件里 `apiAvailable` 是 false、列表 0 行。

新增 `Api.whenReady()`，谓词页也一并改用。谓词页此前「看起来正常」只是
因为它的 mounted 恰好排在 probe 之后——靠运气正确不算正确。

## 5.6 已实施：提交校验（S3 骨架）

`POST /api/commit`，**只校验不落盘**。

真正写入要走完整链路：落 `raw/` → transformer 重跑 → 重新 build。
那是分钟级、多进程的，不能挂在一个 HTTP 请求里。端点响应里明确说明这一点，
否则调用方会以为已经写入。

### 校验规则

来自 `docs/architecture/节点类型与谓词.md` §6：

| 规则 | 拒绝理由 |
| --- | --- |
| `quote` 必填非空 | 空 quote 等于没出处 |
| `rawRef` 必填且能在 raw 层解析 | 出处不能是编的 |
| 谓词必须在注册表 | 未注册谓词产生「存在但看不见」的边 |
| 禁止自指 | 几乎总是录入失误 |
| 宾语类型匹配谓词 range | 类型错乱会让查询失真 |

**一次返回全部问题**，不是遇到第一个就停。用户提交一次表单，
应该一次看到所有问题，而不是改一个、再试、再发现下一个。

### 实测

- 真实 `rawRef` 通过；编造的 `rawRef` 被拦（`raw-not-found`）
- 空 `quote` 被拦
- 未注册谓词被拦
- **现有数据 878 条抽样 100% 通过**，200 条 `rawRef` 全部能在 raw 层解析

最后一项是关键：规则若比数据更严，编辑功能会无法使用；
若比数据更松，脏数据能进来。当前两者一致。

### 尚未做的

| 项 | 状态 |
| --- | --- |
| 写入链路（落 raw/ → transformer → build） | 未做 |
| 录入后台界面（读原文、划取） | 未做 |
| commit 序号分配与 commits.jsonl 追加 | 未做 |

`buildCommit()` 已能组装提交记录结构，但 `commitId` 分配留给调用方。

## 5.7 已实施：引文从原文截取 + 录入 CLI

### quote 不能由提交者填写

若允许直接写 `quote`，它与手写一条断言没有区别——任何内容都能被塞进
「原文摘录」，校验无法分辨是抄的还是编的。

改成：提交者只给 `span: {start, end}`，服务端从 raw 记录截取。
**编造在结构上不可能**。

### 第 0 层必须能确定性映射为纯文本

这是上一条的前提。`raw/` 存的是结构化记录（`payload` 对象），不是散文，
所以需要一层投影。

最初用 `JSON.stringify(payload)`，有两个问题：

1. **转义污染 span**——中文引号、换行变成 `\"` `
`，用户在界面上划取的是
   **渲染后**的文字，两者偏移对不上
2. **人读不了**——一行几百字符的 JSON，录入员看不出哪段是「原文」

改用行式格式 `字段名<TAB>值`：

```
c_notes	[待考。《宋史·安惇傳》云，惇二子郊、邦。]
c_personid	1
c_source	0
```

- 没有转义字符，界面显示的就是投影本身，span 一一对应
- 每行一个字段，录入员能直接看出「这句注释是原文」
- 字段名排序，顺序稳定

**确定性是硬要求**：同一条记录任何时间、任何进程投影结果必须逐字节相同，
否则今天存的 span 明天指向别的位置。

投影带 `version`，与 quote 一起记录。版本不符 → 拒绝信任旧 span，
要求重新核对。宁可让用户重做一次，也不要展示错位的引文。

### 反向还原

重新编辑时需要把已有 quote 的 span 还原成高亮区间。`locate()` 返回
原文、引文、前后文：

```
c_modified_date	
c_notes	[待考。《宋史·安惇傳》云，惇二子郊、邦。]   ← 划取「二子郊、邦」
。]
c_pages	
```

### 录入 CLI

```bash
# 先看原文，找要划的区间
node scripts/commit_cli.js --show-text 'raw:cbdb/KIN_DATA/1|2|180'

# 提交（可混合 entity 与 claim）
node scripts/commit_cli.js --file claims.json --author tester --message "说明"

# 只看截取结果，不写盘
node scripts/commit_cli.js --claim '...' --dry-run
```

链路：校验 → 落 raw（`raw/commit/{ENTITY,CLAIM}/`）→ 落分片 → 追加
`data/commits/commits.jsonl` → 提示重建。

### 端到端实测

提交「陳升之(77) —friend→ 王安石(1762)」，引文从
`raw:cbdb/ASSOC_DATA/...` 截取「初附王安石」：

| 层 | 结果 |
| --- | --- |
| 校验 | 通过，`span [607, 612) → 「初附王安石」` |
| raw | `raw:commit/CLAIM/c-000005#0` 可读回 |
| 分片 | `person:cbdb-77.json` 的 `relations.friend` 新增 |
| DB | 边数 347,939 → 347,940 |
| API | `/api/entity/person:cbdb-77` outgoing 含该边 |
| 前端 | 王安石 incoming 显示「← 陳升之」 |

### 顺带修的两个 bug

1. **`rawStore.append` 不清缓存**：`loadGroup` 把「组不存在」缓存成空 Map，
   于是写入后立刻 `getByRawId()` 返回 null。实测过。
2. **rawId 格式错误**：曾写成 `raw:commit/c-000004/2`，`parseRawId` 会把
   `c-000004` 当成 group，记录写进 `raw/commit/CLAIM/` 却按
   `raw/commit/c-000004/` 读，永远读不到。序号必须放进 key：
   `raw:commit/CLAIM/c-000004#2`。

### 实测中发现的一个真实录入错误

首次提交时把方向弄反了（1762 是王安石，77 是陳升之，而原文「初附王安石」
的主语是陳升之），产生了自指边。已修正并重建。

**教训**：`reason` 里的方向说明无法自动核对——「主语是谁」需要读原文才能判断。
这是自动校验的边界，也是为什么录入后台必须显示原文。

## 5.8 已实施：网页信源先落 raw

### 顺序不能反

抽取算法会变，网页会消失。若第一次抽取时只留下「结构化结果」，后来发现
漏抽了一个字段，就只能重新抓——而那时页面可能已改版或下线。

所以顺序必须是：

1. 抓 HTML
2. 清洗成纯文本
3. 落 raw（`payload.text` = 清洗后正文，`payload.html` = 原始 HTML）
4. **之后**才基于 raw 抽取

### 保留原始 HTML 的理由

清洗规则也会变（比如某天发现导航栏没去干净）。保留原始 HTML 意味着
清洗可以重做，不必重新抓。代价是体积大 10–30 倍——这是「不可更易的
本地信源」的代价。

### 异构站点的处理

不同站点正文容器不同。用「候选选择器 + 兜底全文」：

| 模式 | 含义 |
| --- | --- |
| `selector` | 命中已知容器（如人民网 `.text_con`），质量好 |
| `fallback` | 全部候选都没中，用清洗后全文，含导航页脚，**需复核** |

兜底的结果质量差，但**不丢数据**——抓到了就存，之后能重跑。

人民网类页面在正文末尾有 `(责编：xxx)` 标记，从该处截断比靠容器嵌套

### 证据节点：excerpt 是清洗后文本

这是核心原则：**信息源是清洗后的文本，不是会变动的外链**。

```json
{
  "id": "evidence:web-b3dbd7a5e23a",
  "medium": "web",
  "url": "http://cpc.people.com.cn/n1/2023/0311/c64036-32641934.html",
  "excerpt": "蒋作君简历

2023年03月11日…",
  "note": "rawRef: raw:web/people/b3dbd7a5e23a"
}
```

### 精确映射而非前缀映射

CBDB 用前缀映射（`raw:cbdb` → `evidence:cbdb`），因为它是一个数据库的
百万条记录。但网页是**每篇独立文档**——用 `raw:web` 前缀会把所有文章
归到同一个证据节点，等于说「这份简历出自人民网（整个网站）」，追不到
具体文章。

改为精确映射：`note` 字段声明 `rawRef: <rawId>`，`build_db` 据此建
一对一的映射。
