### 1.3 未解决：编辑功能与架构原则冲突

**现状**：

| 组件 | 行数 | 状态 |
| --- | --- | --- |
| `editor_panel.js` | 283 | 弹窗抽屉，编辑实体属性/关系/源码 |
| `relation_panel.js` | 258 | 弹窗抽屉，增删改关系类型 |

编辑写入 `localStorage`（`data_store.js:381 saveEntity`），不是数据库：

```js
DataStore.prototype.saveEntity = function (entity) {
  if (!this.isLocalMode || !entity || !FOLDERS[entity.type]) return false;
  this[folder][entity.id] = entity;
  local[entity.id] = entity;
  this._write(STORAGE_KEYS[entity.type], local);   // ← 只写浏览器本地
};
```

**这与项目原则冲突**：

1. **绕过 commit 机制**。`节点类型与谓词.md` §6 要求每条断言带 `commitId`，
   指向提交表；前端直接改实体等于凭空产生无出处的数据。
2. **绕过 provenance**。`provenance` 必填非空是硬约束，前端编辑不会产生它。
3. **编辑结果不共享**。只存在当前浏览器，刷新别人的视角看不到。
4. **UI 形态错位**。关系类型管理是低频、结构性操作，塞进弹窗抽屉不合适。

## 2. 目标架构

### 2.1 三层职责

```
raw/（只追加，唯一需备份）
   ↓  tools/raw/ingest_*       搬运，不解释
raw/（第 0 层）
   ↓  src/transformers/*.js     解释，可重跑
data/*/entities/（第 1 层）      派生，可重建
   ↓  scripts/build_db.js
humanmap.sqlite3（第 2 层）      查询用，可重建
   ↓  scripts/build_index.js → build_site.js
site/（发布快照）
```

**写路径只在第 0 层**。任何对意义网的修改都必须：
1. 落到 `raw/`（附文献依据）
2. 由 transformer 重跑生成第 1 层
3. 重新 build 第 2 层

前端**不参与**这条链路。

### 2.2 前端只读原则

| 允许 | 禁止 |
| --- | --- |
| 展示、检索、跳转、图谱 | 修改实体属性 |
| 查看出处、复制引用 | 增删关系 |
| 查看 commit 历史 | 改关系类型定义 |

理由不是「权限」，是**一致性**：前端改的数据没有 `provenance`、没有 `commitId`，
一旦允许，数据库里就会混进无法溯源的条目——而这正是前几轮清理 `tags`/`era`/`kin`
要消灭的东西。

### 2.3 编辑的正确形态

编辑需要**后端**（`技术选型与前端重建.md` §3.1 的 S3 阶段），不是前端功能：

```
POST /api/commit
  { entityId, changes, rawRef, quote, reason }
  → 校验 rawRef 在 raw/ 中存在
  → 校验 quote 非空
  → 写 raw/（只追加）
  → 触发 transformer + build
  → 生成 commitId
```

**在此之前，前端不提供编辑入口。** 宁可没有，也不要一个产生脏数据的入口。

| person→literal | 5 |
| person→organization | 4 |
| organization→person | 4 |
| organization→literal | 3 |
| event→event | 2 |
| person→event | 1 |

**收益**：实体详情里的谓词名可点击跳转到定义页——与「有 id 的地方都可点击」

## 5.5 已实施：文献反向视图（S3 的前置能力）

编辑功能需要「查看 bot 抽取了哪些证据、从哪些证据文件」。
现有查询方向都是「实体 → 它的出处」，管理界面需要反过来。

新增 `/sources` 与 `/sources/:title`：

| 页面 | 内容 |
| --- | --- |
| `/sources` | 389 种文献，按引用数排序，带条形图 |
| `/sources/:title` | 该文献支撑的边断言 / 实体断言 + 引文多样性判定 |

### 数据层改动

`provenance` 表新增两列：

| 列 | 作用 |
| --- | --- |
| `locator` | JSON：`{sourceId, pages, title}`。此前只在分片里，未入库 |
| `source_title` | 文献名，带索引。此前只能从 `reason` 的《…》正则解析 |

实测：396,428 条出处有 locator（含页码/条目号），279,131 条有文献名（86.2%）。

### 引文多样性：核对出处质量的唯一手段

`distinctQuotes / total`。若某文献 2,348 条边断言只有 785 种 quote，
说明 1,563 条复用了别人的引文——它们仍「有出处」，但那个出处不是为它单独核对的。

页面给出三档判定：

- `≥ 0.9` 每条断言几乎都有独立引文
- `≥ 0.5` 部分共用，尚可
- `< 0.5` 大量共用同一条引文，可能不是逐条核对

实测《宋史》：2,348 条边 / 785 种 quote = 0.33，触发警告。这符合实际——
CBDB 的 `c_autogen_notes` 里有大量 `Auto-generated from PersonID = …` 的记录。

### 发现的源数据缺口

《宋史》来源的 3,742 条 KIN_DATA 行里，只有 94 行有 `c_pages`（2.5%）。
所以能追到「出自《宋史》」，追不到「卷 471 页 21a」。

这是 CBDB 本身的缺失，不是我们的 bug——但正是反向视图让这类缺口可见。

### 顺带修的竞态

`Api.isAvailable()` 是同步检查，而 probe 在 `app.mounted()` 里异步跑。
子组件可能先于 probe，于是 `isAvailable()` 返回 false，页面永远走「静态模式」——
即使后端明明在。

实测：`/sources` 页控制台里 `Api.isAvailable()` 是 true，组件里 `apiAvailable` 是 false、列表 0 行。

新增 `Api.whenReady()`，谓词页也一并改用。谓词页此前「看起来正常」只是
因为它的 mounted 恰好排在 probe 之后——靠运气正确不算正确。

## 5.6 已实施：提交校验（S3 骨架）

`POST /api/commit`，**只校验不落盘**。

真正写入要走完整链路：落 `raw/` → transformer 重跑 → 重新 build。
那是分钟级、多进程的，不能挂在一个 HTTP 请求里。端点响应里明确说明这一点，
否则调用方会以为已经写入。

### 校验规则

来自 `docs/architecture/节点类型与谓词.md` §6：

| 规则 | 拒绝理由 |
| --- | --- |
| `quote` 必填非空 | 空 quote 等于没出处 |
| `rawRef` 必填且能在 raw 层解析 | 出处不能是编的 |
| 谓词必须在注册表 | 未注册谓词产生「存在但看不见」的边 |
| 禁止自指 | 几乎总是录入失误 |
| 宾语类型匹配谓词 range | 类型错乱会让查询失真 |

**一次返回全部问题**，不是遇到第一个就停。用户提交一次表单，
应该一次看到所有问题，而不是改一个、再试、再发现下一个。

### 实测

- 真实 `rawRef` 通过；编造的 `rawRef` 被拦（`raw-not-found`）
- 空 `quote` 被拦
- 未注册谓词被拦
- **现有数据 878 条抽样 100% 通过**，200 条 `rawRef` 全部能在 raw 层解析

最后一项是关键：规则若比数据更严，编辑功能会无法使用；
若比数据更松，脏数据能进来。当前两者一致。

### 尚未做的

| 项 | 状态 |
| --- | --- |
| 写入链路（落 raw/ → transformer → build） | 未做 |
| 录入后台界面（读原文、划取） | 未做 |
| commit 序号分配与 commits.jsonl 追加 | 未做 |

`buildCommit()` 已能组装提交记录结构，但 `commitId` 分配留给调用方。

## 5.7 已实施：引文从原文截取 + 录入 CLI

### quote 不能由提交者填写

若允许直接写 `quote`，它与手写一条断言没有区别——任何内容都能被塞进
「原文摘录」，校验无法分辨是抄的还是编的。

改成：提交者只给 `span: {start, end}`，服务端从 raw 记录截取。
**编造在结构上不可能**。

### 第 0 层必须能确定性映射为纯文本

这是上一条的前提。`raw/` 存的是结构化记录（`payload` 对象），不是散文，
所以需要一层投影。

最初用 `JSON.stringify(payload)`，有两个问题：

1. **转义污染 span**——中文引号、换行变成 `\"` `
`，用户在界面上划取的是
   **渲染后**的文字，两者偏移对不上
2. **人读不了**——一行几百字符的 JSON，录入员看不出哪段是「原文」

改用行式格式 `字段名<TAB>值`：

```
c_notes	[待考。《宋史·安惇傳》云，惇二子郊、邦。]
c_personid	1
c_source	0
```

- 没有转义字符，界面显示的就是投影本身，span 一一对应
- 每行一个字段，录入员能直接看出「这句注释是原文」
- 字段名排序，顺序稳定

**确定性是硬要求**：同一条记录任何时间、任何进程投影结果必须逐字节相同，
否则今天存的 span 明天指向别的位置。

投影带 `version`，与 quote 一起记录。版本不符 → 拒绝信任旧 span，
要求重新核对。宁可让用户重做一次，也不要展示错位的引文。

### 反向还原

重新编辑时需要把已有 quote 的 span 还原成高亮区间。`locate()` 返回
原文、引文、前后文：

```
c_modified_date	
c_notes	[待考。《宋史·安惇傳》云，惇二子郊、邦。]   ← 划取「二子郊、邦」
。]
c_pages	
```

### 录入 CLI

```bash
# 先看原文，找要划的区间
node scripts/commit_cli.js --show-text 'raw:cbdb/KIN_DATA/1|2|180'

# 提交（可混合 entity 与 claim）
node scripts/commit_cli.js --file claims.json --author tester --message "说明"

# 只看截取结果，不写盘
node scripts/commit_cli.js --claim '...' --dry-run
```

链路：校验 → 落 raw（`raw/commit/{ENTITY,CLAIM}/`）→ 落分片 → 追加
`data/commits/commits.jsonl` → 提示重建。

### 端到端实测

提交「陳升之(77) —friend→ 王安石(1762)」，引文从
`raw:cbdb/ASSOC_DATA/...` 截取「初附王安石」：

| 层 | 结果 |
| --- | --- |
| 校验 | 通过，`span [607, 612) → 「初附王安石」` |
| raw | `raw:commit/CLAIM/c-000005#0` 可读回 |
| 分片 | `person:cbdb-77.json` 的 `relations.friend` 新增 |
| DB | 边数 347,939 → 347,940 |
| API | `/api/entity/person:cbdb-77` outgoing 含该边 |
| 前端 | 王安石 incoming 显示「← 陳升之」 |

### 顺带修的两个 bug

1. **`rawStore.append` 不清缓存**：`loadGroup` 把「组不存在」缓存成空 Map，
   于是写入后立刻 `getByRawId()` 返回 null。实测过。
2. **rawId 格式错误**：曾写成 `raw:commit/c-000004/2`，`parseRawId` 会把
   `c-000004` 当成 group，记录写进 `raw/commit/CLAIM/` 却按
   `raw/commit/c-000004/` 读，永远读不到。序号必须放进 key：
   `raw:commit/CLAIM/c-000004#2`。

### 实测中发现的一个真实录入错误

首次提交时把方向弄反了（1762 是王安石，77 是陳升之，而原文「初附王安石」
的主语是陳升之），产生了自指边。已修正并重建。

**教训**：`reason` 里的方向说明无法自动核对——「主语是谁」需要读原文才能判断。
这是自动校验的边界，也是为什么录入后台必须显示原文。

## 5.8 已实施：网页信源先落 raw

### 顺序不能反

抽取算法会变，网页会消失。若第一次抽取时只留下「结构化结果」，后来发现
漏抽了一个字段，就只能重新抓——而那时页面可能已改版或下线。

所以顺序必须是：

1. 抓 HTML
2. 清洗成纯文本
3. 落 raw（`payload.text` = 清洗后正文，`payload.html` = 原始 HTML）
4. **之后**才基于 raw 抽取

### 保留原始 HTML 的理由

清洗规则也会变（比如某天发现导航栏没去干净）。保留原始 HTML 意味着
清洗可以重做，不必重新抓。代价是体积大 10–30 倍——这是「不可更易的
本地信源」的代价。

### 异构站点的处理

不同站点正文容器不同。用「候选选择器 + 兜底全文」：

| 模式 | 含义 |
| --- | --- |
| `selector` | 命中已知容器（如人民网 `.text_con`），质量好 |
| `fallback` | 全部候选都没中，用清洗后全文，含导航页脚，**需复核** |

兜底的结果质量差，但**不丢数据**——抓到了就存，之后能重跑。

人民网类页面在正文末尾有 `(责编：xxx)` 标记，从该处截断比靠容器嵌套

### 设计约束：不造泛用谓词

抽取器**只能使用已注册的谓词**，找不到合适的就跳过并记 WARN。
本格式全部对应已有谓词：

| 原文 | 谓词 | 宾语 |
| --- | --- | --- |
| 男 / 女 | `gender` | literal |
| 汉族 | `ethnicity` | literal |
| 1955年7月生 | `birthDate` | literal |
| 安徽怀宁人 | `bornAt` | organization（籍贯节点） |
| 致公党成员 | `memberOf` | organization |
| 十四届全国政协副主席 | `memberOf` | organization + `role` 限定词 |

「副主席」放 `role` 限定词而不是独立谓词——它说不出具体关系，
只是成员关系的属性。造一个 `viceChairmanOf` 就是重复 `tags` 的错误。

### 届次不进组织名

「十四届全国政协副主席」的组织是「全国政协」，不是「十四届全国政协」。
把届次放进组织名会让下一届出现第二个节点，组织永远合并不起来。
届次记在 `reason` 里，不丢信息。

### 组织名展开为全称

原文写简称（「致公党」「民革」），节点名写全称（「中国致公党」「中国国民党
革命委员会」），否则同一组织因页面写法不同而分裂。只做**已知的**展开
（8 个民主党派），不认识的写法原样保留并记 WARN，不猜。

组织 id 由名称哈希生成：同一名的两次哈希一致，跨页面落到同一节点。

### 每条断言都带 span

抽取结果是**候选**不是事实。每条记录原文中的字符区间，提交时服务端
按 span 重新截取 quote——抽取器自己算的 quote 不作数。

## 5.10 已实施：边级起止时间（valid_from / valid_to）

### 发现的设计-实现缺口

文档 §2.1 早有定则：「节点存自身存续区间，边存关系本身的起止。」
但 `edges` 表**从来没有 `valid_from`/`valid_to` 列**——设计存在，
实现缺失，「同一人两次任同一职」这类分阶段关系根本无法表达。

### 不是所有三元组都带时间

按 §2.2 的三档时间性：

| 档 | 谓词例 | 要时间吗 |
| --- | --- | --- |
| `persistent` | 父/母/子/女 | 不要，一旦成立永久成立 |
| `concurrent` | 夫妻/任职/成员 | **要**，两端须同时在 T 时刻存在 |
| `attribute` | 性别/民族/出生时间 | 不要，属性快照 |

只有 `concurrent` 类的边该填起止。`persistent`/`attribute` 填了也没意义。

### 未知日期怎么处理：留空，不编造

`valid_from`/`valid_to` 都可空。**未知 ≠ 不存在**：

- 「加入致公党时间不详」是一条**成立的断言**，只是缺时间
- 只有 `from` 没有 `to`（或反之）是合法状态——「2010 年至今」
- 强制非空会逼人编造日期，或者干脆不录入——两者都比留空更糟

前端显示规则：**有则显示，无则不显示**。不在每条边上挂「时间不详」标签——
绝大多数边（CBDB 的 34.8 万条）都没有时间，挂满标签是噪音。
`role` 与时间一起显示（「中央主席 (2022)」），无时间只显示 role。

### 抽取器不为「现任」编造时间

简历原文「1974年3月参加工作」**不是**加入党派的日期，不是就任现职的日期。
拿它填 `dates.from` 就是编造。所以「现任…」抽出的 `memberOf` 全部 dates 留空。

测试里明确断言了这一点（`dates: 无日期是合法状态，不编造`）。

### 实现

| 层 | 改动 |
| --- | --- |
| schema | `edges` 加 `valid_from INTEGER` / `valid_to INTEGER` + `idx_edges_time` |
| build | `splitRelationEntry` 从分片条目的 `dates:{from,to}` 拆出两列，不留在 qualifiers |
| CLI | 断言可带 `dates:{from,to}`，只写有值的 |
| API | 返回 `validFrom`/`validTo`（null = 时间不详） |
| 前端 | `relationsFromApiDetail` 透传；模板 `r.start`/`r.end` 显示 |

分片格式：`{"id":"organization:x","role":"主席","dates":{"from":1995,"to":2000}}`。

`dates` 拆列而不留在 qualifiers 的理由：语义不同——`role` 回答「哪一个」，
`dates` 回答「什么时候成立」。后者要参与时间切片查询，埋在 JSON 里只能全表扫。

### 验证

给「致公党中央主席」补 `dates:{from:2022}`（示意数据，验证显示链路），
详情页显示「中国致公党 / 中央主席 (2022)」；全国政协（无时间）只显示「副主席」。

## 5.11 边的身份：什么算同一个事实

这是数据模型最容易搞错的一处，两种错误方向都实际发生过。

### 错误 ①：只按 SPO 做 id

原实现 `edgeId(subject, predicate, object)`，配合 `INSERT OR IGNORE`：
第二条同 SPO 的边被**静默丢弃**。同一人两次任同一职被合并成一条，
「有两次」这个事实丢失，两条证据抢一个 id。

CBDB 恰好没有同 SPO 重复（实测 0 条），所以这个 bug 一直没暴露。

### 错误 ②：把证据身份放进 id

第一次修的时候把 `rawRef + span` 放进签名，结果是**每条证据一条边**：
同一事实被两个信源验证就产生两条重复边，页面上同一关系出现 N 次。

### 正确判据：事实本身的差异才分边

| 差异 | 分边？ | 理由 |
| --- | --- | --- |
| 时段不同 | **是** | 同一人两次任同一职，是两个关系实例 |
| 观测点不同 | **是** | 两次分别被记载在不同年份 |
| 限定词不同 | **是** | 「他的妻子」与「他的妾」是不同事实 |
| **证据来源不同** | **否** | 同一事实的多个信源，是同一条边的多个出处 |

所以边 = **一个事实**，provenance = 这个事实的**证据列表**。

### 实现

事实签名（不含证据）：

```
sig = validFrom | validTo | observedAt | qualifiers
edgeId = sha256(subject, predicate, object, sig)[:12]
```

`build_db` 先按签名分组：同组条目合并 provenance，不新建边。

实测效果：

| 情形 | 边 | provenance |
| --- | --- | --- |
| 两个信源说同一件事 | 1 条 | 2 行 |
| 同一人两次任同一职 | 2 条 | 各 1 行 |

### 顺带发现的数据事实

重建后边数 **347,978 → 280,786**，少了 67,192 条。

原因是 CBDB 里存在大量「同一事实多条记录」（同一对人物在不同 `c_source`
下有重复 KIN_DATA 行），之前是重复边，现在按事实签名合并了。
这不是丢数据——出处行数（487,023）没变，证据一条都没少，只是
它们现在挂到了正确的边上。

同 SPO 分条的情况实测只有 7 条，全部是限定词不同
（`role: concubine` vs 无 role），确实是不同事实。

## 5.12 观测点：第三种时间语义

### 问题

史料常常只说「某年某月，他任此职」，**没说何时开始、何时结束**。

两种错误记法：

- `valid_from=1050, valid_to=1050` —— 伪造精度，宣称关系只存在这一年
- `valid_from=1050, valid_to=null` —— 宣称从 1050 年起持续到未知未来

都不对。实际可能持续十年，也可能次年就结束。

### 解法：`observed_at`

第三种语义：**「有证据证明此关系在该时刻成立，但不宣称它此前/之后也存在。」**

```
valid_from / valid_to  ← 明确知道区间
observed_at            ← 只证明此刻成立
两者都空               ← 时间不详（合法状态，不是缺失）
```

### 为什么不能只靠「两端存在」兜底

人物可以靠「生年 ≤ a，卒年 ≥ b」推断区间，因为生卒是连续状态：
活到 60 岁意味着中间每一年都活着。

**任职不是**。允许中间分段任同一职位——A 到 B 时刻都有观测，
不能推出整个 [A, B] 期间都在任。所以任职类关系不能用端点推断，
必须有 `observed_at` 这种「只保证点」的表达。

### 时间切片查询

`GET /api/slice?entity=<id>&at=<year>`，三类边都命中但**用 `basis` 区分**：

| basis | 含义 |
| --- | --- |
| `interval` | 有明确区间，T 落在其中 |
| `observed` | 有证据记载 T 时刻成立（不宣称此前后） |
| `persistent` | 谓词本身永久成立（父子关系不随时间失效） |

`persistent` 这一类是关键：CBDB 不记父子关系的起止，若切片只认时间列，
「查 1050 年他的父亲是谁」会永远返回空——数据在库里，查询却掠过它。
按谓词的时间性把它带出来，才是「能查得出来而非直接被掠过」。

混为一谈会让「1050 年他在任」看起来和有明确任期的边一样确定，
所以 `basis` 必须显式返回给调用方。
