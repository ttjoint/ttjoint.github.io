# 分层架构重构方案（0/1/2/3 层)

> 状态：**设计阶段，未实施**。本文是实施前的冻结依据，代码改动一律以此为准。
>
> 触发原因：项目从「静态展示页」扩展为「资料数据服务器」，且需接入 CBDB 五张大表
> （约 180 万行关系数据）、《明史》《党史》原文、公职人员原始网页存档。
> 现有「实体即事实」的单层模型已无法支撑。

---

## 1. 为什么必须分层

### 1.1 已经造成的损失（不是假设）

| 事实 | 后果 |
| --- | --- |
| `data/imports/official/` 中 **147 / 165** 条记录没有保存原文 | 无法核对、无法重新提取；字段错了就是永久错 |
| 111 个证据节点中 **0** 个保存了 `excerpt` | 证据无法验证，只剩一个 URL |
| 486,786 个人物只存了 `external.cbdbId` | CBDB 原行未入库，改映射必须重查 584MB 的 SQLite |
| 本轮修导入器 bug，**重导了全部 486k 人** | 一处映射错误 = 一次全量重算 |

最后一条是核心动机。当前 `data/*/entities/` 既是权威又是派生物，导致**任何映射修正都要重写权威数据**，而重写过程中一旦出错（历史上真的发生过：5269 个实体被索引倒灌成空壳，见 `架构设计.md` §6.7）原始信息就不可恢复。

另一个具体例子：官方人员导入器把解析结果与原文混在同一个 `records` 数组里——
`{ "name": "李强", "birthDate": "1959年7月", "resume": "李强，男，汉族……" }`。
已解析字段与原文平铺共存，没有哪个字段能说清「这个名字是从哪段原文取的」。
分层后二者各归各位。

### 1.2 分层要解决的三件事

1. **原始语料永久保存**，与解析结果解耦。映射规则可版本化、可重跑、可丢弃。
2. **证据链可回溯**：任何一条边都能指到 0 层的某一行/某一段。
3. **schema 不必冻结**：因为 1 层可从 0 层重建，改模型不再有「重导 500 万条」的代价。

## 2. 四层定义

```
┌──────────────────────────────────────────────────────────────┐
│  第 0 层  raw/          原始记录。**只追加，永不修改**            │
│  ──────────────────────────────────────────────────────────  │
│  CBDB 行、网页原文、史书段落、用户录入文本                      │
│  存的是「某来源在某个位置说了什么」，不做任何解释                  │
└──────────────────────────────────────────────────────────────┘
                            ↓  转换器（可版本化 / 可重跑 / 可丢弃）
┌──────────────────────────────────────────────────────────────┐
│  第 1 层  entities/     实体与边。**派生，可整层重建**            │
│  ──────────────────────────────────────────────────────────  │
│  8 类节点、谓词原语、关系边。这一层回答「库里有什么」             │
│  ← 当前 data/*/entities 的形态，但降级为派生物                    │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  第 2 层  index/ + SQLite   查询索引。**派生，可随时重建**        │
│  ──────────────────────────────────────────────────────────  │
│  分页、时间轴、搜索、FTS5、邻接表                                │
│  这一层回答「怎么快速找到」                                      │
└──────────────────────────────────────────────────────────────┘
                            ↓
┌──────────────────────────────────────────────────────────────┐
│  第 3 层  views/        视图与展示。**可替换，可并存多套**        │
│  ──────────────────────────────────────────────────────────  │
│  家谱视图、任职视图、时间轴、生成式词条、图渲染                   │
│  这一层回答「怎么呈现」                                          │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 每层的不变量

| 层 | 可变性 | 谁能写 | 丢了怎么办 |
| --- | --- | --- | --- |
| 0 raw | **只追加** | 抓取器、导入器、用户提交 | **不可恢复**，必须备份 |
| 1 entities | 可重建 | 转换器（从 0 层） | 重跑转换器 |
| 2 index | 可重建 | `build_index.js` / `build_db.js` | 重建命令 |
| 3 views | 无状态 | 前端代码 | 改代码 |

**只有第 0 层需要备份。** 这是分层最重要的收益之一——备份目标从 487,389 个文件的目录树，变成一份不可变的原始语料归档。

## 3. 第 0 层设计

### 3.1 存储位置

```
raw/
├── cbdb/                          # record 类
│   ├── manifest.json              # 源文件哈希、抓取时间、行数
│   └── BIOG_MAIN/
│       ├── batch-000.jsonl        # 每行一条，原始字段原样保留
│       └── batch-001.jsonl
├── web/                           # document 类
│   └── gov-cn-2023-03-12-5746205/
│       ├── manifest.json          # rawId、url、contentHash、segments
│       ├── content.html           # 原始字节，一字不改（不截断）
│       └── text.txt               # 抽取的纯文本，供浏览与定位
├── book/                          # document 类
│   └── 明史/
│       ├── manifest.json
│       ├── 卷一.txt
│       └── 卷二.txt
└── user/                          # document 类
    └── <userId>/
        └── submission-2026-10-20.jsonl
```

**目录按来源分类，不按内容分类**——因为「怎么读它」取决于来源（CBDB 按列读，
网页按段读，史书按章节读）。内容主题（人物/组织/事件）是第 1 层的事。

### 3.2 两种载体：`record` 与 `document`

不同原始语料的形态差异很大，不能塞进同一个 `payload` 字段：

| 类型 | 例子 | 体积 | 结构 | 定位方式 |
| --- | --- | --- | --- | --- |
| **`record`** | CBDB 表行、结构化数据 | 1 KB/行 | 强（列） | `sourceKey` |
| **`document`** | 网页、史书、公文全文 | 2 KB–数百万字 | 无/弱 | `(rawId, segId)` |

两者共用 `rawId` / `contentHash` / `capturedAt` / `locked`，但内容布局不同。

#### A. `record` —— 一行一记录的强结构数据

```jsonc
{
  "rawId": "raw:cbdb-BIOG_MAIN-100001",
  "kind": "record",
  "source": "cbdb",
  "sourceTable": "BIOG_MAIN",
  "sourceKey": "100001",               // 表内主键，也是定位键
  "capturedAt": "2026-10-20T10:00:00Z",
  "contentHash": "sha256:...",
  "payload": { "c_personid": 100001, "c_name_chn": "許雪英", "c_female": 1, "c_dy": 20 }
}
```

一条边指向整个记录：`raw:cbdb-BIOG_MAIN-100001`

#### B. `document` —— 网页、史书、公文

```jsonc
{
  "rawId": "raw:web-gov-cn-2023-03-12-5746205",
  "kind": "document",
  "source": "web",
  "url": "https://www.gov.cn/guoqing/2023-03/12/content_5746205.htm",
  "capturedAt": "2026-10-17T03:06:56.024Z",
  "httpStatus": 200,
  "title": "李强 简历",
  "contentHash": "sha256:...",
  "files": {
    "raw": "content.html",      // 原始字节，一字不改
    "text": "text.txt"          // 抽取的纯文本，供浏览与定位
  },
  "segments": [
    { "segId": "p1", "text": "李强，男，汉族，1959年7月生……", "offset": 0, "length": 102 },
    { "segId": "p2", "text": "……", "offset": 102, "length": 87 }
  ]
}
```

**`segments` 是必需的，不是可选的。**

没有分段，`rawRef` 只能指到「在《明史》里」——与现在「在某个 URL 里」一样无用。
分段的粒度由来源决定：

| 来源 | 分段单位 |
| --- | --- |
| 网页 | HTML 块级元素（`<p>`、`<div>`） |
| 电子书 / 史书 | 章节 → 段落 |
| 公文 / 报告 | 段落 |
| 用户录入 | 每次提交为一段 |

边指向具体段落：`raw:web-gov-cn-2023-03-12-5746205#p1`

### 3.3 三条硬规则

1. **原文字节一律原样保存**，不做 trim、不转码、不合并同义字段、**不截断**。
   CBDB 的 `0` 是「未知」哨兵这种事，是**解释**，属于转换器，不属于第 0 层。
2. **`contentHash` 必填**。它让「这份原文是否被改过」可以机械验证，也是锁定时要校验的对象。
3. **不存解释，只存陈述**。第 0 层不知道「父亲」是什么，只知道某张表某行某个字段、
   或某份文档某一段写了什么。

### 3.4 已造成的反向教训：截断发生在源头

现有 `scripts/import_gov_leaders.js:85` 有一行：

```js
if (stop > 40) body = body.slice(0, stop);   // ← 解析前先砍掉正文
```

它把网页正文截到第一个句号附近，只留下 102 个字符（实测），而原页有数 KB。
已入库的官方人员记录中 **147/165 条无完整原文**（实测），且**没有任何脚本保存过 HTML 字节**——
`writeFileSync` 只写解析后的 JSON。

这条规则因此不是冗余表述：它对应的是一次已经发生的信息丢失。

### 3.5 锁定（lock）

用户提到的「确认原文忠实后将之锁定」：锁定的含义是**记录进入不可变状态**。

```jsonc
{
  "rawId": "raw:web-...",
  "locked": { "at": "2026-10-21T09:00:00Z", "by": "user:me", "contentHash": "sha256:..." }
}
```

- 未锁定：允许追加校正（如重新抓取修正编码错误）
- 已锁定：只读。要改必须新建一条 raw 记录并标注 `supersedes`，旧记录保留
- 转换器只从**已锁定**的 raw 记录提取实体（未锁定的数据还在变动，提取结果无意义）

### 3.6 统一读接口

不管底层是 `record` 还是 `document`，转换器只看同一个接口：

```js
rawStore.get('raw:cbdb-BIOG_MAIN-100001')
// → { rawId, kind:'record', payload, ... }

rawStore.get('raw:web-gov-cn-2023-03-12-5746205#p1')
// → { rawId, kind:'document', segId:'p1', text:'李强，男，汉族……', ... }

rawStore.segments('raw:web-gov-cn-2023-03-12-5746205')
// → [{segId,text,offset,length}, ...]   // 供需要遍历整篇的抽取器
```

**存储形状分两种，读取接口只有一个。** 加新语料类型时只需新增 transformer，
不改 raw 层与读接口。

## 4. 第 1 层：实体与边

### 4.1 与现状的关系

**形态不变**：`data/<type>/entities/*.json` 仍是这个形状。变化只有两点：

1. **降级为派生物**——可以从 0 层完整重建
2. **每条边/字段带 `rawRefs`**——指向 0 层的证据

### 4.2 新增 `provenance` 字段

```jsonc
{
  "id": "person:cbdb-100001",
  "name": "許雪英",
  "type": "person",
  "props": { "性别": "女", "朝代": "清" },
  "provenance": {
    "props.性别": ["raw:cbdb-BIOG_MAIN-100001"],
    "props.朝代": ["raw:cbdb-BIOG_MAIN-100001"]
  },
  "relations": { "father": ["person:cbdb-100002"] },
  "relationProvenance": {
    "father:person:cbdb-100002": ["raw:cbdb-KIN_DATA-555"]
  }
}
```

这解决了现状里「`external.cbdbId` 只能指到人，指不到具体断言」的问题。

### 4.3 类型扩充

从 5 类扩到 8 类（详见 `docs/architecture/节点类型与谓词.md`）：

```
person  organization  event  evidence  thing      现状已有
office  work  place                                 新增
```

**不合并为「抽象概念」单类**。理由见 §4.4。

### 4.4 为什么保留类型而不合并

上一轮讨论过的取舍，结论记录在此以免反复：

| 方案 | 检索成本 | 维护成本 |
| --- | --- | --- |
| 合并为 `abstract` 单类 | 每次查询都要靠**边模式**推断「这是职位还是书」；边模式无法索引 | 低（少 3 个类型） |
| 保留 8 类 | 类型即索引，`WHERE type='office'` 一步到位 | 低（一张 8 行的表） |

类型表只有 8 行，却能替检索层挡掉全部边模式推断。**合并省下的维护成本远小于它带来的查询复杂度。**

若将来确实需要「所有抽象事物」的视图，在第 3 层做联合查询即可——那正是视图层的职责。

## 5. 转换器（0 → 1）

### 5.1 定义

```js
// src/transformers/<source>.js
module.exports = {
  name: 'cbdb-biog',
  version: '1.0.0',            // 语义化；映射规则变了必须升版本
  appliesTo: { kind: 'record', source: 'cbdb', sourceTable: 'BIOG_MAIN', locked: true },
  transform(rawRecord, ctx) {  // 返回 0..n 个实体/边片段
    return { entities: [...], edges: [...] };
  },
};
```

`appliesTo` 必须声明 `kind`（`record` 或 `document`），因为两种载体的入参形状不同：

| `kind` | 转换器收到的 | 典型用法 |
| --- | --- | --- |
| `record` | 整个 `payload` 对象（一行） | 按列取字段 |
| `document` | **单个 `segment`** | 从一段文本抽取 |

`document` 类转换器按段调用，而不是整篇——这样每个抽取结果都自带精确的 `segId`，
不需要事后回找位置。需要跨段逻辑时（如「李强的职位在下一段」）用 `ctx.segments()`
拿到全文自行拼接。

### 5.2 版本化的意义

- 转换器版本写进实体：`"derivedBy": "cbdb-biog@1.0.0"`
- 改映射后**重跑该转换器即可**，不动其他转换器的产物
- 「某个字段为什么是这个值」可回答：哪条 raw + 哪个转换器版本

**对人文学科尤其重要**：抽取规则（正则、词典、LLM prompt）会反复调。
旧版抽取结果必须可重现，否则无法回答「当时为什么把这句读成生年」。

### 5.3 转换器清单（预估）

| 来源 | kind | 转换器 | 产出 | 阶段 |
| --- | --- | --- | --- | --- |
| CBDB `BIOG_MAIN` | record | `cbdb-biog` | 人物实体 | P2 |
| CBDB `KIN_DATA` | record | `cbdb-kin` | 亲属边 | P2 |
| CBDB `ALTNAME_DATA` | record | `cbdb-altname` | 别名 | P4 |
| CBDB `ENTRY_DATA` | record | `cbdb-entry` | 科举边 | P4 |
| CBDB `POSTED_TO_OFFICE_DATA` | record | `cbdb-office` | 任职边 | P4 |
| 政府网简历 | document | `resume-gov` | 人物实体 + 任职 | P7 |
| 《明史》 | document | `book-mingshi` | **未定** | 远期 |
| 《党史》 | document | `book-dangshi` | **未定** | 远期 |

最后两行刻意写成「未定」：**史书抽取规则依赖人读，不能先编一套正则。**
先无结构存入 raw，抽取方式等到真要用时再定——这正是分层的价值：
原始语料存下来了，抽取可以以后再补。

### 5.4 CBDB 映射的现状问题

现有 `scripts/import_cbdb.js` 是**导入器**（读 SQLite → 写 entities），把三件事混在一起：读源、映射、写库。

重构后拆为：

```
tools/raw/ingest_cbdb.js        SQLite → raw/cbdb/*.jsonl   （只搬运，不解释）
src/transformers/cbdb-biog.js   raw → 人物实体
src/transformers/cbdb-kin.js    raw → 亲属边
```

这样「重导 486k 人」变成「重跑 transformer」，10 分钟内完成，且 raw 不动。

### 5.1 实施状态：`cbdb-kin` 已接线（`cbdb-biog` 尚未）

`src/transformers/cbdb-kin.js` 从设计起就存在，但**长期没有调用方**——
`import_cbdb.js` 一直直接读 SQLite。结果是同一份 KIN_DATA 有两套读取路径：

| | 输入 | 现状 |
| --- | --- | --- |
| raw 层 | `raw_store.readGroup` | 已接线（`raw_transformer_runner.js`） |
| SQLite | `db.prepare('SELECT * FROM KIN_DATA')` | 仅作回退 |

两条路都调 `derivePredicate()`，映射一致，但 raw 层多两样东西：

- **`rawId`** 第 0 层定位，可直接当 `provenance.rawRef`，且能在 `raw/` 里
  用 `rawStore.exists()` 核验。SQLite 路径的 rawRef 是字符串拼出来的，
  拼错了也看不出来。
- **`contentHash`** 内容指纹，可检测源记录被篡改。

而且 raw 层是**不可变的原始记录**，SQLite 会随 CBDB 换版本而变。

**接线后实测**：559,456 条 raw 记录 → 412,016 条边，跳过自指 55 /
模糊码 6,791 / 复合码 140,584。边的 `rawRef` 与 raw 层 `rawId` 完全一致，
抽查 200 条全部能在 `raw/` 中解析到真实记录——溯源闭环成立。

**回退保留**：`raw/` 未生成时（旧 checkout）自动回退到 SQLite，导入不中断。

**小样本优先**：`runTransformer` 支持 `limit` / `filter` / `enrich`。
验证接线只需几百条——全量 55.9 万行要几分钟，而接线是否通几百条就能看出。

## 6. 第 2 层：存储引擎

### 6.1 为什么需要 SQLite

实测当前规模：

| 文件 | 体积 | 问题 |
| --- | --- | --- |
| `persons/index/` | 140.2 MB | 静态可接受，但角色是「全量下载」 |
| `persons/index/chrono.json` | **29 MB** | 时间轴必须整份下载 |
| `persons/search/` | 35.4 MB | 108 个首字桶 |

接入 CBDB 五表后需处理约 **180 万条关系**。静态方案无法做跨实体组合查询（例如「曹操的儿子们的任职」），组合数不可预计算。

**结论：SQLite 作为查询引擎，FTS5 做全文搜索。**

### 6.2 SQLite 的角色：索引，不是权威

明确记下这条，防止将来搞反：

```
权威：raw/（只追加）  →  派生：entities/  →  派生：SQLite / index/
```

SQLite 丢失可以重建；`raw/` 丢失不可恢复。

### 6.3 表结构草案

```sql
CREATE TABLE entities (
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL,
  name TEXT NOT NULL,
  summary TEXT,
  props_json TEXT,
  valid_from INTEGER,      -- JDN
  valid_to INTEGER,
  derived_by TEXT
);
CREATE INDEX idx_entities_type ON entities(type);
CREATE INDEX idx_entities_time ON entities(valid_from, valid_to);

CREATE TABLE edges (
  subject TEXT NOT NULL,
  predicate TEXT NOT NULL,
  object TEXT NOT NULL,      -- 实体 id 或 literal 值
  is_literal INTEGER NOT NULL DEFAULT 0,
  role TEXT,
  valid_from INTEGER,
  valid_to INTEGER,
  source_raw TEXT
);
CREATE INDEX idx_edges_subject ON edges(subject, predicate);
CREATE INDEX idx_edges_object ON edges(object, predicate);
-- ⚠ 必需：实测缺此索引时「某谓词的全部边」慢 1400 倍（111ms vs 0.08ms），
-- 因为 predicate 不是上面两个索引的首列。见 §9.2。
CREATE INDEX idx_edges_predicate ON edges(predicate, subject);

CREATE TABLE aliases (entity_id TEXT, alias TEXT, kind TEXT);
CREATE INDEX idx_aliases ON aliases(alias);
CREATE VIRTUAL TABLE search USING fts5(name, aliases, summary, content='');
```

### 6.4 分阶段

**第 1 阶段**：SQLite 只读，作为 `data/` 的替代查询源，与现有静态路径并存对照
**第 2 阶段**：前端改走 SQLite（本地 HTTP API）
**第 3 阶段**：录入走 SQLite（事务、并发）

## 7. 第 3 层：视图层重建

### 7.1 现状问题

`css/style.css` 1,078 行、`js/views/*.js` 2,583 行，全部假设「静态 JSON + 全量内存」。引入 SQLite 后取数方式改变，视图层需要重建。

### 7.2 视图与「域」的关系

对照参考方案（wikimedia 式现象库）的「域」概念：本项目的视图层承担类似职责，但**不做版本化域管道**。理由：

- CBDB 是单一权威源，不像众包现象库需要多套互相矛盾的读法
- 域管道的重算成本在 1 亿现象级才值得，本项目是百万级

保留接口余地：`views/` 声明「需要哪些谓词、如何排序」，将来可升级为域。

## 9. 规模边界与性能实测

以下均为实测（`node:sqlite` 内存库，Node v24.19.0），不是估算。

### 9.1 查询性能随规模的变化

| 操作 | 10 万 | 50 万 | 200 万 | 结论 |
| --- | --- | --- | --- | --- |
| `COUNT(*)` 全表 | 1 ms | 1 ms | 2 ms | 安全 |
| `LIKE '%x%'` 全表扫描 | 10 ms | 51 ms | **247 ms** | ⚠ 线性，不可用于交互路径 |

**`LIKE '%..%'` 是本项目唯一真正的性能陷阱。** 它无法用索引，200 万行就已经 247ms。
对策：所有文本搜索走 **FTS5**，禁止在查询路径写 `LIKE '%..%'`。

### 9.2 索引设计决定成败

同一句 SQL，索引首列不同差 6 倍：

| 查询 | 索引 | 耗时 |
| --- | --- | --- |
| `WHERE predicate=?` （取 100 行） | `(subject,predicate)` | 111 ms → **0.08 ms** |
| 同上 | `(predicate,subject)` | **19 ms**（count） / 0.08 ms |

**结论**：`edges` 必须建 **`(predicate, subject)`** 与 **`(object, predicate)`** 两个索引。
只建前一个会使「某谓词的全部边」这类查询慢 1400 倍。

### 9.3 实际基准（500k 实体 + 180 万边）

| 操作 | 耗时 |
| --- | --- |
| 单实体出边 | 0.005 ms |
| 单实体入边 | 0.005 ms |
| 二跳展开（父之父） | 0.005 ms |
| `predicate` 全量 count | 19 ms |
| 建库（含 180 万边插入） | 约 11 s |

**一跳、二跳邻接查询在百万级下均为微秒级**——这是本项目 90% 的查询形态。

### 9.4 FTS5 全文检索

20 万行、双字段（名 + 别名），前缀搜索 **5.2 ms/次**。按线性推算，
200 万行约 50 ms——可接受。

### 9.5 瓶颈会在哪里出现

按风险排序：

| 风险 | 触发条件 | 对策 |
| --- | --- | --- |
| **无索引的文本筛选** | 写了 `LIKE '%..%'` | 代码审查硬规则；走 FTS5 |
| **类型聚合** | `WHERE type=?` 无索引 → 100 次 3.7 s | `(type)` 索引，已列入建表语句 |
| **深图递归** | 「曹操的所有后代」（递归 CTE） | 限制深度；缓存结果 |
| **全量重建** | 每次 `build_db` 都全建 | 接受；本就是派生层 |
| **JSON 分片写入** | 487k 小文件 I/O | 只写变更；批量打包 |

### 9.6 合理规模上限

| 规模 | 可行性 |
| --- | --- |
| 百万实体 + 200 万边 | ✅ 单机 SQLite 轻松（实测一跳 0.005 ms） |
| 千万实体 | ⚠ **可行但需改动**，见 §9.7 |
| 亿级 | ❌ 超出本项目目标 |

**不要为亿级做设计。** 本项目当前需求（CBDB 全量约 66 万人、约 180 万边）只在百万级。

### 9.7 千万级实测：哪些会坏，哪些不会

为避免「凭感觉说需要换数据库」，以下为 **1,000 万实体 + 800 万边**的实测
（`node:sqlite` 磁盘库，WAL，AMD/Windows 单机）。

#### 不会坏的

| 操作 | 百万级 | 千万级 | 结论 |
| --- | --- | --- | --- |
| 主键查 | 0.005 ms | **0.040 ms** | ✅ 依然微秒级 |
| 单实体出边 | 0.005 ms | **0.140 ms** | ✅ |
| 单实体入边 | 0.005 ms | **0.260 ms** | ✅ |
| 递归 4900 层祖先链 | — | **4 ms** | ✅ 家谱深度不是问题 |
| `LIKE` 全扫 | 247 ms / 200 万 | **14 ms**? | 见下文陷阱 |

**一跳/二跳邻接查询在千万级仍为亚毫秒**，而这是本项目 90% 的查询形态。
这意味着**千万级不需要换数据库**。

#### 会变慢的

| 操作 | 耗时 | 评价 |
| --- | --- | --- |
| 类型 + 时间窗 `LIMIT 100` | **30 ms** | 可用，但接近交互上限（~50 ms） |
| 单类型 `COUNT(*)` | **88 ms** | 需缓存 |
| 时间轴分页（全类型） | **45 ms** | 需预计算 |
| `OFFSET 9000000` 深分页 | **713 ms** | ❌ 不可接受，必须改游标分页 |

#### 两个实测陷阱（与数据量无关，是设计错误）

**陷阱一：选择性为 0 的索引不如没有**

首次测试把全部记录都写成 `type='person'`，结果复合索引 `(type,valid_from)`
反而**比不建更慢**（1950 ms → 2833 ms），因为索引扫到全部行。
重新造了带选择性的数据（5/8 是 person）后才得到 30 ms 的真实值。

→ **教训：索引效果取决于值分布，基准测试必须用真实分布。**

**陷阱二：`OFFSET` 深分页线性变慢**

`LIMIT 10 OFFSET 9000000` 要 **713 ms**——SQLite 必须先跳过 900 万行。
这在百万级（~70 ms）尚可忽視，千万级就不是了。

→ **必须改为游标分页**：`WHERE (valid_from,id) > (?,?) ORDER BY valid_from,id LIMIT 100`

#### 写入耗时（不可忽视）

| 规模 | 无索引插入 | 加一个复合索引 |
| --- | --- | --- |
| 1,000 万实体 | **55 s** | — |
| 1,000 万实体（带选择性） | **268 s** | 建 `(type,valid_from,valid_to)` 索引 **11 s** |
| 800 万边 | **280 s** | — |

**全量重建从百万级的 ~11 s 变成千万级的 ~5–10 分钟。**
P3 阶段的「全量重建，不增量」假设在千万级不再成立——
要么接受分钟级重建，要么加增量。

### 9.8 家谱图查询：复杂递归的实测与陷阱

需求：给一人，向上向下各数 5 代，并包含兄弟姐妹、叔伯、侄辈。

#### 结论

| 场景 | 耗时 | 节点数 |
| --- | --- | --- |
| 200 万人 / 880 万边：上 5 + 下 5 代 | **0.80 ms** | 64 |
| 同上：兄弟姐妹 | 0.05 ms | 4 |
| 同上：完整家谱（上下5+兄弟+叔侄+配偶） | **0.85 ms** | 64 |
| 极端扇出 10、下 5 代 | 149.6 ms | 111,111 |
| 极端扇出 10、下 6 代 | 1,705 ms | 1,111,111 |

**正常家谱在千万级边下是毫秒级**——这个查询根本不需要性能优化。

但有两个写法陷阱会让它从 1ms 变成 26 秒。

#### 陷阱一：`predicate IN (...)` 会让优化器选错索引（慢 970 倍）

```sql
-- ❌ 7,582 ms
WITH RECURSIVE up(id,d) AS (
  SELECT ?,0 UNION
  SELECT e.object,up.d+1 FROM edges e JOIN up ON e.subject=up.id
  WHERE e.predicate IN ('father','mother') AND up.d<5
) SELECT count(*) FROM up;
```

查询计划为 `SEARCH e USING INDEX i3 (predicate=?)` —— 它先按谓词找**全部**
father/mother 边（190 万条）再与递归集合关联，而不是从 `up.id` 出发定位。

| 写法 | 耗时 |
| --- | --- |
| `predicate IN (...)` | 7,582 ms |
| `predicate='a' OR predicate='b'` | 8,147 ms |
| 无谓词过滤 | 3 ms |
| **`INDEXED BY i1` + 谓词过滤** | **2.45 ms** |

**规则：家谱递归一律写 `FROM edges e INDEXED BY i1`（按 subject 的索引）。**
不加提示时，只要写了谓词过滤，优化器就会选错。

#### 陷阱二：双向递归在一个 CTE 里会路径爆炸（慢 25000 倍）

```sql
-- ❌ 26,546 ms，返回 241,383 节点（实际只有 64 人）
WITH RECURSIVE t(id,dep) AS (
  SELECT ?,0
  UNION SELECT e.object,t.dep-1 FROM edges e ... WHERE t.dep>-5
  UNION SELECT e.subject,t.dep+1 FROM edges e ... WHERE t.dep<5
) SELECT count(DISTINCT id) FROM t;
```

`UNION` 按 `(id,dep)` 去重，同一节点在不同 `dep` 下被视为不同行，
祖先链上的节点被反复向下扩展。实测各层均为 12–13 万，是**路径数而非人数**。

**正确写法：两个独立 CTE 再合并（1.05 ms，64 节点）**

```sql
WITH RECURSIVE
 up(id,d) AS (
   SELECT ?,0 UNION
   SELECT e.object,up.d+1 FROM edges e INDEXED BY i1 JOIN up ON e.subject=up.id
   WHERE e.predicate IN ('father','mother') AND up.d<5),
 dn(id,dep) AS (
   SELECT ?,0 UNION
   SELECT e.subject,dn.dep+1 FROM edges e INDEXED BY i2 JOIN dn ON e.object=dn.id
   WHERE e.predicate IN ('maleChild','daughter') AND dn.dep<5)
SELECT id FROM up UNION SELECT id FROM dn;
```

#### 完整家谱图查询（可直接用）

```sql
WITH RECURSIVE
 up(id,d) AS (SELECT ?,0 UNION SELECT e.object,up.d+1
   FROM edges e INDEXED BY i1 JOIN up ON e.subject=up.id
   WHERE e.predicate IN ('father','mother') AND up.d<5),
 dn(id,dep) AS (SELECT ?,0 UNION SELECT e.subject,dn.dep+1
   FROM edges e INDEXED BY i2 JOIN dn ON e.object=dn.id
   WHERE e.predicate IN ('maleChild','daughter') AND dn.dep<5)
SELECT id FROM up UNION SELECT id FROM dn
UNION SELECT s.subject FROM edges s INDEXED BY i2
  WHERE s.object IN (SELECT object FROM edges INDEXED BY i1
                     WHERE subject=? AND predicate='father')
    AND s.predicate IN ('maleChild','daughter')      -- 兄弟姐妹
UNION SELECT sp.object FROM edges sp
  WHERE sp.subject=? AND sp.predicate='spouse';      -- 配偶
```

实测 0.85 ms / 64 节点（200 万人 / 880 万边库）。

#### 必须限深

扇出 10 的家谱，下 5 代 11 万人、下 6 代 111 万人。
**家谱视图必须强制 `depth` 上限并默认 5**，否则一个「查看全部后代」就能把浏览器拖死。
这不只是性能问题——真实家谱里确实有人在某代有几十个子女。

#### 现有数据的真实度数

实测 12 万个实体分片：

| 指标 | 出度 | 入度 |
| --- | --- | --- |
| 中位 | 1 | — |
| P90 | 2 | 3 |
| P99 | 4 | 5 |
| 最大 | 29 | 13 |

度数极小，所以家谱查询的实际耗时比上面的压力测试还低。

### 9.9 如果真到几千万，需要哪些大改动

按「改动量 × 必要性」排序。**前两项几乎肯定要做，后两项看情况。**

### 改动 1：分页改游标（必做，成本低）

```sql
-- 现在（OFFSET 713 ms）
SELECT * FROM entities ORDER BY valid_from LIMIT 100 OFFSET 9000000;
-- 改后（恒定 ~0.1 ms）
SELECT * FROM entities
 WHERE (valid_from, id) > (?, ?)
 ORDER BY valid_from, id LIMIT 100;
```

前端接口从 `?page=N` 改为 `?after=<cursor>`。
**这是 API 形状变更**，最好在 P3 建库时一次做对，否则以后前端要改两遍。

### 改动 2：热点查询预计算（必做，成本中）

| 查询 | 千万级实测 | 对策 |
| --- | --- | --- |
| 单类型 `COUNT(*)` | 88 ms | 建 `stats` 表，写入时维护 |
| 时间轴分页 | 45 ms | 预生成分页索引文件（现有 `chrono.json` 思路，但分片） |

具体：多一张 `counts(type, bucket, n)` 表，每次 build 后一次性算好。

### 改动 3：raw 层分库/分区（看情况）

千万实体对应的 raw 约 **10–20 GB**（按当前 1,774 MB / 247 万行推算）。

- 单文件 JSONL 仍可读，但**全量哈希链验证**从 12.8 s 变成 **~2 分钟**
- 建议：按来源分文件，链也按来源分（已经是这样）；验证支持 `--source=cbdb` 单源校验

### 改动 4：换数据库（最后才考虑）

**只有当以下任一成立时才需要**：

- 多人**同时写入**（SQLite 单写者锁）
- 需要跨机器水平扩展
- 查询模式变成大量多跳图遍历（当前 90% 是一跳）

**千万级单机只读/单写者场景，SQLite 完全够。**
把 1800 万行换成 Postgres 只会换来运维负担，换不来体验提升。

若真要换，**SQLite 的 schema 可以几乎原样搬过去**（除了 `TEXT` vs `VARCHAR`），
这是坚持用标准 SQL 写查询的理由。

### 不需要改的

| 直觉上觉得要改 | 实测 |
| --- | --- |
| 「千万级要换图数据库」 | 一跳 0.14 ms，图库优势在深遍历，本项目用不上 |
| 「JSON 分片存不下」 | 分片数量不变（每片行数固定），只是片数变多 |
| 「哈希链撑不住」 | 247 万条 12.8 s；千万条约 1 分钟，可接受 |
| 「递归查询会爆」 | 4900 层链 4 ms |

### 现在就该做的最小预留（成本≈零）

即使不确定会不会到千万级，以下三件事**现在做成本几乎为零，以后省很大**：

1. **所有列表查询从一开始就用游标分页**，不要 `OFFSET`
2. **查询只写标准 SQL**（不用 SQLite 特有语法），保留换库可能
3. **`counts` 表从第一天就建**，即使百万级用不上

## 10. 完整性与防篡改

### 10.1 需求

原始语料一旦入库就必须能证明「未被改过」。这不是防黑客，是防**自己**：
迁移脚本写错、批量修复误伤、索引倒灌（历史上真发生过，5269 个实体被写成空壳）。

### 10.2 三层机制

#### 第一层：每条记录的 `contentHash`

```jsonc
{
  "rawId": "raw:cbdb-BIOG_MAIN-100001",
  "contentHash": "sha256:...",          // 对 canonical(payload) 的哈希
  "capturedAt": "2026-10-20T10:00:00Z" // 录入/抓取时刻，必填
}
```

能发现单条被改，但不能发现**整条记录被删除或替换**（因为新记录自带自洽哈希）。

#### 第二层：哈希链（append-only log）

每个来源维护一条链，每条记录的哈希包含上一条的哈希：

```
hash[i] = sha256( hash[i-1] || canonical(record[i]) )
```

```jsonc
{
  "rawId": "raw:cbdb-BIOG_MAIN-100001",
  "prevHash": "sha256:...",
  "recordHash": "sha256:..."
}
```

- 删改中间任何一条 → 后续全部哈希对不上
- 验证成本：重新算一遍全链

**实测成本**（20 万条）：

| 方案 | 耗时 | 247 万条推算 |
| --- | --- | --- |
| 仅单条 `contentHash` | 721 ms | ≈ 8.9 s |
| 哈希链 | 1,029 ms | **≈ 12.8 s** |

**哈希链只比单条哈希慢 42%，完全可接受。** 值得做。

#### 第三层：外部锚点（可选）

定期把链头的哈希发布到不可控的地方（git 提交、公证、公开时间戳服务）。
这样连「整条链被重建」也能被发现。

**本项目建议**：把链头哈希写入 git 提交信息即可。成本为零，且提交历史本身
由 git 保证不可篡改。

### 10.3 录入日期：`capturedAt` vs `occurredAt`

这两个必须分开，不能混：

| 字段 | 含义 | 例子 |
| --- | --- | --- |
| `capturedAt` | **系统录入/抓取时间**。自动生成，不可手填 | `2026-10-17T03:06:56Z` |
| `occurredAt` | **原始文献自身的时间**。未知则 `null` | 《明史》成书于 1739 |
| `accessedAt` | 网页实际访问时间（用于证据节点） | 可以与 `capturedAt` 相同 |

**`capturedAt` 由系统注入，不接受调用方传入。** 这与 `entity_writer` 的
`createdAt` 一致。

### 10.4 锁定与链的关系

```jsonc
{
  "locked": { "at": "...", "by": "user:me", "recordHash": "sha256:..." }
}
```

锁定 = 把当时的 `recordHash` 写下来。之后任何人若改了内容，
哈希对不上，`verify_chain` 会报错并指出是哪一个 `rawId`。

### 10.5 验证工具

`tools/raw/verify_chain.js`：

```
$ node tools/raw/verify_chain.js
✓ cbdb/BIOG_MAIN     660,311 条，链完整
✗ cbdb/ALTNAME_DATA  第 4,821 条 recordHash 不匹配（raw:cbdb-ALTNAME_DATA-9821）
```

**归入 `npm run check`**：链断即测试失败。这样哈希链就不只是一种「设计」，
而是每次提交都会被检查的硬约束。

## 11. 风险与对策

| 风险 | 对策 |
| --- | --- |
| raw 层体积膨胀 | 实测六表 JSONL 未压缩约 **1,774 MB**；gzip 后**实际落盘 290 MB**（实测压缩率 16.4%，496 文件）。比预估的 220 MB 高 32%——早先 12.4% 的估算是按短行样本推的，BIOG_MAIN 的长文本字段拉高了总体积。文件级 gzip 足够 |
| 搬运器重复执行产生重复 raw | `rawId` 由 `source + sourceKey` 决定，天然幂等 |
| 已锁定的 raw 需要修正 | 新增记录 + `supersedes`，旧记录保留 |
| SQLite 与 JSON 不一致 | P3 阶段做逐条对照；不一致即失败 |
| 视图层重建破坏现有功能 | 新旧并存，`site/` 保持可用直到新版通过验收 |
