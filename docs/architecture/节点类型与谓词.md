## 1. 节点类型：5 → 8

### 1.1 现有 5 类

| 类型 | 定义 | 数量 |
| --- | --- | --- |
| `person` | 人物 | 486,786 |
| `organization` | 组织、国家、政党、机关、报社 | 67 |
| `event` | 事件 | 22 |
| `thing` | 可触摸的载体（报纸、网站） | 6 |
| `evidence` | 证据节点，指向 `thing` 载体 | 111 |

### 1.2 新增 3 类

#### `office` —— 职位/官职

**为什么必须有独立类型**：任职是 `(人, 职位, 时段)` 三元组。职位不是组织——
「知縣」是职位，「国務院」是组织。混进 `organization` 会让
`memberOf`（成员）与 `holdsOffice`（任职）语义混淆，而这两者在数据里都有。

CBDB 规模：`OFFICE_CODES` 34,079 条，实际被任职使用 12,932 个。

```jsonc
{
  "id": "office:cbdb-1234",
  "name": "知縣",
  "type": "office",
  "external": { "cbdbOfficeId": 1234 },
  "provenance": [ ... ]
}
```

> 无 `props`（§5.4 已删），无 `validFrom`——存续期是边，不是字段（§2.5）。

#### `work` —— 作品

书、文章、画作、奏折、律法。

**为什么不能并入 `event`**：`work` 有「作者」（person → work），`event` 有「参与者」
（person → event）。合并后这两个谓词的 domain/range 无法区分作者的与参与者。

```jsonc
{
  "id": "work:local-000001",
  "name": "明史",
  "type": "work",
  "external": { },
  "provenance": [ ... ]
}
```

#### `place` —— 地点

籍贯、任职地、事件发生地。

**现状**：只能用 `literal` 存（`birthplaceOf` 的宾语是字符串）。这导致
「所有湖北人物」这类查询无法实现——字符串没有包含关系。

```jsonc
{
  "id": "place:cbdb-12345",
  "name": "湖北",
  "type": "place",
  "external": { "cbdbAddrId": 12345 },
  "provenance": [ ... ]
}
```

### 1.3 为什么不合并为「抽象概念」

上一轮讨论过的取舍，此处定稿：

| | 合并 | 分开 |
| --- | --- | --- |
| 类型表 | 少 3 行 | 多 3 行 |
| 判断「这是职位还是书」 | **需边模式推断，不可索引** | `type='office'`，一步 |
| `author` vs `holdsOffice` | domain 无法区分 | 各自明确 |

**类型表成本 ≈ 0，边模式推断成本 = 每条查询。**

若将来需要「所有抽象事物」的统一视图，在**第 3 层**做联合查询——那是视图层的职责，
不该污染第 1 层。

## 2. 时间语义

> **本节推翻了此前「时段只放节点」的设计**。记录推翻理由与代价，
> 避免以后有人觉得「放节点更简单」又改回去。

### 2.1 时间属于断言，不属于事物

早先方案把时段放在节点上，让任职实例成为节点（589,825 个），边永远不带时间。
理由是「检索只有一个时间过滤点」。**这个理由是错的**，它偷换了问题：

- 「某人活了 1950–2020」是**事物**的属性
- 「某人 1995–2000 任某职」是**断言**的属性

同一对实体之间的关系可以**分阶段存在**：同一人两次任同一职位是两个不同时段。
把这些塞进节点，等于宣称「这个人一辈子只有一个任职时段」——这是假的。

**定则：节点存自身存续区间，边存关系本身的起止。查询时实时求交。**

预先算好交集是诱人的，但那意味着日后精确了某个卒年，所有相关边都要重算。
**原始事实分开存，交集是查询的产物。**

### 2.2 谓词的时间性：三档

时间性是**基础原语**的属性（§8.4），路径继承最弱成员：

| `temporality` | 语义 | 基础原语 |
| --- | --- | --- |
| `persistent` | 一旦成立永久成立，与端点存续无关 | `father` `mother` `son` `daughter` `brother` `sister`、朋友、荐举、出生地、作者、主题、见于/记载、载于/载有 |
| `concurrent` | 要求两端在 T 时刻都存在才成立 | `husband` `wife` `concubine`、同僚、所属组织、任职于、上级/下级组织、控股、前身/后继、参与事件、发生地、相关事件、前置/后续事件、户籍、老师/学生、出版/出版方 |
| `attribute` | 属性快照，不参与时间切片 | 性别、民族、学历、出生时间、逝世时间、存在时间、开业/解散日期 |

**路径的 `temporality` 取最弱成员**（`concurrent` 弱于 `persistent`）：
岳父 = `wife` + `father`，含 `concurrent` → 婚姻终止后岳父关系是否成立需显式标注。

**为什么不用「两端各一个 `endsOn` 布尔」**：两端独立标注只在「师生」一处有正收益
（老师去世仍是学生的老师，学生去世则关系消失），其余都能被三档表达。
若将来真出现大量「两端行为不同」的谓词，再引入 per-end 覆盖。

**为什么 `attribute` 单独成档**：这些谓词的客体是字面值，没有「存续」概念。
「出生时间」本身就是时间，「性别」终身不变，「学历」理论上会变但 CBDB 无年份数据。
**它们的精度局限要写进文档，不要假装有精度。**

### 2.3 时间切片：一条边在 T 时刻成立的条件

```
persistent:  边.validFrom <= T <= 边.validTo
concurrent:  边.validFrom <= T <= 边.validTo
             且 主体在 T 时刻存在
             且 客体在 T 时刻存在
attribute:   恒成立（不参与切片）
```

「主体在 T 时刻存在」来自该节点自己的存续期，**不来自任何默认推断**。

### 2.4 默认规则覆盖不了的三种情况

任何默认规则都会在这三种情况下出错，所以 **边的显式时间永远优先于默认推断**：

**① 遗腹子**：父亲在子女出生前已死。若机械套用「两端必须同时存活」，
所有遗腹子关系会被静默删除。这是真实史实，不是数据错误。

**② 过继**：血缘父与养父并存，同一人有两条 `father` 边。

**③ 流亡政府、失去宣称**：组织并非只有「成立–灭亡」一次状态转换。
1949 年成立的政权可能在 1949–1972 处于流亡状态、之后另计。
这类转换**必须记录转换时刻与原因事件**，不能用单一 `dissolvedOn` 表达。

因此：**`concurrent` 的「两端存在」是默认兜底，不是硬约束。**
边若显式给出 `validFrom`/`validTo`，以显式值为准。

**派生结论：生死不作为人物的必填段。** 若要求每人必须有生卒，
上述三种情况全都无法录入。

### 2.5 存续期：权威在边，节点上是缓存

节点的存续期（人物生卒、组织成立–解散）本身应当是**边**
（`birthDate`/`deathDate`/`existedDuring` 谓词已存在），不是节点字段。

但时间切片查询要判定每个节点的存续期，若存续期要遍历边，**索引无法预计算**，
性能会崩。因此折中：

```jsonc
// 节点上的派生缓存，可重建
"lifespan": { "from": 2415021, "to": 2437001, "srcHash": "sha256:..." }
```

**规则**：

1. **权威在边**。`lifespan` 是派生值，丢了可重建。
2. **缓存只读不写**。任何代码不得直接改 `lifespan`，只能「写边 → 触发重算」。
3. **带版本戳**。`srcHash` 是来源边的内容哈希，用于判定是否过期。
4. **写边同事务重算**。写 `birthDate`/`deathDate` 边的路径必须在同一事务内更新缓存。
5. **`npm run check` 校验一致性**。缓存与边不符即失败，不允许静默漂移。

### 2.5.1 宾语何时建实体，何时用 literal

「每个连线都是两个实体 + 一个谓词」**不完全正确**。正确的判定只看一个问题：

> **宾语是一个独立可识别、可能被别人也引用的对象吗？**

| 宾语性质 | 形式 | 例子 |
| --- | --- | --- |
| 独立实体，有自己的一生/属性 | 谓词三元组 | 夫妻、父子、任职于某机构、参加某事件 |
| 只是一个值 | literal 边 / props | 生卒日期、性别、字、号、异体字 |

**为什么日期不建实体**：建一个 `date:1104` 节点毫无意义——它没有属性、
没有边、不能单独被检索，只是把三元组变成四元组。日期作为**值**参与的是
区间比较（§2.6），不是关系遍历。

**为什么字/号也不建实体**：`徐宗卿(字)` 的「字」不是一个人或物，
它是名字的一种形式。建实体造出 5 万个空壳节点，而 `aliases` 数组
本来就是为这个设计的。

**反过来，名字括注里的「趙禎」必须建边**：它是个人，有自己的记录，
而且「趙禎的妻子是谁」是一个真实的反向查询需求。把它塞进
`props['名字括注'] = '趙禎妻'` 就把三元组压平成了一个字符串。

判定规则的实质：**literal 只能装「不能作为关系起点或终点」的东西。**
一个值如果将来可能被单独拿出来问「还有谁和它有关」，它就不是 literal。

### 2.6 精度与「无测度的点」

- 年份精度存 `validFrom = validTo = JDN(该年起始)` + `precision: 'year'`
- 检索时按 `precision` 放宽窗口
- **不虚构起止日**：「清 1644–1911」就是区间，不换算成具体某天
- 只有死亡日期时只记死亡，不反推出生

#### 2.6.1 实施：模糊生卒（已落地）

**「只知道大致时期」写日期区间，不写朝代标签。** 前者是可切片、可检索的事实，
后者是推导值冒充原始记录。

CBDB 在 `BIOG_MAIN` 里自己标了不确定性，对应 `YEAR_RANGE_CODES`：

| `c_by_range`/`c_dy_range` | 语义 | 写入 props 的形式 |
| --- | --- | --- |
| `0` | during（恰好） | `1104年` |
| `2` | around（约） | `约 1104年 ± 30` |
| `-1` | before（之前） | `1104年之前` |
| `1` | after（之后） | `1104年之后` |

± 半径取 30 年（`RANGE_RADIUS`）。当前落盘量：出生 2,489 条、逝世 15,705 条带 ±，
另有 228 条开口区间。

**解析链路上两个必须同时存在的环节**（缺一个就静默失配）：

1. `parseFuzzy` 必须认「前N年」——导入器写出的正是这种形式（`formatYear` 的 BCE 写法）。
   只认「公元前」会把 `约 前300年 ± 30` 读成公元 300 年。
2. `lifespanFromProps` 必须把文本传给 `birthFuzzy`/`deathFuzzy`。只传字符串时
   `lifespanRange` 只调 `parseYearMonth`，带 ± 的文本整体变成 null。

**开口区间不能压成点**：`parseYearMonth` 对「1104年之前」必须返回 null，
否则会取到前缀数字 1104，把「不晚于 1104」读成「活到 1104」。
由 `parseOpenRange` 转成单端区间，`source: 'open'` 让 `formatRange` 显示
「1104年 之前」而不是「? – 今」。

**双端区间显示起止，不显示中点**：`formatRange` 只在某一端缺失时才用
`mid ± uncertainty`。否则「947 – 约1004」会退化成「约 975年」，生卒年从时间线上消失。

## 3. 谓词设计

### 3.1 现有 55 个原语

已在 `src/predicates/registry.js` 注册。`domain`/`range`/`inverse`/`aliases`
骨架保留（理由见 `分层架构重构方案.md` §4.4）。

### 3.2 每个谓词的字段

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `key` | 是 | 英文标识，唯一 |
| `label` | 是 | 默认显示名 |
| `domain` | 是 | 主体类型，竖线分隔多类型 |
| `range` | 是 | 客体类型 |
| `temporality` | 是 | `persistent`/`concurrent`/`attribute`，见 §2.2 |
| `aliases` | 是 | 同义词数组，可为空 |
| `negatable` | 是 | 是否允许 `/非` |
| `inverse` | | 反向谓词 key（与 `symmetric` 二选一） |
| `symmetric` | | 反向即自身 |
| `subjectGender` | | 主体性别硬约束 |
| `genderFamily` | | 性别族标记（「儿子/女儿」互斥检索） |
| `usesRole` / `usesPlace` | | 边是否可用 `role`/`place` 字段 |
| `description` | | 一句话说明 |

**删除 `qualifiers`**：5 个值里 `source` 在 55 个谓词中 100% 出现（等于没约束），
`dates` 42/55、`note` 49/55（实际是默认允许），真正有区分度的只有 `role`（10 个）
与 `place`（1 个）。改用两个显式布尔。

**删除 `aliasesNote`**：只出现 1 次，并入 `description`。

### 3.3 字段瘦身已在 §8 定案

现有 13 个字段中，`negatable`/`symmetric`/`subjectGender`/`genderFamily`
**全部是为血缘关系设计的**，55 个谓词里只有 5–10 个真用到。
经语言学重审（§8）与数据验证，定案瘦身到 10 个，`inverse`/`subjectGender`/`genderFamily` 删除，
改用 `/反` `/男` `/女` 修饰符。

## 4. `tags` 字段：删除

### 4.1 现状

实测 3,000 个实体：`tags` 100% 存在，但**去重后只有 3 种值**——
`年代不详`（2,146）、`隋唐及以后`（853）、`organization:local-000099`（1 个 id 残留）。

### 4.2 决定：整字段删除

**所有关系与分类都走谓词**，不留任何自由字符串分类字段。

| 现状 | 改后 |
| --- | --- |
| `tags: ["年代不详"]` | 无任何边。缺失即未知，不造值 |
| `tags: ["隋唐及以后"]` | 删除。时代从 `birthDate`/`deathDate` 推导（§2.6） |
| `tags: ["organization:local-000099"]` | 对应关系边 |

理由：`tags` 既存分类词又存 id，两种语义混在一个字符串数组里，
且不参与搜索、不被 `check_references` 覆盖——是个法外之地。

#### 4.2.1 `era` 谓词曾被引入，后又删除（已实施）

第一版实现把朝代词改成 `era` 边（person → literal）。**这是错的**，已全部删除：

- 它没有自己的原始记录。CBDB 导入器按年份分档生成（先秦/秦/两汉/三国/晋/南北朝/
  隋唐及以后），而最后一档吸收了 589 年以后的**所有人**。
- 实测 234,871 条 `era` 边中 **228,903 条（97.5%）取值是「隋唐及以后」**——
  这不是朝代，是「不知道」穿了件朝代外衣。正是 §4 开头禁止的那类假值。
- CBDB 自己的 `c_by_range`/`c_dy_range`（before/during/after/around）被完全丢弃，
  而它们才是真实的精度标注（`c_dy_range` 有 23,239 条非空）。

**正确做法**（§2.6）：只知道大致时期的人，写**带区间的生卒日期**。
「是战国人」→ `birthDate: 约 前300年 ± 30`，而不是一条指向「战国」抽象节点的边。
时代分类是查询时从日期推导的产物，永不入库。

#### 4.2.2 名字里的括注：转成边，不存 props（已实施）

CBDB 有 50,638 行把关系写进名字：`郭氏(趙禎妻)`、`雷氏(孛朮魯遠妻)`。

曾一度剥离后存进 `props['名字括注']`。**那仍然是错的**：关系是边，不是属性。
存在 props 里等于把三元组压平成一个字符串，「趙禎的妻子是谁」永远查不到。

正确做法（按 §2.5.1 判定）：括注里的「趙禎」是人，所以它是边。

| 括注形式 | 处理 |
| --- | --- |
| `郭氏(趙禎妻)` | 郭氏 `-husband->` 趙禎（`husband` 主体是妻，§8.5） |
| `趙氏(趙晉女)` | 趙氏 `-father->` 趙晉 |
| `謝琳英伯母` | 剥掉修饰词 `伯`，查「謝琳英」；修饰词存 `role` |
| `趙佶女15` | 末尾序号是排行，存 `role:'第15'` |
| `徐宗卿(字)` | 字/号是名字注记，并入 `aliases`，**不建实体** |
| `瞿祐(佑)` | 异体字，同上 |

实测结果：50,079 条中，21,522 条新建边、22,261 条已有同边（KIN_DATA 已覆盖）、
6,255 条无法判定。后者主要是「查无此人」——CBDB 只记了妻子，没给丈夫建档，
或名字带 `?` 占位符。**按 §1 不猜，保留原状并记 WARN。**

关系修饰词（继/庶/嫡/生/伯/祖/乳…）不是新谓词，是边的 `role`：
`繼母` = `mother{role:'繼'}`。这避免了为每个修饰词新增一个 key。

### 4.3 连带影响：会打断发布筛选

`build_index.js` 的发布判定（1900+ 现代人物）可能依赖 `tags`。
**删除前必须改走 `birthDate` 边**，否则发布树会空。

## 5. 节点骨架字段

### 5.1 原则

**只有「该类节点必然拥有、且不属于关系」的字段才留在节点上。**
其余一律外接为谓词与连线。

### 5.2 必备

| 字段 | 理由 |
| --- | --- |
| `id` | 身份，不派生自名字 |
| `type` | 决定其余一切 |
| `name` | 无名实体无法显示或引用；**必须原子**，不含括注/序号 |

**就这三个，不能再多。**

### 5.3 骨架但可空

| 字段 | 说明 |
| --- | --- |
| `aliases: []` | 名字的集合，不是关系 |
| `external: {}` | 来源键（如 `cbdbId`），用于去重与溯源 |
| `provenance: []` | 节点自身出处数组，见 §6 |
| `lifespan` | 派生缓存，见 §2.5 |

### 5.4 删除的字段

| 字段 | 实测填充率 | 删除理由 |
| --- | --- | --- |
| `props` | 32% 非空，仅 4 个键 | 4 个键全部可外接为谓词；留着会变成第二个 `summary` |
| `tags` | 100% 但只有 3 种值 | 见 §4 |
| `wikiUrl` | **0%** | 永远是 null 的字段是负债 |
| `summary` | **0%** | 同上 |
| `sources` | ~0% | 已迁到证据节点 |

### 5.5 `props` 外接对照

| 现在的 props | 改后 |
| --- | --- |
| `性别` | `gender` 边 → literal（谓词已存在） |
| `民族` | `ethnicity` 边 |
| `学历` | `education` 边 |
| `出生年月` | `birthDate` 边 |
| `逝世时间` | `deathDate` 边 |
| `生卒`（散文） | 拆成上述两条边 |
| `史料注记` | 证据节点 |

**`birthDate`/`deathDate` 谓词已存在，机制已经具备。**

### 5.6 不拆姓氏与名字

`name` 保持原子字符串，**不拆 `surname`/`givenName`**：

1. 中文名拆分无定义边界（欧阳修 vs 欧姓，复姓表无法穷举）
2. 拆了也查不出东西——「查姓欧的人」是**索引功能**，不是字段结构
3. 拆分后仍需拼回原名，白增一层出错机会

若来源明确给出（CBDB 有 `c_surname_chn`/`c_mingzi_chn`），可加**可选**的
`nameParts`，但不作为检索依赖。

## 6. 引用与溯源

### 6.1 三层：节点出处、边出处、证据节点

| 位置 | 记什么 | 例子 |
| --- | --- | --- |
| **节点** `provenance[]` | 这个实体**本身被记载于**哪里 | 张伟 出自 `raw:cbdb/BIOG_MAIN/100001` |
| **边** `provenance[]` | **这条断言**出自哪里 | (A,father,B) 出自 `raw:cbdb/KIN_DATA/59224\|86216\|-10000` |
| **证据节点** | **一份文献**的完整元信息 | 《明史》卷一百二十三 |

**节点出处不能由边推导**：一个只有名字、没有任何边的实体仍然真实存在过
（现有 140,848 个空壳人物正是这种情况）。

**边出处不能由节点出处推导**：同一个人的生年出自 `BIOG_MAIN`，
父子关系出自 `KIN_DATA`，是不同的原始记录。

### 6.2 引用结构（`provenance` 数组元素）

```jsonc
{
  "rawRef":   "raw:cbdb/KIN_DATA/59224|86216|-10000",
  "locator":  { "pages": "45" },
  "quote":    "（原文摘录）",
  "reason":   "c_kin_code=-10000 映射为父",
  "commitId": "c-000123"
}
```

五个字段，**没有一个是冗余的**：

| 字段 | 能否由他处推出 |
| --- | --- |
| `rawRef` | 不能。第 0 层唯一定位，必填 |
| `locator` | 不能。文献载体内部的卷/页/行，可空 |
| `quote` | 不能。原文摘录，必填非空 |
| `reason` | 不能。凭什么推出这条断言，可空 |
| `commitId` | 不能。指向提交表，必填 |

**为什么 `rawRef` 与 `locator` 不重叠**：`rawRef` 是**第 0 层**定位
（哪张表哪一行 / 哪个文档第几段），`locator` 是**文献载体内部**位置
（古籍的卷/页/行）。CBDB 一行可能记载「《明史》卷一百二十三，页四十五」——
前者是数据库位置，后者是原始文献页码，两者都要。

**若 `locator` 也存数据库位置就会与 `rawRef` 重复**，一处改了另一处会不同步。
这条在讨论中被明确纠正过。

### 6.3 被删掉的字段及理由

| 字段 | 删除理由 |
| --- | --- |
| `evidenceId` | 冗余派生值。由 `raw_records.evidenceId` 表 join 得到，不该在 800 万条边上各存一份 |
| `accessedAt` | 可由 `commitId → commits.at` 推出 |
| `by`（作者） | 由 `commitId → commits.author` 给出 |
| `confidence` | 三档无定义阈值，会变成人人填 `medium` |
| `note` | 属于证据节点（描述文献本身的毛病），不属于每条引用 |

### 6.4 规则

- `provenance` **必须是数组且非空**。空数组 = 无出处断言，正是要消灭的东西。
- 支持多出处（CBDB 中同一关系可能被 `KIN_DATA` 与 `ASSOC_DATA` 双份记载）。
- **`quote` 必填非空**。空字符串等于没出处——现有 111 条证据 `excerpt` 全空就是教训。
- `check_references.js` 必须校验每个 `rawRef` 在 `raw/` 中真实存在。

#### 6.4.1 实施：边级出处（已落地）

出处挂在**边的每次实例**上，不是挂在谓词定义上。「张三是李四的父亲」和
「王五是赵六的父亲」是同一种谓词、两处出处。

表结构无需改动：`provenance.scope` 早已支持 `'edge'`（见 `db_schema.js`
注释「scope='edge' -> target_id is an edge id」），只是从未写入过。

**数据流**：

```
KIN_DATA 一行
  → provenanceFromKinRow()   rawRef/quote/locator/reason
  → 分片 relations[pred] = [{ id, provenance }]
  → build_db: INSERT provenance (scope='edge', target_id=edgeId)
```

`rawRef` 用 `raw:cbdb/KIN_DATA/<personid>|<kin_id>|<kin_code>`——三元组能
唯一定位 KIN_DATA 的一行。

**`quote` 在 80% 的行上取不到原文**（`c_notes` 为空）。此时用「对源行字段的
直接重述」作为 quote（`c_kin_code=75（父） c_personid=… c_kin_id=…`）。
这不是编造引文：任何人拿 `rawRef` 都能核对这几个字段。空 quote 才是问题。

**`c_source=0` 不得写成 `sourceId`**。它在 CBDB 里对应一条叫「未知」的
`TEXT_CODES` 记录——不是一本书，是「没有记载出处」。写成 sourceId 会让
「这条断言出自哪本书」的答案变成一本叫《未知》的书。

实测：484,322 条边中 **437,372 条有出处（90.3%）**，零孤儿、零空 quote、
零空 rawRef。剩余 9.7% 是名字括注迁移建的边，源数据无对应 KIN_DATA 行。

**两个必须同时存在的开关**（缺一个就静默失效）：

| 开关 | 不传的后果 |
| --- | --- |
| `replaceRelations` | `Object.assign({}, rec, prev)` 让 prev 胜出，新出处永远写不进去，却报「更新 0 条」 |
| `dropProps` | 导入器删掉的字段（如废弃的 `名字括注`）永远留在磁盘上 |

`replaceRelations` **按谓词合并**而非整体替换：名字括注迁移建的边不在
KIN_DATA 里，导入器重跑不会重新产生，全替换会静默删掉 2 万多条边。

### 6.4.2 `quote` 对二手数据库保持原样，性质写在 `reason` 里

CBDB 不是文献，是把文献整理成字段的**二手数据库**。它没有句子可摘，
所以 `quote` 里是列名拼接：

```
c_birthyear=1873 c_by_nh_code=666 c_by_nh_year=11 c_deathyear=1959 c_dy_nh_code=0
```

这串东西对人不可读，但它**是可核验的**——拿 `rawRef` 去查
`raw/cbdb/BIOG_MAIN/120760`，`c_by_nh_code=666` 确实在那儿，
`NIAN_HAO` 表里 666 确实对应「清·同治」。

**不做的事**：不把它「翻译」成「清同治十一年生」。
那是解释，不是摘录；一旦翻译，就再也分不清哪部分是源数据、哪部分是
我们的理解。用户看到 `c_birthyear=1873` 至少知道这是库里的原始值。

**做的事**：在 `reason` 里说清楚这是什么。

| 位置 | reason 示例 |
| --- | --- |
| 实体级（BIOG_MAIN） | `出生年月,逝世时间；二手数据库摘录，非文献原文` |
| 边级（KIN_DATA，有文献） | `c_kin_code=182 → 長子；经 CBDB 转述，出处《宋史》` |
| 边级（KIN_DATA，无文献） | `c_kin_code=75 → 父；CBDB 未记文献出处` |

「经 CBDB 转述」不能省。`出处《宋史》` 读起来像我们直接查了《宋史》，
实际是 CBDB 声称它据《宋史》——前者我们能对原文负责，后者只能对
CBDB 的转述负责，而转述可能断章、可能错系。

同时 `evidence:cbdb` 的 `medium` 是 `database`，前端显示为「二手数据库」
（`MEDIUM_LABELS` 补了这一项；此前它不在枚举里，会露出裸英文 key）。

**后续网页类来源相反**：那些有真正的原文句子，`quote` 就放原文，
不需要这层说明——它本来就是一手材料。

### 6.4.3 `quote` 是原文副本，不是指针

**`quote` 存摘出来的原文本身，不是「去哪里找原文」的线索。**

划取只发生在**录入后台**一次：用户打开原文、划出句子、提交。
此后所有展示（详情页气泡、文献反查页、导出）都读 `quote`，
不再回原文。

理由：

1. **原文会消失。** 网页改版、数据库下线、古籍扫描件失效——
   只存链接的引用，几年后就是死链。存副本才能长期可核。
2. **回原文是有成本的。** 每次点开气泡都去抓一次网页，既慢又不可靠，
   而且会随对方服务波动。
3. **副本是审计依据。** 「这条断言凭什么」的答案应该是当时看到的那句话，
   而不是「现在那个网址上写着什么」。

代价是存储：一条 `quote` 通常几十到几百字。当前 810,813 条出处，
即使平均 100 字也只有 80MB 量级——远小于 `raw/` 的 292MB。

#### 两类文献的 `quote` 形态不同

| 类型 | `quote` 内容 | 例 |
| --- | --- | --- |
| **一手文献**（网页、报刊、档案、碑刻） | 原文句子 | 「……任政协第十三届全国委员会常务委员」 |
| **二手数据库**（CBDB 等） | 源记录的字段串 | `c_birthyear=1873 c_by_nh_code=666 …` |

二手数据库没有句子可摘——它把文献整理成了字段。此时 `quote` 放字段串
**是诚实的**：它准确表示「我们看到的就这些」，而不是伪造一句原文。
数据性质由 `reason` 说明（「二手数据库摘录，非文献原文」），
由 `evidence.medium = database` 结构化标注。

**不要求为 CBDB 的每条断言去找古籍 txt。** CBDB 声称「据《宋史》」，
我们能负责的范围是「CBDB 这么说」，不是「《宋史》确实这么写」——
后者需要真的读《宋史》，那是另一个量级的工作，且不属于当前阶段。

### 6.5 `locator`：按载体分型

`locator` 是对象，键受 `medium` 软约束（不是每种载体一个独立 schema 类型，
那样新增载体要改代码；软约束只改配置表）。

| `medium` | 允许的键 | 例子 |
| --- | --- | --- |
| `web` | `segment` | `{ "segment": "p3" }` |
| `book` | `volume`、`chapter`、`section`、`page`、`line` | `{ "volume": "123", "page": "45" }` |
| `database` | `pages`、`sourceId` | `{ "pages": "45", "sourceId": 62087 }` |
| `inscription` | `site`、`plate`、`line` | 碑刻 |
| `archive` | `fond`、`series`、`file`、`item`、`folio` | 档案编号 |
| `chronicle` | `year`、`reign`、`juan`、`entry` | 编年体 |

**古籍卷次存原文 + 规范化值双字段**：`{ "volume": "一百二十三", "volumeNorm": 123 }`。
只存规范化值会丢失原文写法；只存原文则无法排序检索。

### 6.6 证据节点

证据节点记录**一份文献的完整元信息**，是实体（可以有自己的边和属性）。

```jsonc
{
  "id": "evidence:local-000003",
  "type": "evidence",
  "name": "人民网人物资料 · cpc.people.com.cn/n1/...",
  "medium": "web",
  "rawRef": "raw:web/gov-5746205/doc",
  "url": "http://cpc.people.com.cn/...",
  "capturedAt": "2026-10-16T16:08:26.049Z",
  "note": ""
}
```

**删除** `documentedAt`（永远 null）、`reliability`（无数据源）、
`unresolved`（永远 false）、`excerpt`（迁到引用的 `quote`）。

`note` **留在证据节点**，不进 `provenance`：它描述「这份文献有什么毛病」，
不是「这条断言出自哪一行」。

### 6.7 只接受已落盘的引用

系统**不接受指向未抓取内容的引用**。任何 `rawRef` 必须能在 `raw/` 中找到。
网页类文献的 `capturedAt` 就是抓取落盘日期，**没有单独的「访问日期」概念**。

## 7. 提交溯源

### 7.1 为什么要它

版本号字符串只能回答「哪个转换器版本产生了这条边」，回答不了：
这条边是**哪次任务**改的、那次任务改了**哪些边**、被改过**几次**。

### 7.2 但不做完整 git

800 万边 × 每条 300 字节 = 2.4 GB/次快照。存 diff 则需实现 diff 引擎、
合并逻辑、分支——那是重建一个 git，与本项目目标无关。

### 7.3 轻量方案：提交表 + 边上存 `commitId`

```jsonc
// data/commits/commits.jsonl  只增不改
{ "commitId": "c-000123",
  "at": "2026-10-20T10:00:00Z",
  "author": "cbdb-biog@1.0.0",
  "message": "CBDB 六表全量导入",
  "parentId": "c-000122",
  "stats": { "edgesAdded": 1599800, "nodesAdded": 486786 },
  "anchor": "sha256:..."
}
```

`author` 可以是脚本版本（`cbdb-biog@1.0.0`）或人工（`human:alice`）。

**开销**：8 字节 × 800 万边 = **64 MB**，而非 2.4 GB。

**收益**：

```
边 → commitId → 该次提交的 raw 链头 → 247 万行原始记录
```

任意一条边都能追到产生它的原始数据状态。这是字符串版本号做不到的，
也是引入 commit 的真正理由——**不是为版本控制，是为溯源闭环**。

### 7.4 规则

- **人工编辑也生成 commit**。不搞脚本/人工两套时间线。
- **被修改的边不留历史**：主存储只存当前版本，旧版本可选写入
  `data/audit/edge-history/` 冷档案。
- `anchor` 必须指 raw 层链头，且该链头可验证。

## 8. 谓词模型：从枚举到组合

> 谓词决定全网形态，也决定后续所有检索、关联分析与可视化的可执行性。
> 本节不靠推测，全部结论有实测数据支撑。

### 8.1 实测证据：现有设计已经漏出了什么

对全部 486,786 个实体扫 `relations`，共 51,818 条边、15 种谓词。其中
**26,891 个实体用了 6 种注册表里不存在的谓词**：

| 未注册谓词 | 实体数 | 病因 |
| --- | --- | --- |
| `wife` | 21,645 | 缺客体性别方向 |
| `stepMother` | 3,876 | 缺关系修饰（继） |
| `daughter` | 1,060 | 与 `femaleChild` 重复 |
| `concubine` | 165 | 缺名分 |
| `son` | 128 | 与 `maleChild` 重复 |
| `olderSibling` | 17 | 与 `elderBrother` 重复 |

抽样核实 `wife` 的方向：`王氏(person:cbdb-100128) → [person:cbdb-100129]`，
主体是女性、客体是其丈夫。**`wife` 的主宾方向与 `spouse` 相反。**

这说明：**手工枚举谓词必然漂移**。每来一个新词就补一个 key，
补到 55 个仍在漏，而漏掉的部分（2.1 万条）比已注册的总边数还多。

### 8.2 CBDB 自己是怎么做的：字母链

CBDB 的 `KINSHIP_CODES` 表有 488 行，其 `c_kinrel` 字段用的是
**结构化字母记法**，每个字母是代际/婚姻上的一步：

| 字母 | 关系 | 字母 | 关系 |
| --- | --- | --- | --- |
| `F` | 父 | `S` | 子 |
| `M` | 母 | `D` | 女儿 |
| `B` | 兄弟 | `Z` | 姊妹 |
| `H` | 丈夫 | `W` | 妻子 |
| `C` | 妾 | `A` | 姻亲 |

链式组合实测（全部来自 CBDB 源表，无手写）：

| `c_kinrel` | 中文 | 结构 |
| --- | --- | --- |
| `F` | 父 | 一步 |
| `FF` | 祖父 | 父之父 |
| `FFF` | 曾祖 | 父之父之父 |
| `SS` | 孙 | 子之子 |
| `DH` | 女婿 | 女儿之夫 |
| `WF` | 岳父 | 妻子之父 |
| `FBS` | 堂兄弟 | 父之兄弟之子 |

**这就是「符合语言表达逻辑」的答案**：关系不是 488 个词条，
而是 10 个基础步长的**路径组合**。中文「岳父」本身就是「妻子的父亲」这个路径。

### 8.3 覆盖率实测

KIN_DATA 全量 559,940 行，`c_kin_code` 实际用了 438 种：

| 类别 | 行数 | 占比 |
| --- | --- | --- |
| **单步**（`c_kinrel` 仅一个基础字母） | 412,943 | **73.7%** |
| **复合链**（多字母） | 146,987 | **26.3%** |
| 哨兵值（`[missing data]` 等） | 10 | 0.0% |

核心字母链去重后只有 **262 种**，且分布极度集中：

```
B 20.8% | S 20.1% | F 16.5% | H 5.3% | W 5.2% | FF 5.2% | SS 5.1%
M 4.4% | FFF 3.6% | SSS 3.5% | DH 1.6% | WF 1.5% | D 1.1% ...
                                —— 前 12 种覆盖 93.8%
```

**98.5% 的行可被基础字母链完全表达**。剩余 1.5% 是 `G-n`（直系祖先）、
`K-n`（同族长辈）、`F*`（非特定父）这类**语义本就模糊**的编码——
它们无法精确化成链，正好说明它们不应被强行塞进单一谓词。

### 8.4 结论：谓词分两层

**第一层：基础关系原语（原子，不可再分）**

**10 个单步关系，但只有 6 个是真正独立的**——因为父子/夫妻是同一关系的两个方向：

| 独立原语 | 字母 | 反向（`/反` 修饰符） | 理由 |
| --- | --- | --- | --- |
| 父 | `F` | 子 `S` / 女 `D` | 反向按客体性别分两支 |
| 母 | `M` | 子 `S` / 女 `D` | 同上 |
| 兄弟 | `B` | 兄弟 `B` | 主宾同构 |
| 姊妹 | `Z` | 姊妹 `Z` | 同上 |
| 夫 | `H` | 妻 `W` | 婚姻两端，性别对称 |
| 妾 | `C` | 夫 `H` | 特殊名分，非对称 |

> **实施修正（P5-5b）**：妾 `C` **没有**成为独立谓词。
>
> §8.4 把 `C` 列为原语是站在**字母链视角**（「某人的妾是 X」）。但本项目的边存的是
> 主体→客体且读法为「A 的 X 是 B」，所以 `A --concubine--> B` 只能读作
> 「**A 的妾是 B**」——A 是夫、B 是妾。
>
> 而实测 37 条带 `role:'concubine'` 的边全是「妾 → 其夫」：
>
> ```
> 郭氏(劉仁妾) --spouse{role:concubine}--> 劉仁
> ```
>
> 写成 `郭氏 --concubine--> 劉仁` 会读作「郭氏的妾是刘仁」——荒谬。
> 所以妾的身份用 `husband{role:'concubine'}` 表达，**不新设谓词**。
>
> 同理，`husband`/`wife`/`brother`/`sister` 四个新 key 都已落地；
> `elderBrother`/`youngerSibling` 因 `subjectGender` 看主体而 label 说客体（语义不自洽）已删除。

为什么`father` 的反向有两种（子/女），而 `brother` 的只有一种：
**中文的「子女」在宗法地位上不同，必须分开；而「兄弟」互为兄弟，不需区分。**
这不是性别修饰能达到的——「父亲的孩子」和「父亲的儿子」是两个概念。

#### 方向语义：从属视角，不是语言学主谓

这一点必须写死，否则整张图会反。注册表里 `father` 的 **label 是「父亲」**，
所以 `A --father--> B` 读作：

```
A 的父亲是 B          ← 正确（从属视角，与 label 一致）
A 是 B 的父            ← 错误（语言学主谓，与本项目所有代码相反）
```

**实证**（CBDB 源数据自身就是这么记的）：

```
30148 朱元璋 --135(W)-->  118451 馬氏(朱元璋妻)   female=1
30148 朱元璋 --182(S1)-->  67200 朱標            female=0  （长子）
```

`c_personid --c_kinrel--> c_kin_id` 读作「c_personid 的 c_kinrel 是 c_kin_id」。
这解释了 P5-5a 修复时的两个现象：

1. `D`（女兒）在**从属人物**上应映射为 `femaleChild`（「某人 的女儿是 X」），
   而不是 `daughter`。注册表里根本没有方向意义上的 `daughter`。
2. 早期怀疑 `split_relational_names.js` 把 `王氏(項某妻)` 的方向写反了——
   **实测否定**：`王氏 --spouse--> 項某` = 「王氏的配偶是項某」，正确。

**对反向的影响**：`A --father--> B` 的 `/反` 读作「B 的子女包含 A」，
客体性别决定显示「子」还是「女」。这不是两个谓词，是同一断言的两个视角。

查询“B 的子/女” = `father/反` + 客体性别筛选。

**第二层：路径（path），由基础关系组合而成**

任何复合关系表示为**有序的边序列**，不注册为新谓词：

```jsonc
// 岳父：配偶之父 —— path 每步都从上一个节点出发
{ "path": ["spouse", "father"], "label": "岳父" }
// 堂兄弟：父之兄弟之子
{ "path": ["father", "sibling", "maleChild"], "label": "堂兄弟" }
// 曾祖：父之父之父
{ "path": ["father", "father", "father"], "label": "曾祖" }
```

**每步语义**：从当前节点出发走一条边。所以 `path: ["father", "father"]` 读作
「我的父亲的父亲」，不是「我是某人的祖父」——与从属视角一致。

**边只存单步**。`A → B` 的 `father` 边加 `B → C` 的 `father` 边，
查询时用递归走成「祖父」。**不为派生关系建边**——那会导致同一事实存多份，
一处改了另一处不一致。

#### 8.4.0 `kin`（亲属）已删除

`kin` 与 `era`、`tags` 是同一类错误：**说不出具体关系时往这里塞一个宽泛标签**，
读起来像一条事实，实际什么也没说。

- CBDB 的 `A`（姻親）码就是典型：334 行「姻親」落成了 299 条 `kin` 边，
  而源数据自己都承认不知道是哪种姻亲（岳父？女婿？连襟？）。
- 复合路径（`SS`=孫、`WF`=岳父）本该由单步边组合得出（§8.6），
  早期实现却落成 11 万条 `kin` 边。
- 还有 527 条无出处的旧 `kin` 边，来自名字括注迁移。

**原则：有称呼就用称呼。** 父亲、母亲、兄、弟、夫、妻、子、女、姊妹——
每一个都是独立谓词。说不出的就不记，不造一个「亲属」兜底。

实施：
- `VAGUE` 集合补入 `A`（原先只有 U/G/K/P），姻親不再出边
- `SINGLE_STEP` 里模糊符号的 `key` 改为 `null`，不再是 `'kin'`
- `derivePredicate` 对复合路径/哨兵行返回 `key: null`
- `cbdb.js` 的 `|| 'kin'` 兜底改为 `null`（不建边）
- `ownedPredicates` 声明 `kin` 归导入器管，清掉磁盘上的历史边

结果：`kin` 边从 113,328 条降为 **0**，总边数 461,284 → 347,939。

#### 8.4.1 实施对齐：SINGLE_STEP 曾落后于本节（已修）

`cbdb_kinship.js` 的 `SINGLE_STEP` 表长期没跟上本节裁定，把 `B`/`Z` 归到
`sibling`、`H`/`W`/`C` 归到 `spouse`。后果是同一关系存两遍：

```
84,654 条 sibling  与  83,013 条 brother 指向同一对实体
51,217 条 spouse   与  30,295 条 husband 指向同一对实体
```

这不是「两套映射并存」——映射逻辑只有一份（`derivePredicate()`）。
真正的问题是 `SINGLE_STEP` 表比本节旧，而**降级到兜底谓词等于把已知信息丢掉**：
`B` 已经说了是兄弟，降到 `sibling` 是白丢性别。

修正后：`B→brother`、`Z→sister`、`H→husband`、`W→wife`、`C→husband{role}`。
`sibling`/`spouse` 退为真正的兜底（源数据说不出性别时），现存 35 条 `spouse`
全是这种情况。

**旧谓词必须逐条清理，不能整键删除**：一个人的 `sibling` 可能指向三个人，
其中两个已细化为 brother/sister，第三个源数据只说「是手足」——整键删除
会把第三条也删掉，而它本来就是正确答案。

### 8.5 第二个普适问题：22 对谓词全是纯镜像

对 55 个谓词做 domain/range 互换检测，**`inverse` 关联的 22 对全部是纯镜像**，无一例外：

| | |
| --- | --- |
| `father` ↔ `childOfFather` | `memberOf` ↔ `hasMember` |
| `employer` ↔ `employee` | `parentOrg` ↔ `childOrg` |
| `owns` ↔ `ownedBy` | `successorOf` ↔ `predecessorOf` |
| `participantIn` ↔ `hasParticipant` | `eventAt` ↔ `hostsEvent` |
| `teacherOf` ↔ `studentOf` | `recommendedBy` ↔ `recommended` |
| `bornAt` ↔ `birthplaceOf` | `residedAt` ↔ `residentHere` |
| `publisher` ↔ `publishedBy` | `author` ↔ `authored` |
| `about` ↔ `topicOf` | `documentedBy` ↔ `documents` |
| `carriedBy` ↔ `carries` | `precededBy` ↔ `followedBy` |

**语言学上「反向」不是另一个谓词，而是同一关系的另一个视角。**
英语 `A employs B` = `B is employed by A`；中文「A 是 B 的雇主」=「B 是 A 的雇员」。

**代价**：谓词数虚增一倍（55 个里只有 33 个不同语义）；
改一个词的 aliases 要同步改两个（`father` 改了 `childOfFather` 不跟）；
存储时双向写边造成冗余（实测已有 5,216 对反向边纯冗余）。

**结论（已被 P5-5c 推翻）：删 `inverse` 字段，反向改用 `/反` 修饰符在查询时反转主宾。**
镜像词的别名挂在 `aliasViews` 上保留检索能力：

```js
{ key: 'teacherOf', label: '老师',
  aliases: ['教师', '业师'],
  aliasViews: { inverse: ['学生', '门生'] } }
```

检索「学生」→ 命中 `aliasViews.inverse` → 生成 `teacherOf/反` 查询 → 主宾反转。

---

#### 实施时的推翻：`inverse` 保留

上面这段推理本身没错，但它漏掉了一个**功能依赖**，实测后必须修正。

**`inverse` 不只是别名索引，它承担查询召回。**

`Graph.edgesByPredicate()` 与 `Query._collectRows()` 都靠 `inverseKey()` 做
跨 key 展开：

```js
// graph.js:167
const inv = this.registry.inverseKey(base);
if (!inv || inv === base) return direct;
return direct.concat(keep(this.byPredicate.get(inv) || []));
```

删字段就必须先建一套等价的 `/反` 展开机制，否则每次查「父亲」会静默漏掉
`childOfFather` 方向的断言。这是正确性问题，不是精简问题。

**而且预期收益在本项目不成立。** 实测 57 个谓词里：

| | 数量 |
| --- | --- |
| 有边数据的谓词 | **11** |
| 零边的谓词 | **46** |

有边的 11 个全是亲缘谓词（P5-5a/b 修过的那批）。其余 46 个是**能力声明**，
组织/事件/物的关系尚未导入——它们不是“重复定义”，而是“尚未启用”。
在零边的谓词上做镜像合并，只减少计数，不减少真实复杂度，
却会立即弄坏那 11 个有数据的谓词的查询。

**最终方案**：

| 字段 | 去留 | 理由 |
| --- | --- | --- |
| `inverse` | **保留** | 查询召回依赖，非纯别名 |
| `symmetric` | 保留但改为**显式声明** | 不再从 `inverse === key` 推导 |
| `/反` 修饰符 | 保留 | 与 `inverse` 互补，不互斥 |
| `subjectGender` | **删除** | 见下 |
| `genderFamily` | **删除** | 从未生效 |

#### `subjectGender` 是真正该删的

它声称约束**主体**，但 `maleChild` 的 label 是「儿子」：

```
A --maleChild--> B   读作「A 的儿子是 B」
                    主体 A 是父，客体 B 才是孩子
```

约束应落在**客体**上。原注释写的是
“Gender is a hard constraint on the SUBJECT of this edge (**the child**)”——
把主体当成孩子，主体/客体搞反了。

这个错误**从未被发现**，因为 `checkAssertion()` 只校验 domain/range，
完全不看性别字段。它从第一天起就是死代码，只持续误导读者。

已改名 `objectGender` 并指回客体，`matchesGender()` 同步修正。
这个错误与 P5-5b 删 `elderBrother` 的理由是同一个毛病——
**主体视角与 label 视角混用**。

### 8.6 编码：复用 CBDB 记法，不重造

`path` 的序列化直接用 CBDB 的字母链：

| 谓词 | 字母 | 谓词 | 字母 |
| --- | --- | --- | --- |
| `father` | `F` | `son` | `S` |
| `mother` | `M` | `daughter` | `D` |
| `brother` | `B` | `sister` | `Z` |
| `husband` | `H` | `wife` | `W` |
| `concubine` | `C` | `affinal` | `A` |

于是「岳父」= `WF`，「堂兄弟」= `FBS`。**与 CBDB 源数据同构，导入零转换。**

这一点很重要：如果自造一套编码，就多一层翻译，每层翻译都是一次出错机会。
CBDB 的 488 种亲属编码可以直接落到「基础关系 + 路径」上，不需要 488 条映射表。

### 8.7 三档时间性与两层模型的正交关系

`temporality`（§2.2）加在**基础原语**上，路径继承组合规则：

| 基础原语 | `temporality` | 理由 |
| --- | --- | --- |
| `father` `mother` `son` `daughter` `brother` `sister` `affinal` | `persistent` | 血缘一旦确立不可撤销 |
| `husband` `wife` `concubine` | `concurrent` | 婚姻可终止（离异、休妻） |

路径的 `temporality` 由**最弱的成员**决定（`concurrent` 弱于 `persistent`）：
岳父 = `wife` + `father`，含 `concurrent` → 婚姻终止后岳父关系是否成立需显式标注。

### 8.8 修饰符：如何表达「长子」「继母」「亡父」

字母链表达**关系路径**，修饰符表达**同一步内部的差异**。修饰符是正交的：

| 修饰符 | 语法 | 例子 |
| --- | --- | --- |
| 序数 | `+`(长) `-`(幼) `1`/`2`/`3`(第N) | `S+` 长子、`Z2` 次女 |
| 继/养 | `^` | `F^` 继父 |
| 收养 | `[]` | `S[]` 养子 |
| 否定 | `/非` | `F/非` 非父 |

**这些是「断言的内容」，不是「谓词的定义」**，所以不进注册表，进边的字段：

```jsonc
{ "predicate": "son", "qualifiers": { "order": "eldest" } }
{ "predicate": "father", "qualifiers": { "kind": "step" } }
```

### 8.9 字段最终定案

**基础原语（10 个）的字段：**

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `key` | 是 | 英文标识 |
| `letter` | 是 | 单字母编码（`F`/`M`/`S`…），用于路径 |
| `label` | 是 | 默认显示名 |
| `domain` | 是 | 主体类型 |
| `range` | 是 | 客体类型 |
| `temporality` | 是 | `persistent`/`concurrent`/`attribute` |
| `symmetric` | | 反向即自身 |

**非亲缘谓词**（任职、参与、出版等）沿用原字段集，但删掉亲缘专用项：

| 删除 | 理由 |
| --- | --- |
| `inverse` | 改由 `/反` 修饰符；镜像词进 `aliasViews` |
| `subjectGender` | `son`/`daughter` 已是独立原语，无需性别约束 |
| `genderFamily` | 同上，不再需要族互斥标记 |
| `qualifiers`（数组） | 改 `usesRole`/`usesPlace` 布尔 + 边的 `qualifiers` 对象 |
| `aliasesNote` | 并入 `description` |

### 8.10 与检索、可视化的关系

**检索「孙子」**：不查某个 `grandson` 谓词，而是路径 `SS`——
递归两跳 `son` 边。这走 §9.8（`分层架构重构方案.md`）已实测的递归方案，
限深默认 5，正常家谱 0.85ms。

**可视化「家谱图」**：路径长度天然决定纵深。`F`/`S` 是一代，`FF` 是两代，
渲染时按路径长度分层，不需要另建层级表。

**「所有湖北人物」这类查询**：仍需要 `place` 作为实体类型（§1.2），
路径模型不解决这个问题——它解决的是**关系**，不是**属性**。
